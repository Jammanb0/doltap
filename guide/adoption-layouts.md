# 환경에 맞게 적용하기

[사용 안내](README.md) · [시작하기](getting-started.md)

공통 조사·승인 절차는 [APPLY.md](../APPLY.md)가 원본입니다. 여기는 위치와 보관
방식이 다른 사례를 설명합니다. 사례에 맞지 않는 환경도 조사 결과로 계획을 세우며,
아래 내용을 자동 설치나 모든 환경의 동작 보장으로 읽지 않습니다.

## 같은 저장소에 규칙과 기록을 함께 두기

운영 루트와 코드 저장소가 같은 일반적인 구성입니다. 기존 규칙과 기록을 승인된
범위에서 합치고, Git에 남기기로 한 문서와 변경만 그 저장소에 커밋합니다.
커밋은 로컬 이력이며 다른 기기·협업자에게 전달하려면 별도의 공유가 필요합니다.

## 회사 레포 밖의 부모 폴더에 개인 기록 두기

```text
workspace/                 운영 루트·에이전트 시작 위치 후보
  AGENTS.md                기존 개인 규칙과 doltap 안내
  CLAUDE.md                부모 AGENTS.md로 연결
  .doltap/                 개인 운영 기록
  repo/                    회사 작업 저장소
    .git/
    AGENTS.md              회사 지침, 보존
    CLAUDE.md              회사 지침, 보존
```

부모에 기존 지시 파일이 있다면 내용을 보존해 합칩니다. 부모의 CLAUDE.md 본문을
부모 AGENTS.md로 옮길 때도 도구별 적용 범위가 달라지지 않는지 확인하고 승인받습니다.
회사 레포의 파일은 읽기 전용으로 조사하고, 이 설치 때문에 수정·이관하지 않습니다.
부모에 파일이나 하위 레포가 있으면 `init`으로 덮어쓰지 않습니다.

부모가 실제로 Git 밖이면 회사 `.gitignore`에 추가할 것은 없습니다. doltap은 Git
없이 사용할 수 있고, 설치를 위해 회사 레포에 브랜치·커밋·remote 변경을 만들 필요도
없습니다. 부모가 더 상위의 Git에 속해 있지는 않은지 먼저 확인합니다.

적용 계획은 다음처럼 구분할 수 있습니다.

| 항목 | 이 사례의 판단 |
| --- | --- |
| 부모 지침 병합·.doltap 생성 | 적용 — 승인된 부모 파일만 변경 |
| 회사 지시 파일·설정 변경 | 해당 없음 — 기존 원본 보존 |
| 문서 커밋·Git 제외 설정 | 해당 없음 — 부모가 Git 밖이고 로컬 보관을 선택 |
| 코드 작업 | 설치 이후 별도 요청에 따라 repo에서 진행 |
| 새 세션의 규칙 로딩·기록 쓰기 | 실제 확인 전까지 미확인 |

### 명령을 어디서 실행할까

아래는 운영 루트에서 실행하는 위치 예시입니다. `doltap` 실행 방법은
[시작하기](getting-started.md)를 따릅니다. 실제 경로가 다르면 바꿉니다.

```sh
doltap check .
doltap map .
git -C repo status --short
git -C repo rev-parse --show-toplevel
```

코드의 검사·커밋·push는 repo를 기준으로 합니다. 개인 문서를 별도 Git에 남긴다면
그 커밋은 운영 루트에서 합니다. **모든 Git 명령을 repo에서 하라**고 쓰면 개인 문서
커밋을 처리할 수 없으므로, 대상별 기준을 구분합니다. 회사 코드 커밋은 그 저장소의
diff와 결과 커밋으로 확인하며 부모의 깨끗한 상태로 대신하지 않습니다.

부모 AGENTS.md에는 설치 후에도 쓸 위치·보관·지침 적용 규칙을 남깁니다. 예를 들어
“운영 문서와 doltap 명령은 부모 기준, 코드와 코드 Git 작업은 repo 기준, repo의
기존 지침을 작업 전에 읽고 준수, repo 문서는 doltap 관리에 등록하지 않음”처럼
범위를 명시합니다. 이것은 에이전트에게 주는 지침이며 강제 접근 차단 기능은 아닙니다.

repo 파일에 ID를 발급하거나 운영 문서에서 ID 관계로 연결하면 관리 범위에 들어갈
수 있습니다. `audit repo`는 미등록 Markdown도 읽으며, 이동 탐색은 하위 폴더까지
볼 수 있습니다. Git 제외 설정은 doltap의 읽기·쓰기 범위를 제한하지 않습니다.

### 에이전트는 어디서 시작할까

부모를 작업 공간으로 열면 운영 기록과 코드를 함께 다루기 쉽습니다. 다만 **시작
위치, 지침 로딩, 파일 권한, 프로젝트 설정을 각각 확인**해야 합니다.

- Codex는 보통 Git 루트부터 현재 작업 위치까지 AGENTS.md를 찾습니다. repo에서
  시작할 때 Git 밖 부모의 AGENTS.md를 자동으로 읽는다고 가정하지 않습니다.
  [공식 지침 탐색 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Claude Code는 상위 CLAUDE.md를 읽고, 하위 지침은 해당 파일을 읽을 때 추가로
  로딩합니다. AGENTS.md는 별도 import나 명시적 읽기가 필요합니다. 양쪽 지침의
  충돌을 해소하고 실제로 무엇을 읽었는지 확인합니다.
  [공식 메모리 문서](https://code.claude.com/docs/en/memory)
- repo에서 시작해도 추가 디렉터리 접근을 설정하는 방법이 있습니다. 접근 허용과
  지침·훅·MCP 등 프로젝트 설정의 로딩은 별개입니다. 부모에서 시작했다고 회사
  레포의 모든 설정까지 적용됐다고 보지 않습니다. 필요한 설정이 빠지면 시작 위치나
  승인된 접근 방식을 조정합니다. [공식 권한 문서](https://code.claude.com/docs/en/permissions)

세부 동작은 사용 중인 도구·버전·설정에 따라 확인합니다. 필요한 파일을 못 읽거나
못 쓸 때 회사 지침을 바꾸거나 권한을 우회하지 않습니다. 새 세션이 부모의 current와
status, 코드 작업에 필요한 회사 지침을 읽는지 확인합니다. 확인하지 못했으면
그 사실을 설치 결과에 남깁니다. 지침 몇 줄만으로 준수를 보장하지 않습니다.

## 부모의 개인 기록에도 Git 이력이 필요하다면

부모 Git은 선택입니다. 사용자가 원하면 개인 문서의 커밋 이력을 남길 수 있지만
회사 레포의 remote를 부모에 복사하거나 새 remote를 자동으로 연결하지 않습니다.

부모에 Git을 만들기로 했다면 하위 회사 레포를 부모에서 추적하지 않도록 정합니다.
예를 들어 부모 `.gitignore`의 `/repo/`로 제외하고 실제 스테이징 대상을 확인합니다.
이는 회사 레포의 `.gitignore`를 고치는 일이 아닙니다. 부모가 이미 다른 상위 Git에
속하면 그 관계까지 확인한 뒤 결정합니다.

`git init` 자체가 하위 레포를 등록하지는 않습니다. 이후 `git add .` 등으로 하위
레포를 포함하면 내장 저장소가 인덱스에 들어갈 수 있습니다. Git은 정식 submodule
등록 없이 내장 저장소를 추가할 때 경고합니다. [git add 문서](https://git-scm.com/docs/git-add)

**이미 부모에서 추적 중이면 ignore 한 줄로 해결되지 않습니다.** 추적 해제는
별도 변경안으로 다루고 회사 레포 파일을 삭제하지 않습니다. 미추적 파일의 로컬
제외에는 `.git/info/exclude` 같은 방법도 있으므로 `.gitignore`만 필수인 것은
아닙니다. [Git 제외 문서](https://git-scm.com/docs/gitignore)

부모와 repo의 커밋·remote는 별도로 관리합니다. 부모 Git의 커밋으로 회사 코드가
커밋됐다고 보고하지 않습니다. 부모의 미커밋 파일이나 PC 자체의 손실까지 로컬
Git이 보호하지는 않으므로 필요한 백업·공유 방법은 따로 정합니다.

Git 없이도 남아 있는 `.doltap/recovery/` 자료로 해당 doltap 쓰기를 복구할 수
있습니다. 모든 수동 편집이나 직접 삭제를 보관하는 전체 이력은 아닙니다.
Git 또한 커밋한 상태의 이력이라는 범위가 있습니다. [복구 안내](moving-deleting.md)

## 여러 저장소·다른 위치라면

공통 조사에서 작업 저장소마다 코드 위치·지침·Git 기준을 구분합니다. 별개의
프로젝트 규칙을 하나로 합치거나, 한 저장소의 승인·브랜치·remote를 다른 저장소에
적용하지 않습니다. 운영 기록도 공통으로 둘지 프로젝트별로 나눌지 먼저 정합니다.
이번 부모·단일 레포 사례를 여러 저장소의 검증 근거로 넓히지 않습니다.

## 골격 위치와 정리

골격 위치는 템플릿을 읽는 소스 위치이며, 운영 문서를 둘 위치와 다릅니다.
`.doltap-bootstrap/`은 기본 경로 예시입니다. APPLY의 **부트스트랩 커밋**은 적용
준비 내용을 남기는 커밋으로, 폴더 이름과 무관하고 추적할 변경이 있을 때만 생깁니다.

| 골격의 형태 | Git 제외 | 적용 후 정리 |
| --- | --- | --- |
| 이번 적용을 위한 임시 클론 | Git 안이면 승인된 제외 방식, 밖이면 불필요 | 정리 대상으로 합의하고 확인 절차를 통과했을 때 |
| 원래 있던 doltap 소스 | 새 제외 설정이 필요한지 조사 | 하지 않음 |
| doltap 저장소 자신에 적용 | 자기 소스는 제외하지 않음 | 하지 않음 |

정리 여부는 **이번 적용을 위해 임시로 마련했는가**로 가릅니다. 저장소 밖이라고
지워도 되는 것은 아닙니다. 형태·제외 방식·정리 여부와 실제 위치는 세팅 status에
남기고, 실제 삭제 확인 절차는 세팅 plan을 따릅니다. 운영 루트·코드 저장소·기존
골격 소스나 이들을 포함하는 상위 폴더를 임시 클론으로 취급하지 않습니다.

기록에는 운영 루트 기준으로 개인정보 없는 상대 경로만 씁니다. 다른 드라이브이거나
상대 경로에도 사람·계정 이름이 드러나면 기록하지 않습니다. 필요한 세션에서만
경로를 확인하고 셸에 맞게 인용합니다. 이 원칙은 Git에 커밋하지 않을 때도 같습니다.
