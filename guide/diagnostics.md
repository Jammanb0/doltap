# 검사 결과 읽고 고치기

[사용 안내](README.md) · [명령과 문법](reference.md) · [검토](review.md)

`doltap check .`는 문서를 고치지 않고 문제와 확인 항목을 보여줍니다.
`✗ 문제`가 있으면 종료 코드 1, `! 확인`만 있거나 모두 통과하면 0입니다.
확인 항목은 내용이 틀렸다는 판정이 아니라 사람이 판단할 지점입니다.

## 한 항목 읽기

CLAUDE.md에 import가 없을 때 출력되는 문제 부분입니다.

```text
✗ 문제 1개
  [CLAUDE_IMPORT_MISSING] CLAUDE.md
    `@AGENTS.md` 가 없어 AGENTS.md로 이어지지 않습니다
    다음: CLAUDE.md의 규칙 본문을 AGENTS.md로 옮기고 @AGENTS.md 한 줄로 연결하세요.
```

- 대괄호는 **진단 코드**입니다. 한국어 문구가 달라져도 같은 검사 항목을 구분합니다.
- 그 옆은 **고칠 위치**입니다. `파일:행`이면 그 행을, 파일만 있으면 문서 전체를 봅니다.
  없는 파일이나 폴더를 가리키는 경우도 있습니다. 경로는 검사한 프로젝트 기준입니다.
- 설명 아래의 **관련**은 함께 볼 위치입니다. 중복 ID의 다른 범위나 옮겨진 대상,
  재검토할 두 범위가 있으면 표시합니다. 다른 위치가 없으면 이 줄은 생략합니다.
- **다음**은 수정·검토를 시작할 행동입니다. 명령의 실행 결과나 승인 기록이 아닙니다.

위 예시에서는 기존 규칙 본문을 보존해 원본으로 옮기고 CLAUDE.md를
`@AGENTS.md` 한 줄로 정리한 뒤 다시 검사합니다. 같은 문제는 골격 검사와
그래프 검사 양쪽에서 발견돼도 한 번만 표시합니다.

## 자주 만나는 코드

| 코드 | 먼저 할 일 |
| --- | --- |
| `REQUIRED_DOCUMENT_MISSING` | 없는 필수 문서를 복원하거나 프로젝트에 맞게 작성합니다. |
| `DOCUMENT_PATH_MISSING`, `LINK_FILE_MISSING` | 표시된 행의 경로와 실제 파일을 대조합니다. |
| `ID_DUPLICATE` | 관련 위치와 본문을 비교해 원본을 정합니다. 복사본은 중복 앵커를 제거한 뒤 새 ID를 발급하고 참조를 대조합니다. |
| `ANCHOR_CROSSED`, `ANCHOR_END_MISSING` | 같은 ID의 시작·끝 앵커와 닫는 순서를 확인합니다. |
| `RELATION_PATH_STALE`, `LINK_PATH_MISMATCH` | 관련 위치의 ID가 의도한 대상인지 확인합니다. 이동한 관계 경로는 move-fix 미리보기로 확인합니다. |
| `RELATION_ID_MISSING`, `RELATION_DELETED` | 대상의 발급·삭제 기록을 읽고 살아 있는 대상과 연결합니다. |
| `DOCUMENT_UNREACHABLE`, `WORKSTREAM_INDEX_UNREACHABLE` | 진입점이나 current·history 색인에서 문서로 이어지는 indexes 관계를 확인합니다. |
| `REVIEW_STALE` | 양쪽 내용을 읽고 변경 영향을 판단한 뒤 해당 관계의 검토를 기록합니다. |
| `REVIEW_INVALID`, `REGISTRY_INVALID` | 표시된 표 행의 필드와 허용 값을 확인합니다. |
| `REGISTERED_RANGE_MISSING` | 이동인지 직접 삭제인지 확인하고 move-fix 또는 delete-fix 미리보기를 봅니다. |
| `RECOVERY_PENDING` | 표시된 실행 ID로 recover 미리보기를 읽습니다. |
| `PLACEHOLDER` | 표시된 행을 채우고 처리한 자리표시자 주석을 지웁니다. |
| `OPERATING_DIR_IGNORED` | 운영 기록을 공유할지 판단합니다. 로컬 전용 의도라면 남겨도 됩니다. |

수정 뒤에는 같은 프로젝트를 다시 검사합니다. 한 원인으로 여러 항목이 생길 수
있습니다. 예를 들어 파일 이동은 필수 파일 누락·링크 오류·낡은 관계 경로를 함께
만들 수 있습니다. 한 항목을 고친 뒤 다른 판정까지 해결됐다고 가정하지 않습니다.

## 재검토가 필요한 이유

`REVIEW_STALE`는 검토 기록이 없는 경우와 이전 검토 이후 내용 해시가 바뀐 경우를
구분합니다. 내용 변경은 관계 유형이 검토 대상으로 삼는 쪽에 한해서 안내합니다.
예를 들어 depends-on은 도착, produces는 출발, verified-by와 update-with는 양쪽을 봅니다.
해시는 정규화한 본문을 비교하므로 단순 줄바꿈 변경을 모두 내용 변경으로 보지는 않습니다.

출력의 `doltap context <ID>`로 연결된 범위를 읽은 뒤
`doltap review <관계-ID> --as <판단> --why <이유> --actor <주체>`로 기록을 미리 봅니다.
판단은 `반영함`·`영향 없음`·`재검증함`, 주체는 `사람`·`에이전트`입니다.
띄어쓰기가 있는 값은 따옴표로 감쌉니다. `영향 없음`은 이유를 10글자 이상 적습니다.
실제로 검토하지 않고 안내를 없애기 위해 기록하지 않습니다.

진단에 나온 명령은 **검사한 프로젝트 폴더에서** 실행합니다.
다른 폴더에서 `check <프로젝트>`를 실행했다면 먼저 그 프로젝트로 이동하거나,
그래프 명령에 `--root <프로젝트>`를 붙입니다. 꺾쇠 안의 값은 실제 값으로 바꿉니다.
쓰기 명령은 기본 미리보기이며 변경안을 확인한 뒤 허용된 작업에 `--apply`를 붙입니다.
자세한 이동·삭제 절차는 [이동·삭제·복구](moving-deleting.md)에 있습니다.

## JSON을 사용하는 도구

`doltap check . --json`의 스키마 이름은 `doltap.check.v1`입니다.
기존 `problems`, `notices`, `nodes`, `edges`와 각 진단의 `where`, `message`를 유지합니다.
문제·확인 항목에는 다음 필드가 추가됩니다.

| 필드 | 뜻 |
| --- | --- |
| `code` | 안정적인 진단 분류 문자열. 문구를 파싱하는 대신 사용합니다. |
| `location` | `{ "path": "파일", "line": 12 }`. 행을 특정하지 못하면 line을 생략합니다. |
| `hint` | 다음 행동을 설명하는 문장. 실행 명령 API가 아닙니다. |
| `related` | `{ "path": "파일", "line": 12, "label": "설명" }`의 배열. line은 선택 사항이며 관련 위치가 없으면 빈 배열입니다. |
| `reason` | REVIEW_STALE에만 제공. unreviewed, source-changed, target-changed, both-changed 중 하나입니다. |

출발·도착은 선언한 관계의 방향입니다. 대칭 관계의 내부 ID·해시 정렬 순서와 구분합니다.
소비 도구는 모르는 코드나 추가 필드를 허용하고, 메시지와 hint의 문구 자체에 의존하지
않도록 작성합니다. 터미널의 공백·줄 배치는 기계용 계약이 아닙니다.
존재하지 않는 검사 폴더나 잘못된 옵션처럼 검사를 시작하지 못한 CLI 오류는 이 진단
배열에 포함되지 않으며 stderr와 종료 코드로 확인합니다.
