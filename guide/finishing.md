# 대작업 마무리와 아카이브

[사용 안내](README.md) · [전체 흐름](workstreams.md) · [실행 방법](getting-started.md)

완료 조건을 검증하고 반영 대상을 확인한 뒤 진행합니다. 여기서는 순서를 설명하며
실제 승인·브랜치 절차의 원본은 적용한 프로젝트의 .doltap/plans/workstreams.md입니다.
사용자가 허용한 종료점까지 실행합니다. push나 브랜치 삭제가 자동으로 포함되지는 않습니다.

## 남은 판단과 계속 쓸 규칙 확인

```sh
doltap archive-check .doltap/plans/workstreams/010-example
```

check는 문서 구조와 관계를, archive-check는 지정 범위의 종료 전 선언을 확인합니다.
둘 다 읽기 전용이고 archive-check 자체가 폴더를 옮기지는 않습니다.

전제·열린 질문은 별도 ID 범위로 감싸고 상태를 하나 선언합니다.

```markdown
- `열린 질문` 기존 형식도 지원할 것인가
- `상태` 해결
```

미해결은 처리해야 합니다. 이월은 작업 밖의 활성 노드가 해당 항목을 직접
가리켜야 하고, 폐기는 같은 범위에 이유가 필요합니다. 코드·HTML 주석 속
예시는 실제 선언으로 세지 않습니다.

decisions.md의 각 결정 절에는 다음 중 하나를 적습니다.

```markdown
## 앞으로 유지할 결정
- `계속 유효` 활성 원본: .doltap/plans/decisions.md 「지원 범위」

## 이번 작업에만 해당하는 판단
- `이번만` 일시적인 검증 환경 선택
```

아직 이관하지 않았다면 진행 중에는 옮길 곳을 표시할 수 있습니다.
종료 전에는 계속 쓸 규칙·결정만 담당 활성 문서에 실제로 반영하고 대조합니다.
검사 통과는 “저기에 진짜 옮겨졌다”는 증거가 아닙니다. 과거 조사 과정을
활성 문서로 통째로 복사할 필요는 없습니다.

## 완료를 기록하고 보관

1. 완료 조건을 확인하고, 승인된 반영을 마친 대상에서 다시 검증합니다.
2. status에 완료 결과·반영 위치·검증 결과·다음 행동 없음을 적습니다.
3. history에 결과와 보관 위치를 적고 current에서 활성 작업과 관계를 제거합니다.
4. 폴더 전체를 .doltap/archive/workstreams/로 옮기고 history에서 ID로 연결합니다.
5. move-fix의 수정안을 보고 적용한 뒤 check와 프로젝트 검증을 실행합니다.

```sh
doltap move-fix .
doltap move-fix . --apply
doltap check .
```

실제 폴더 이동은 파일 탐색기나 현재 셸에 맞는 명령으로 합니다. ID를 새로 발급하거나
아카이브에 복제본을 남기지 않습니다. 커밋·push는 프로젝트의 승인 범위를 따릅니다.
취소라면 미완성 구현을 완료로 반영하지 않고 결과와 취소 이유를 남겨 보관합니다.

아카이브는 당시 기록입니다. 다음 작업의 현재 규칙을 알려면 활성 plans·rules를
읽습니다. 나중에 보관 기록을 삭제하는 일은 [삭제 절차](moving-deleting.md)로 따로 다룹니다.
