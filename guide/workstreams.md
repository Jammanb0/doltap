# 대작업은 어떻게 흘러가나

[사용 안내](README.md) · 이전: [개념](concepts.md) · 다음: [시작하기](getting-started.md)

**대작업(워크스트림)은 따로 목표와 상태를 관리할 만한 작업 묶음**입니다.
예를 들어 “검색 기능 개편”은 여러 파일과 판단이 연결되므로 대작업으로
관리할 수 있습니다. 오타 하나를 고치는 일까지 매번 대작업으로 만들지는 않습니다.

doltap을 처음 적용하는 것과 대작업을 만드는 것은 다릅니다.
`init`은 프로젝트에 문서 골격을 넣는 명령입니다. 그 프로젝트에서 이후
진행하는 대작업은 사람이나 에이전트가 별도의 문서 폴더로 만듭니다.

```text
할 일 제안
  → 목표·범위·작업 위치를 정하고 대작업 생성
  → current에 위치 연결
  → 작업·검증·status 갱신
  → 완료 조건과 남은 판단 확인
  → 승인된 반영·종료 절차 수행
  → history에 결과 기록, current에서 제거
  → 대작업 폴더 전체를 archive로 이동
```

이 화살표는 자동으로 실행되는 프로그램 순서가 아닙니다. 사람이 요청하고
에이전트가 문서를 쓰거나 명령을 실행하며 이어갑니다.
CLI에는 대작업 생성·종료를 자동 실행하는 명령이 없습니다.

## 1. 만들 때 — 무엇을 끝낼 것인지 정한다

“검색을 개편해줘”라는 요청을 받으면 기존 작업에 속하는지 먼저 확인합니다.
새 대작업으로 정하면 목표, 포함·제외 범위와 완료 조건을 소개 문서에 적습니다.
Git을 쓴다면 작업 브랜치와 반영 대상도 정합니다.

```text
.doltap/plans/workstreams/010-search/
  README.md       무엇을 왜 하는지, 어디까지 하면 끝인지
  status.md       지금 어디까지 왔는지, 다음 행동은 무엇인지
  plan.md         순서와 검증 방법이 필요할 때
  decisions.md    중요한 판단과 이유를 보존할 때
  design.md       상세 설계가 필요할 때
```

번호와 이름은 예시입니다. 기존 활성·아카이브 번호를 확인해 다음 번호를 쓰고,
이전에 쓴 번호는 다시 쓰지 않습니다. 필수 파일은 README와 status 둘입니다.
필요 없는 선택 문서를 빈 틀로 만들지 않습니다.

새 문서에 ID를 발급하고 current에서 소개와 상태를 연결하면 다음 세션이 찾을 수
있습니다. current에는 상세 진행 상황을 복사하지 않고 **위치만** 적습니다.

에이전트에게는 이렇게 요청할 수 있습니다.

```text
현재 대작업과 운영 규칙을 읽어줘.
검색 개편을 새 대작업으로 관리할지 판단하고 범위와 완료 조건을 제안해줘.
작업 위치를 정한 뒤 소개와 상태를 만들고 current에서 연결해줘.
```

골격의 승인 규칙을 쓰는 프로젝트에서는 생성과 작업 위치를 먼저 합의합니다.
이미 명확하게 승인한 범위의 개별 편집마다 같은 승인을 반복하지 않습니다.

## 2. 진행할 때 — 현재 상태를 한곳에 유지한다

작업을 시작할 때 AGENTS와 안내된 규칙을 읽고 current → README → status를
따라갑니다. plan이나 decisions는 순서·판단 이유가 필요할 때 추가로 읽습니다.

코드를 고치고 검증한 뒤에는 status를 **현재 상태로 갱신**합니다.
“어제 한 일, 오늘 한 일”을 계속 쌓기보다 끝난 것·남은 것·막힌 점을 바로 알 수
있게 씁니다. 새 세션에서는 다음과 같이 이어갈 수 있습니다.

```text
AGENTS.md와 안내된 규칙을 읽고 current가 가리키는 대작업을 이어가줘.
README와 status를 확인하고, 기록된 작업 위치에서 다음 행동을 진행해줘.
```

프로젝트 공통 규칙이나 전제가 생기면 종료 때까지 작업 폴더에 묻어두지 않습니다.

| 내용 | 현재 원본 |
| --- | --- |
| 항상 따를 규칙 | AGENTS.md 또는 rules/ |
| 프로젝트 전체 설명 | plans/project.md |
| 여러 작업에 적용할 결정·전제 | plans/decisions.md |
| 아직 시작하지 않은 후보 | plans/ideas.md |
| 이 작업에서 판단한 과정과 당시 근거 | 작업 폴더의 decisions.md |

작업의 결정에는 `계속 유효`와 담당 활성 원본, 또는 `이번만`을 적습니다.
“어디에 옮겼다”는 표식만으로 실제 이관이 증명되지는 않습니다.

## 3. 마칠 때 — 결과를 확인하고 원문을 보관한다

“코드 작성이 끝남”과 “대작업 종료”는 다릅니다. 완료 조건을 검증하고, 계속 쓸
규칙을 활성 원본에 반영하며, 미해결 항목을 처리해야 합니다.
Git 반영·push·아카이브는 프로젝트에서 승인한 범위에 따라 별개로 진행합니다.

완료로 마친다면 결과가 반영 대상에 들어간 것을 확인한 뒤 status를 완료 상태로
갱신합니다. history에는 결과와 보관 위치를 한 줄 남기고 current에서는 뺍니다.
그다음 폴더 전체를 옮기고 ID·관계 경로를 맞춥니다.

```text
.doltap/plans/workstreams/010-search/
                    ↓ 폴더 전체 이동, ID 유지
.doltap/archive/workstreams/010-search/
```

아카이브는 끝난 작업의 기록 보관소입니다. 내용을 자동으로 현재 규칙으로 만들지
않으며 다음 세션이 전부 읽을 필요도 없습니다. 과거 판단의 이유가 필요할 때
history에서 찾아봅니다. 취소한 대작업도 결과와 이유를 남겨 보관합니다.

아카이브는 삭제나 복구 백업과 다릅니다. 완료한 작업을 보관하려고 `delete`를
실행하지 않습니다. 실제 종료 순서는 [마무리](finishing.md)에 있습니다.
골격의 상세 운영 원본은 프로젝트 안의 `.doltap/plans/workstreams.md`입니다.
