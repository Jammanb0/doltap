# doltap 구조 적용 — 단계

<!-- 이 문서는 골격 위치의 `setup-workstream/`에서 복사해 온 것입니다.
     `.doltap/plans/workstreams/<번호>-doltap-setup/plan.md`에 놓습니다. -->

> 배경과 완료 조건은 `README.md`, 지금 어디까지 왔는지는 `status.md`에
> 있습니다. 여기는 무엇을 어떤 순서로 하는지만 다룹니다.

이 프로젝트에는 아직 doltap의 워크스트림 규칙이 자리 잡지 않았습니다. 그래서 이
대작업만은 일반 규칙 대신 아래 단계를 따릅니다. 적용이 끝나 이 워크스트림을
아카이브한 뒤부터는 `.doltap/plans/README.md`와 `.doltap/plans/workstreams.md`가
원본입니다.

이 문서는 승인된 적용 구성에 맞춰 작성하는 계획 골격입니다. `status.md`의
「적용 구성」을 읽고 아래 각 단계의 대상과 조건을 구체화합니다. 해당 없는 단계는
이유를 적고, 미확인 항목에 의존하는 쓰기는 확인 전까지 진행하지 않습니다.
기존 제약·승인 절차를 생략하는 용도로 쓰지 않습니다.

문서 경로와 doltap 명령은 **운영 루트 기준**입니다. 코드 검사·Git 작업은 합의한
작업 저장소, 문서 Git 작업은 운영 문서를 추적하는 저장소에서 합니다. Git 작업이
없으면 해당 단계는 하지 않습니다. 아래 `<골격 위치>`와 `<임시 골격 경로>`는
`status.md`의 「골격 위치」에 적힌 값으로 바꿔 읽습니다.

**경로 자리가 비어 있으면** 상대 경로로 가리킬 수 없어 적지 않은 것입니다. 그
자리에 쓸 값을 사용자에게 한 번 묻고 이 세션 안에서만 씁니다. 문서에 적지
않습니다. 묻지 못하면 골격이 필요한 단계를 진행하지 않고 무엇이 막혔는지
알립니다.

## 1. 규칙을 가른다

변경을 승인받은 기존 지시 파일에 아래 성격의 내용이 섞여 있으면 해당 파일로
옮깁니다. 보존하기로 한 회사 레포 등의 지시 파일은 읽고 참조하며 수정하지 않습니다.

- 완료 전 확인 방법, 테스트·빌드 명령 → `.doltap/rules/verification.md`
- 답변 방식, 설명 태도 → `.doltap/rules/communication.md`
- 목적, 배경, 장기 방향, 범위의 상세 설명 → `.doltap/plans/project.md`

**항상 지켜야 하는 제약은 `AGENTS.md`에 남깁니다.** 옮기는 것은 상세 설명이지
제약 자체가 아닙니다. 특히 「하지 않는 것」은 작업 중에 매번 걸리는 선이라
`AGENTS.md`에 짧게 남기고, 그렇게 정한 배경만 `.doltap/plans/project.md`로 옮깁니다.

| 성격 | 어디에 |
| --- | --- |
| 작업할 때마다 걸리는 제약, 금지 사항, 승인 규칙 | `AGENTS.md`에 짧게 |
| 그 제약을 왜 정했는지, 배경과 장기 방향 | `.doltap/plans/project.md` |
| 특정 작업을 할 때만 필요한 절차와 체크리스트 | 해당 문서에 두고 `AGENTS.md` 안내표에서 가리킴 |

기존 `.doltap/`가 doltap과 다른 구조라면 폴더를 지우지 말고 위 기준으로 내용만
옮깁니다. 어디에 넣을지 애매한 것은 사용자에게 묻습니다.

## 2. 기록을 옮긴다

이관하기로 승인받은 문서(`TODO.md`, `NOTES.md`, 핸드오프 문서 등)가 있으면
성격에 따라 나눠 옮깁니다. `.doltap/plans/current.md`는 위치만 가리키는 색인이고
`.doltap/plans/history.md`는 짧은 색인이라, 상세 내용을 여기에 쌓지 않습니다.

| 무엇 | 어디로 |
| --- | --- |
| 진행 중인 작업의 배경·범위·완료 조건 | 그 워크스트림 폴더의 `README.md` |
| 그 작업이 지금 어디까지 왔는지 | 같은 폴더의 `status.md` |
| 남은 단계와 검증 방법 | 같은 폴더의 `plan.md` (필요할 때만) |
| 그 작업에서 정한 것과 이유 | 같은 폴더의 `decisions.md` (필요할 때만) |
| 진행 중인 작업이 어디 있는지 가리키는 줄 | `.doltap/plans/current.md` |
| 이미 끝난 작업의 원문 기록 | 폴더로 관리할 만하면 `.doltap/archive/workstreams/` 아래 그 폴더. 한 줄짜리 완료 메모는 만들지 않습니다 |
| 끝난 작업의 한 줄 요약과 보관 위치 | `.doltap/plans/history.md` |
| 아직 착수를 약속하지 않은 것 | `.doltap/plans/ideas.md` |

워크스트림 폴더 이름은 `<세 자리 번호>-<영문 소문자 이름>`입니다. 여기서 새로
만드는 워크스트림의 번호는 이 세팅 다음 번호부터 씁니다.

**한 줄짜리 기록까지 워크스트림으로 만들지 않습니다.** "무엇을 붙였다" 정도의
완료 메모는 배경도 완료 조건도 없어서, 폴더를 만들면 없는 내용을 지어내야
합니다. 원본에 그대로 두거나 `history.md`에 한 줄로 남깁니다. 무엇을
워크스트림으로 볼지는 `.doltap/plans/workstreams.md`의 「무엇을 대작업으로
보는가」가 원본입니다.

**여기서 만드는 워크스트림은 골격 위치의 `APPLY.md` 3번에서 이미 승인받았습니다.**
몇 개가 어떤 이름으로 생기는지를 그때 함께 보여주었기 때문입니다. 승인 목록에
없던 워크스트림을 새로 만들어야 하면 그때는 따로 묻습니다.

**원본 기록 문서를 어떻게 할지도 3번에서 정했습니다.** 정해진 것이 없으면
보존합니다. 원본을 안내문으로 바꾸기로 승인받았을 때만 원본에 이관처와 현재
원본을 적습니다. 읽기 전용으로 정한 파일은 그대로 두고 운영 문서에서 참조합니다.

## 3. 연결한다

**이 단계를 빠뜨리면 파일만 생기고 아무도 읽지 않습니다.**

- **운영 루트의** `AGENTS.md`에 문서 안내표를 넣습니다. 기존 안내가 있으면 항목을 더합니다.
- **운영 루트의** `CLAUDE.md`가 없으면 `@AGENTS.md` 한 줄로 만듭니다. 본문이 직접 들어 있으면
  그 내용을 `AGENTS.md`로 옮기고 한 줄로 줄일지 확인합니다. APPLY에서 승인받은
  선택을 따르고, 아직 결정하지 않았을 때만 묻습니다.
- Git 안의 문서를 제외하기로 했으면 승인된 제외 방식이 적용됐는지 확인합니다.
  Git 밖이면 제외 설정은 해당 없습니다. 보존할 회사 레포의 ignore는 수정하지 않습니다.
- 설치 뒤의 실행 위치·지침 적용 범위·기록 보관 방식을 운영 루트의 AGENTS.md와
  연결된 운영 문서에 반영합니다. 문서와 코드의 저장소가 다르거나 Git이 없다면
  workstreams의 브랜치·커밋·반영 단계도 그 조건에 맞춥니다. 세팅 status의 값을
  여러 원본으로 복제하지 말고, 계속 쓸 원본의 위치를 decisions에 남깁니다.

문서 배치 후 `node <골격 위치>/bin/doltap.mjs migrate .`의 미리보기를 봅니다.
승인 범위 안이면 `--apply`로 문서 ID와 색인을 연결합니다. 템플릿에서 복사한
ID를 다른 문서에 중복 사용하지 않습니다. 추가 범위와 관계는 필요한 곳만 만듭니다.
관리에서 제외한 코드 저장소의 파일에는 ID를 발급하거나 ID 관계로 등록하지 않습니다.

## 4. 현재 상태를 채운다

`.doltap/plans/project.md`와 `.doltap/plans/current.md`를 빈 틀로 두지 않습니다.
README, 코드, `git log`, 열린 이슈에서 확인되는 것으로 채웁니다. 확인되지 않는
것은 `<!-- 확인 필요: 무엇을 -->`로 남기고 사람에게 무엇이 비었는지 알립니다.

## 5. 어긋나는 규칙을 처리한다

기존 규칙과 골격이 충돌하면 조용히 덮어쓰지 않습니다. APPLY에서 이미 정한
선택을 따르고, 새 충돌만 짚어 사람에게 묻습니다. 개인 설정으로 조직의 지침을
무시하지 않으며 회사 규칙의 복제본을 새 원본으로 만들지 않습니다. 흔한 경우는 이렇습니다.

- 커밋 메시지 언어와 형식 — 기존 `git log`를 따르는 것이 보통 맞습니다
- 승인 범위 — 팀마다 다릅니다
- 이미 다른 문서 체계를 쓰고 있는 경우 — 섞을지 한쪽으로 통일할지 정해야 합니다

정한 결과와 그 이유는 `decisions.md`에 남깁니다. 결정마다 이 프로젝트에 계속
적용되는 것인지(`계속 유효`) 적용할 때만 필요했던 판단인지(`이번만`) 한 줄
선언합니다. 계속 유효한 것에는 담당 활성 원본이나 옮길 곳을 같은 줄에 적습니다.

## 6. 새 규칙을 다시 읽는다

**적용으로 바뀐 `AGENTS.md`와 `.doltap/rules/`의 문서를 전부 다시 읽습니다.**
지금 세션이 파일 변경을 자동으로 다시 읽는다고 가정하지 않습니다. 이 단계부터는
방금 놓은 규칙이 적용됩니다.

## 7. 적용됐는지 확인한다

파일이 생긴 것만으로는 확인이 되지 않습니다.

**명령으로 확인**

```text
node <골격 위치>/bin/doltap.mjs check .
```

기본값이면 `node .doltap-bootstrap/bin/doltap.mjs check .`, 골격이 이 저장소 자신이면
`node bin/doltap.mjs check .` 입니다.

안내표가 가리키는 경로가 실재하는지, `CLAUDE.md`가 `AGENTS.md`로 이어지는지,
필수 문서가 다 있는지, 남은 채우기 자리와 워크스트림 상태가 어떤지를 한 번에
봅니다. 문제가 있으면 종료 코드 1로 끝납니다. 아래 항목 가운데 기계가 대신 볼
수 없는 것은 직접 확인합니다.

**문서로 확인**

- `grep -rn "채우기\|고르기\|확인 필요" AGENTS.md .doltap/` 결과에 남은 것이
  무엇인지 사람에게 알렸는가
- `CLAUDE.md`에서 `AGENTS.md`로, `AGENTS.md`의 안내표에서 `.doltap/`의 각
  파일로 실제로 이어지는가. 안내표에 적힌 경로가 실재하는가
- 적용 전에 있던 규칙 중 사라진 것이 없는가. 옮겼다면 옮긴 자리에 실제로 있는가
- 같은 규칙이 두 곳에 원본으로 중복되어 있지 않은가
- 앞으로 계속 쓰는 활성 문서에 **임시 골격 경로** 참조가 남아 있지 않은가. 곧
  지울 폴더를 가리키면 안 됩니다. **이 세팅 워크스트림 문서와 그 아카이브
  기록은 검사에서 뺍니다.** 적용 절차를 설명하느라 그 경로를 담고 있는 것이
  정상입니다. 골격이 doltap 자신이나 계속 쓸 기존 소스면 정리는 **해당 없음**입니다.

  ```text
  grep -rnF --exclude-dir='*-doltap-setup' -- \
    <현재 셸에 맞게 인용한 임시 골격 경로> AGENTS.md CLAUDE.md .doltap/
  ```

  기본값이면 찾을 문자열은 `.doltap-bootstrap` 입니다.

  **`doltap check`는 이 검사를 대신하지 못합니다.** 검사기는 골격이 어디에 어떤
  이름으로 있는지 알 방법이 없어 기본값 `.doltap-bootstrap` 뒤에 경로가 이어진 것만
  봅니다. 적용이 진행 중이면 검사기가 그 사실을 확인 항목으로 알려 줍니다.
  다른 이름이나 경로에 두었거나 경로 없이 폴더만 가리켰으면 위 `grep`이
  유일한 확인 수단입니다.

**실제로 확인**

- 새 세션에서 "지금 뭐 하던 중이었지?"라고 물었을 때 에이전트가
  `.doltap/plans/current.md`를 찾아 읽고 답하는가
- 시작 위치에서 부모·작업 저장소의 필요한 지침과 프로젝트 설정이 적용되는가.
  운영 문서와 코드를 각각 읽고 쓸 권한을 확인했는가
- 보존 대상의 전후 파일 상태와 저장소별 Git 상태를 대조했는가. 기록 위치가
  분리됐다면 부모의 `git status`로 회사 레포의 상태를 대신하지 않았는가

명령·문서·새 세션 확인의 결과를 구분해 status에 남깁니다. 실행할 수 없었던
확인은 미확인으로 남기고, CLI 통과만으로 실제 지침 준수까지 검증했다고 쓰지 않습니다.

## 8. 임시 골격을 정리한다

**`status.md`의 「골격 위치」에 정리 대상이 `예`로 적힌 임시 클론일 때만
합니다.** 골격이 대상 저장소 자신이면(포크했거나 doltap 저장소 자신이면) 지울
것이 없으므로 건너뜁니다. 아래 명령의 경로를 저장소 루트로 바꿔 읽으면 **저장소
자체를 지우게 됩니다.**

지우기 전에 여섯 가지를 모두 확인합니다. 하나라도 아니면 지우지 않습니다.

- **이번 적용을 위해 마련한 임시 골격인가.** 누가 받았는지가 아니라 이번
  적용을 위한 것인지로 가릅니다. 원래 있던 폴더는 지우지 않습니다. 판단이 서지 않으면
  지우지 말고 사람에게 묻습니다. 아래 항목들은 잘 관리된 저장소일수록 더
  안전해 보이게 만들므로, 이 질문이 먼저입니다
- 「골격 위치」에 정리 대상으로 기록되어 있는가
- 그 경로를 해석한 절대 경로가 운영 루트·작업 저장소 또는 이들을 포함하는
  상위 폴더가 **아닌가**
- 그 경로 안에 `APPLY.md`, `template/`, `setup-workstream/`이 있어 실제 doltap
  골격이 맞는가. 잘못 기록된 경로가 남의 저장소를 가리킬 수 있습니다
- 7번의 임시 골격 경로 참조 검사가 통과했는가
- 폴더 안의 파일을 사용자가 고친 것이 없는가

```text
git -C <현재 셸에 맞게 인용한 임시 골격 경로> status --short
```

**이 명령이 승인 거부나 오류로 실패하면 확인되지 않은 것입니다.** 내가 이
폴더를 편집하지 않았다는 것은 사용자가 편집하지 않았다는 증거가 아닙니다.
확인될 때까지 지우지 말고, 무엇을 확인하지 못했는지 사람에게 알립니다.

확인이 끝나면 폴더를 지웁니다. 경로는 현재 셸에 맞게 인용하고, 하이픈으로
시작하는 경로가 옵션으로 읽히지 않도록 `--`를 넣습니다.

```text
rm -rf -- <현재 셸에 맞게 인용한 임시 골격 경로>
```

`.gitignore`에 넣었다면 **이번 적용에서 추가한 그 줄만** 지웁니다. 원래 있던
항목은 건드리지 않습니다. 다른 로컬 제외 방식을 썼다면 그곳에 이번에 넣은 항목만
정리합니다. 어느 Git에도 속하지 않는 임시 클론이었다면 넣은 항목이 없습니다.

**`.gitignore` 자체가 이번 적용으로 생긴 파일이고 그 줄이 전부였다면 파일째
지웁니다.** 적용 전에 없던 파일을 빈 채로 남기지 않습니다. 원래 있던
파일이었다면 줄만 빼고 파일은 남깁니다.

## 9. 일반 흐름으로 마무리한다

6번에서 새 규칙을 다시 읽었으므로 여기서부터는 일반 규칙이 적용됩니다. 다만
일반 흐름에 최종 커밋이 적용되는 경우 **세팅에만 해당하는 정리를 먼저 끝낸 뒤에
들어갑니다.** 추적할 변경이 없으면 커밋은 해당 없으며, 문서 갱신과 검증은 여전히 합니다.

**8번에서 임시 골격을 지우면 그 안의 `doltap check`도 함께 사라집니다.** 아래
5항이 가리키는 일반 흐름은 `history.md`와 `current.md`, 아카이브 폴더를 바꾼
**뒤에** 검사를 다시 돌리라고 합니다. 그 검사는 종료 과정에서 생긴 끊긴 연결을
잡는 자리이므로, **바꾸기 전에 미리 돌려 두는 것으로 대신할 수 없습니다.**

둘 중 하나를 고릅니다.

- **골격을 남겨 두고 끝냅니다.** 5항의 이력·색인·아카이브 갱신과 그 뒤의 검사를
  먼저 마치고, 정리 대상으로 정했다면 8번으로 돌아가 골격을 지웁니다. 커밋이
  있다면 그 전에 정리합니다. 실제 추적되는 삭제·제외 설정 변경만 해당 저장소의
  커밋에 넣습니다. 지웠다는 사실은 최종 status에 남기고, 커밋이 있을 때는
  메시지에도 적습니다.
- **먼저 지웠으면 다른 자리의 검사기를 씁니다.** `npx --yes
  github:Jammanb0/doltap check .` 로 받아서 돌립니다. 네트워크를 쓸 수 없거나
  내려받는 것이 내키지 않으면 앞의 갈래를 고릅니다.

둘 중 무엇을 했는지 `status.md`에 적습니다.

**검사 시점과 삭제 시점이 어긋나는 것을 그대로 적습니다.** 앞의 갈래를 고르면
검사할 때는 아직 골격이 남아 있습니다. 그때 `status.md`에 「지웠다」고 적으면
사실과 다릅니다. 검사 시점에는 예정으로 적고, 실제로 지운 뒤에 사실대로
고칩니다. 이 파일은 그대로 아카이브에 남으므로 마지막 값이 사실이어야 합니다.

1. 골격 위치의 `APPLY.md` 4번의 5항에서 기존 지시 파일에 넣었던 임시 연결 문구를 위
   3번의 정식 안내표로 대체합니다.
2. `.doltap/plans/current.md`에서 이 세팅을 뺄 때, 2번에서 옮긴 기록으로 만든
   다른 워크스트림이 있으면 그것은 남긴다는 것을 확인합니다.
3. `README.md`의 완료 조건을 하나씩 대조합니다.
4. **`status.md`의 「골격 위치」에 절대 경로가 들어가지 않았는지 봅니다.**
   들어갔다면 실제로 커밋·공유됐는지도 확인합니다. 커밋에 남았다면 현재 문장에서
   지우는 것만으로는 부족합니다. 공개됐거나 공개될 예정이면 사용자에게 알리고
   어떻게 할지 정합니다. 이력을 다시 쓰는 것은 사용자가 정할 일입니다.
5. **이번 구성에 맞춘 `.doltap/plans/workstreams.md`의 「마칠 때」와 「반영할 때」를
   따릅니다.** Git 작업이 없는 위치의 커밋·반영은 해당 없고, 문서 검증·보관은
   수행합니다. 반영부터 최종 확인과 브랜치 정리까지 거기 있고, 아카이브로
   옮기는 것은 사용자 허락을 받고 합니다. 순서를 여기에 다시 적지 않습니다 —
   두 곳에 적으면 한쪽만 고쳐져 어긋납니다.
