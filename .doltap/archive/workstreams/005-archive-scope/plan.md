# 아카이브 검사 범위 — 계획

> 무엇을 왜 하는지는 `README.md`, 지금 어디까지 왔는지는 `status.md`에
> 있습니다. 여기는 순서와 검증 방법만 담습니다.

순서가 중요합니다. 코드를 먼저 고치면 지금 있는 시험 둘이 깨지므로, 깨지는
것을 확인하고 나서 시험을 고칩니다. 깨지지 않으면 그 시험이 애초에 동작을
고정하지 못하고 있었다는 뜻이므로 그것도 확인 대상입니다.

## 1. 검사 대상 문서를 활성 문서만으로 좁힌다

`lib/check.mjs`가 문서 목록을 만들 때 아카이브 폴더에 들어가지 않게 합니다.
목록을 만든 뒤 거르면 파일 이름과 형식을 먼저 훑게 되므로, 재귀 탐색 전에
제외합니다. 한 자리에서 빼면 4번(링크), 5번(자리표시자), 7번(`.cairn` 참조)이
함께 아카이브를 보지 않게 됩니다.

같이 정리할 것

- 4번의 `staleArchive` 집계와 「아카이브 N곳은 아래 확인」 통과 문구
- 5번 안의 `isArchived` 건너뛰기. 목록에서 이미 빠지므로 필요 없습니다.
- 7번의 `SETUP_SUFFIX` 건너뛰기는 **남깁니다.** 활성 세팅 워크스트림에
  여전히 필요합니다.

검증: `node bin/cairn.mjs check .`에서 아카이브 경로가 하나도 안 나온다.

## 2. 번호 검사를 활성 쪽 실수만 잡도록 좁힌다

아카이브 폴더 이름에서 번호만 읽고, 판정 대상은 활성 워크스트림으로 한정합니다.

- 아카이브 이름 형식은 평가하지 않는다.
- 아카이브끼리의 충돌은 잡지 않는다.
- 활성이 지난 번호를 다시 쓰면 잡되, 오류 위치는 **활성 폴더**로 적는다.

검증: 4단계의 시험으로 고정합니다.

## 3. 지금 있는 시험이 깨지는 것을 확인한다

`npm test`를 돌려 아래 둘이 실패하는지 봅니다.

```text
아카이브는 자리표시자를 세지 않고, 끊긴 경로도 확인으로만 본다
아카이브에 끊긴 경로가 있으면 통과 문구가 그 사실을 밝힌다
```

두 시험 모두 없어진 동작을 검사하므로 실패해야 정상입니다. **실패하지 않으면
그 시험이 동작을 고정하지 못하고 있었다는 뜻이므로 이유를 확인합니다.**

## 4. 시험을 새 동작에 맞춘다

고칠 것

- 위 두 시험을 「아카이브 안은 아무것도 잡지 않는다」로 다시 씁니다.
- 「워크스트림 번호가 겹치면 잡는다」에 오류 위치가 활성 폴더인지 확인을
  더합니다. 지금은 메시지만 보고 있어 위치가 바뀌어도 통과합니다.

더할 것

- 아카이브 문서의 `.cairn` 언급을 잡지 않는다.
- 아카이브 폴더 이름이 형식에 어긋나도 잡지 않는다.
- 아카이브끼리 번호가 겹쳐도 잡지 않는다.
- `history.md`가 없어진 아카이브를 가리키면 문제로 잡는다.
- 아카이브만 있고 활성이 없어도 통과한다.

검증: `npm test` 전부 통과.

## 5. 두 README의 설명을 맞춘다

`README.md`와 `README.en.md`에 지금 이렇게 적혀 있습니다.

> 아카이브를 검사에서 통째로 빼는 것은 아닙니다 — 아카이브가 가리키는 끊긴
> 경로는 `확인`으로 알려 주고, 번호가 겹치는 것은 그대로 문제로 잡습니다.

앞 문장이 거짓이 됩니다. 두 파일을 함께 고칩니다. **한쪽만 고치고 다른 쪽을
놓치는 것이 이 저장소에서 반복된 실수입니다.**

검증: 두 파일에서 같은 뜻의 문장을 `grep`으로 찾아 둘 다 바뀌었는지 봅니다.

## 6. 전체 검증

```text
npm test
node bin/cairn.mjs check template
node bin/cairn.mjs check .
```

셋 다 통과하고 `check .`의 확인에 아카이브 경로가 없어야 합니다. 활성 문서가
임시 골격 이름을 설명해서 나는 확인은 남습니다. 범위 밖입니다.

## 7. 남은 기록 정리

- `status.md`를 마지막 상태로 갱신합니다.
- 검사 동작이 바뀐 것을 `docs/trials/README.md`에 반영할지 판단합니다.

푸시와 반영, 아카이브는 하지 않습니다. 사용자 승인이 따로 필요합니다.
