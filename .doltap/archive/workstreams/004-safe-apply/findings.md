## 재적용 시험

고친 절차가 실제로 통하는지 보려고 두 번째 임시 프로젝트 `tideline`에 다시
적용했습니다. 003의 첫 시험과 조건을 하나 바꿨습니다 — **골격을 `.cairn`이
아닌 `skeleton/`에 두었습니다.** 이름 가정 문제까지 함께 걸리게 하려는
것입니다.

적용은 이 세션을 모르는 별도 에이전트가 맡았고, README에 적힌 사용자 문장만
주었습니다.

## 이번 시험이 새로 찾은 모순 넷

넷 다 고쳤습니다.

### 1. 정리 대상 판정이 두 문서에서 달랐습니다 — 이번 작업이 만든 것

`APPLY.md`는 「이번 적용을 위해 받아 왔는가」로 가르라고 했는데, 같은 작업에서
고친 `setup-workstream/plan.md`는 「내가 **직접** 받아 온 폴더인가」라고
썼습니다. 이번 골격은 사용자가 미리 받아 둔 것이라 "내가 직접"이 아닙니다.
문자 그대로 읽으면 남이 받아 둔 임시 클론은 영영 못 지웁니다.

에이전트는 `APPLY.md` 쪽을 따르고 그 판단 근거를 보고했습니다. 누가 받았는지가
아니라 이번 적용을 위한 것인지로 가르도록 고쳤고, 판단이 서지 않으면 묻게
했습니다.

**이 워크스트림이 스스로 만든 불일치를 재시험이 잡았습니다.** 고치기만 하고
다시 돌려 보지 않았다면 그대로 나갔을 것입니다.

### 2. 8번이 지우는 도구를 9번이 다시 요구합니다

`plan.md` 8번은 임시 골격을 지웁니다. 9번이 가리키는 일반 흐름의 「완료로 마칠
때」 9번은 이력과 아카이브를 바꾼 뒤 `cairn check`를 다시 돌리라고 합니다. 그때
검사기는 이미 지워졌습니다.

에이전트는 마지막 검사를 삭제 직전으로 당겨서 돌리고 그 사실을 보고했습니다.
지우기 전에 끝내거나 `npx`로 받아서 돌리게 하고, 무엇을 했는지 적게 했습니다.

### 3. 한 줄짜리 완료 메모를 아카이브 워크스트림으로 만들라고 읽혔습니다

`plan.md` 2단계 표는 「이미 끝난 작업의 원문 기록 → 아카이브 폴더」라고 합니다.
그런데 `workstreams.md`는 독립된 관리 단위가 필요 없는 일은 워크스트림으로
만들지 말라고 합니다. "응답 스키마 검증을 붙였다" 한 줄에는 배경도 완료 조건도
없어서, 폴더를 만들면 지어내야 합니다.

에이전트는 `workstreams.md` 쪽을 따르고 이유를 남겼습니다. 표에 단서를 달고,
무엇을 워크스트림으로 볼지의 원본이 어디인지 가리켰습니다.

### 4. 이관으로 생긴 워크스트림마다 작업 위치를 다시 물어야 했습니다

`workstreams.md`는 작업 위치를 한 번에 하나씩 묻고 사용자가 답한 것으로
간주하지 말라고 합니다. 적용 중에 생기는 워크스트림마다 그러면 세팅이
끝나지 않습니다.

적용을 시작할 때 정한 결정을 그대로 쓰고, 실제로 그 작업을 시작할 때 다른
곳에서 해야 하면 그때 묻도록 했습니다.

## 절대 경로 재검증 — 통과

검토에서 「나중에 지워도 이력에 남는다」는 지적을 받고 처음부터 적지 않도록
고친 뒤, 세 번째 임시 프로젝트 `quaylog`로 다시 돌렸습니다. 조건을 바꿨습니다.

- 골격을 **저장소 밖**에 두었습니다.
- 사용자 메시지에 **절대 경로를 그대로** 주었습니다. 실제 사용자가 그러듯이요.
- "곧 GitHub에 공개할 거야"를 덧붙였습니다.
- 적용부터 아카이브까지 **끝까지** 밟게 했습니다.

### 판정 근거는 Git 이력입니다

에이전트의 보고가 아니라 픽스처 저장소의 이력을 직접 뒤졌습니다.

```text
git log -p --all | grep -c '<계정명>'                    → 0
git log -p --all | grep -cE 'AppData|scratchpad|C:[/\\]' → 0
```

부트스트랩 커밋 시점의 `status.md`를 꺼내 보니 그때부터 상대 경로였습니다.

```text
- 실제 경로: ../cairn-skel/          ← 당시 골격의 항목 이름. 지금은 「상대 경로」
- 형태: 외부 임시 클론
- 정리 대상: 예
```

**절대 경로를 받고도 상대 경로로 적었습니다.** 문서의 지시를 따른 것이고,
공개해도 사용자 이름이 새지 않습니다. 완료 조건이 실제로 충족됐습니다.

피했다고 보고했습니다. 종료 검사가 제 시점에 돌아간 것이 확인됩니다.

## 이번에 새로 나온 모순 둘 — 둘 다 이 작업이 만든 것

### 1. 저장소 밖 골격은 삭제가 커밋에 들어갈 수 없습니다

앞 커밋에서 「골격을 지운 것도 그 커밋에 함께 들어갑니다」라고 썼습니다. 저장소
안에 받은 클론은 `.gitignore` 정리가 커밋에 들어가지만, 저장소 밖이면 추적되는
것이 없어 들어갈 것이 없습니다. 에이전트는 삭제 사실을 커밋 메시지에 적는
것으로 대신했습니다. 그 방법을 문서에 넣었습니다.

### 2. 검사 시점과 삭제 시점이 어긋납니다

골격을 남겨 두는 갈래에서는 검사할 때 골격이 아직 있습니다. 그때 `status.md`에
「지웠다」고 적으면 사실과 다릅니다. 에이전트는 예정으로 적고 지운 뒤에 고쳐
별도 커밋으로 남겼습니다. `workstreams.md`가 그 파일이 그대로 아카이브에
남는다고 했으니 마지막 값이 사실이어야 한다는 판단이었고, 맞습니다. 그
처리를 문서에 넣었습니다.

## 옛 문장이 새 원칙과 충돌해 함께 고친 것

절대 경로를 적지 않기로 정한 뒤에도 「실제 경로를 적는다」는 전제로 쓰인 문장이
**네 문서의 여섯 곳**에 남아 있었습니다. 한쪽만 고치면 갈라진다는 것을 이 대작업에서 세 번
확인했으므로, 표현을 검색해 함께 맞췄습니다.

| 자리 | 무엇이 어긋났나 |
| --- | --- |
| `APPLY.md` 4번 3항 | 「실제 경로를 각각 적습니다」 |
| `APPLY.md` 3번 승인 목록 | 「골격 위치의 실제 경로와 형태」 |
| `APPLY.md` 「골격 위치」 | 「실제 값으로 적습니다」 |
| `setup-workstream/README.md` | 조사 결과에 「실제 경로와 형태」 |
| `setup-workstream/plan.md` | 경로가 항상 적혀 있다고 가정 |
| `setup-workstream/status.md` | 절대 경로를 금지한 직후 다시 「실제 경로」 |

항목 이름도 「실제 경로」에서 「상대 경로」로 바꿨습니다. 이름이 무엇을 적는
자리인지 스스로 말하게 하려는 것입니다.

`plan.md`에는 경로 자리가 비어 있을 때 무엇을 해야 하는지도 넣었습니다 —
사용자에게 한 번 묻고 그 세션 안에서만 쓰고, 묻지 못하면 골격이 필요한 단계를
진행하지 않고 알립니다.

## `.gitignore` 빈 파일 규칙

앞선 시험에서 에이전트가 절차에 없는 판단을 했습니다. `.gitignore`가 이번
적용으로 생겼고 넣은 것이 임시 골격 한 줄뿐이라, 그 줄만 지우면 빈 파일이
남습니다. 적용 전에 없던 파일을 남기지 않는 쪽을 골랐고 그 판단은 맞아
보입니다. 절차에 그 경우를 넣었습니다.

**`.gitignore` 자체가 이번 적용으로 생긴 파일이고 그 줄이 전부였다면 파일째
지웁니다.** 원래 있던 파일이면 줄만 빼고 파일은 남깁니다.

## 중단 뒤 이어서 확인한 두 갈래

두 시험 모두 별도 에이전트가 부트스트랩까지 진행한 뒤 세션 한도로 멈췄습니다.
남은 픽스처를 파일과 Git 이력으로 확인했습니다. **두 갈래의 근거 수준이 서로
다릅니다** — 아래에 각각 밝힙니다.

### 개인정보가 보이는 상대 경로 — 통과

프로젝트를 `work/app`, 골격을 `Users/jdoe/cairn-skel`에 두어 상대 경로가
`../../Users/jdoe/cairn-skel`이 되는 조건이었습니다. 별도 에이전트가 만든
부트스트랩 커밋의 `status.md`에는 경로 대신 다음 값이 들어갔습니다.

```text
- 상대 경로: 적지 않습니다. 상대 경로에 계정 이름이 드러나는 자리입니다
```

현재 세션에서 픽스처 저장소의 전체 Git 이력을 다시 검색했습니다. `jdoe`와
골격의 절대 경로는 Git 이력에 없었습니다. 새 규칙이 의도한 대로 개인정보가
보이는 상대 경로를 기록하지 않은 것이 확인됐습니다.

### 새로 만든 한 줄짜리 `.gitignore` — 부분 통과

두 번째 픽스처는 저장소 안의 `.cairn/`을 임시 골격으로 썼고, 적용 전에는
`.gitignore`가 없었습니다. 부트스트랩 커밋에서 `.gitignore`가 `.cairn/` 한
줄로 새로 생겼습니다.

규칙이 말하는 동작은 그대로 일어났습니다. Git 이력으로 확인했습니다.

```text
e6d0034  add cairn skeleton and bootstrap ...   .gitignore | 1 +
96993b0  test cleanup of generated gitignore    .gitignore | 1 -
```

빈 파일이 남지 않고 파일째 사라졌습니다. 지금 `.gitignore`도 `.cairn/`도
없습니다.

**다만 적용 절차를 따라간 에이전트가 그 자리에서 판단한 결과가 아닙니다.**
그 에이전트는 부트스트랩 직후에 멈췄고, 정리 단계까지 가지 못했습니다.
