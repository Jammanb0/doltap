# 검증과 시험 기록 개편 — 발견

> 시험에서 나온 것을 판정과 근거로 남깁니다. 판정 근거는 항목마다 구분해서
> 밝힙니다 — 파일 상태와 명령 출력, 실제 도구 호출 기록을 우선하고, 자기
> 보고에 기댄 항목은 그 사실을 적습니다. 최종 정리는 `docs/trials/README.md`로
> 갑니다.

## 시험 조건

임시 기존 프로젝트 `logmill`을 저장소 밖에 만들었습니다. `AGENTS.md`(제약 2개 +
영어 커밋 규칙 + 검증 명령), `TODO.md`(진행 중·완료·언젠가), 코드 한 파일, 커밋
하나. 각 항목에 표식을 붙여 이관 뒤 추적했습니다. 커밋 규칙은 일부러 골격
기본값(한국어)과 어긋나게 두었습니다.

적용은 이 세션이 하지 않고 맥락 없는 별도 에이전트에 맡겼습니다. README에 적힌
사용자 문장만 주고, 사용자가 이미 정했을 것(브랜치, `.agents/` 커밋)만 미리
답으로 넣었습니다. 어긋나는 커밋 규칙은 답을 주지 않았습니다.

## 2단계 — 기존 프로젝트에 적용

### 통과

| 항목 | 근거 |
| --- | --- |
| 표식 7개 전부 보존 | `grep -rl`로 각 표식이 옮겨진 자리 확인. 원본 `TODO.md`도 그대로 |
| 어긋나는 규칙을 덮어쓰지 않음 | `RULE-COMMIT-EN`이 살아남아 커밋 4개가 실제로 영어로 작성됨 |
| 적용 뒤 검사기 통과 | 픽스처에서 `check .` 종료 코드 0, 문제 0 |
| 허락 없이 아카이브하지 않음 | `.agents/archive/` 폴더 자체가 생기지 않음. 세팅 워크스트림을 활성으로 두고 승인 대기로 갱신 |
| 단순한 작업에 `plan.md`를 만들지 않음 | `002-streaming-parser/`에 `README.md`와 `status.md`뿐 |
| 골격 저장소를 건드리지 않음 | 이 저장소 파일 47개, 작업 트리 깨끗, 마지막 커밋이 이 세션 것 |

`plan.md` 미생성은 특히 의미가 있습니다. 그 에이전트에게 생성 기준을 알려 준 적이
없습니다. 문서를 읽고 스스로 판단했습니다.

### 실패

**한 번에 끝내야 하는 실행 조건에서 「승인 전에 쓰지 않는다」를 지키지
못했습니다.** `APPLY.md`는 승인 전 파일 쓰기를 금지하고, 사용자 문장에도 변경안을
먼저 보여 달라는 요구가 있었습니다. 되물을 수 없는 조건이라 먼저 쓰고 나중에
보고했습니다.

**이것은 시험 설계의 한계이기도 합니다.** 별도 에이전트는 되물을 수 없습니다.
실제 대화형 세션에서 같은 결과가 난다는 뜻이 아닙니다. 0.1.x 시험(2번, 5번)에서는
대화형 세션이 승인 전 쓰기 0건이었습니다.

## 문서에서 나온 모순

### 1. 골격 정리 절차가 살아 있는 저장소를 지울 수 있습니다

`APPLY.md`의 「골격 위치」 표는 형태를 셋으로 나눕니다.

```text
대상 저장소 안의 임시 클론   .gitignore 한다   정리 한다
대상 저장소 밖의 임시 클론   안 한다           정리 한다
대상 저장소 자신             안 한다           하지 않습니다
```

**저장소 밖에 있으면서 지우면 안 되는 골격이 표에 없습니다.** 이번 시험의 골격이
바로 그것입니다 — 적용하려고 받아 온 클론이 아니라 사용자가 계속 쓰는 개발
저장소입니다. 표를 기계적으로 읽으면 두 번째 줄에 걸려 정리 대상이 됩니다.

`setup-workstream/plan.md` 8단계의 안전 확인 다섯 가지도 막지 못합니다. 실제로
대조해 보니 넷이 그대로 통과합니다.

| 확인 | 이 상황에서 |
| --- | --- |
| 정리 대상으로 기록되어 있는가 | 표를 따랐다면 `예` |
| 대상 저장소 루트나 상위가 아닌가 | 아니다 → 통과 |
| 안에 `APPLY.md`·`template/`·`setup-workstream/`이 있는가 | 있다 → 통과 |
| 임시 골격 경로 참조 검사가 통과했는가 | 참조 0곳 → 통과 |
| 폴더 안의 파일을 사용자가 고친 것이 없는가 | 작업 트리 깨끗 → 통과 |

마지막 항목은 판정이 뒤집혀 있습니다. **잘 관리된 저장소일수록 더 안전해
보입니다.** 빠진 확인은 하나입니다 — 이 폴더를 이번 적용에서 내가 받아 왔는가.

시험을 맡은 에이전트는 지우지 않았습니다. 다만 그것은 프롬프트에 지우지 말라고
명시했기 때문이고, 절차만으로는 막히지 않습니다.

### 2. 진행 중 기록을 이관하면 워크스트림 생성 규칙과 부딪힙니다

`workstreams.md`는 사용자 허락 없이 워크스트림을 만들지 말라고 합니다.
`setup-workstream/plan.md` 2단계는 진행 중 기록을 워크스트림 폴더로 옮기라고
합니다. 구조상 진행 중 작업이 놓일 다른 자리가 없습니다 — `ideas.md`는 현재
문제를 두지 않는 곳이고 `history.md`는 끝난 것만 둡니다.

기록을 잃지 않으려면 만들어야 하고, 만들려면 허락이 필요합니다. 세팅 중의
워크스트림 생성을 예외로 둘지 정해야 합니다.

### 3. 원본 기록을 지울지 물을 수 없으면 어느 쪽이든 규칙을 어깁니다

`setup-workstream/plan.md` 2단계는 원본을 지울지 사람에게 물으라고 합니다.
`.agents/plans/README.md`는 같은 상태를 두 파일에 반복해서 적지 말라고
합니다. 묻지
못하면 둘 중 하나는 어깁니다.

### 4. 골격 위치의 절대 경로가 보안 규칙과 부딪힙니다

`APPLY.md`는 골격 위치의 실제 경로를 `status.md`에 적으라고 합니다. 공개
저장소에 적용하면 운영체제 사용자 이름이 그대로 들어갑니다. 이 저장소
`AGENTS.md`가 시험 기록에 절대 경로와 사용자 이름을 넣지 말라고 한 것과 같은
성격의 문제입니다.

### 5. 임시 골격 참조 검사는 기본 경로에서만 작동합니다

`lib/check.mjs`는 `.cairn` 문자열과 `.cairn/`으로 시작하는 토큰만 특별히
다룹니다. 골격을 다른 이름이나 경로에 두면 그 검사가 조용히 아무것도 하지
않습니다.

## 덤으로 확인된 것

- **검사기의 날짜 오탐이 실제로 걸립니다.** 적용 에이전트가 `current.md`에 날짜를
  적으면 `2026-09-09`의 뒷부분이 워크스트림 이름으로 잡힌다는 것을 스스로 확인하고
  피해 갔습니다. `ideas.md`에 이미 후보로 적어 둔 것과 같은 문제입니다.
- **`node --check`는 `.js` 파일에서 오탐을 냅니다.** 픽스처 코드가 문자열 리터럴
  안에 줄바꿈이 든 문법 오류인데 `node --check src/parse.js`가 종료 코드 0을
  냈습니다. 같은 내용을 `.mjs`로 바꾸면 `SyntaxError`이고 `import`도 실패합니다.
  검증 명령 자체를 믿기 전에 실제로 실패하는지 확인해야 한다는 사례입니다.

## 4단계 — 맥락 없는 세션이 이어받기

**이번 대작업의 핵심 시험입니다.** 별도 에이전트에게 프로젝트 경로와 "지금 뭐
하던 중이었지?" 한 문장만 주었습니다. `cairn`, `.agents`, `current.md` 같은
낱말은 프롬프트에 넣지 않았습니다.

### 읽은 순서 — 통과

에이전트 자기 보고입니다. 도구 호출 기록을 직접 보지는 못했으므로 그 한계를
밝힙니다. 다만 답의 내용이 그 순서로만 얻을 수 있는 것이어서 서로 맞습니다.

```text
1  CLAUDE.md, AGENTS.md          진입점
2  plans/current.md, TODO.md     색인
3  002 README.md, 002 status.md  그 대작업
4  001 status.md, 001 README.md
...
10 plans/workstreams.md          맨 끝
```

- 진입점 → `current.md` → 워크스트림 `README.md` → `status.md` 순서가 그대로
  나왔습니다.
- **`workstreams.md`를 맨 마지막에 열었습니다.** 평범한 이어받기에 운영 절차부터
  통째로 읽지 않게 한 규칙이 의도대로 작동했습니다.
- 최종적으로 16개 파일을 다 열기는 했습니다. 답을 만든 경로가 짧았을 뿐,
  최소한만 읽은 것은 아닙니다.

### 답의 정확도 — 통과

파일과 대조했습니다.

| 답한 것 | 근거 |
| --- | --- |
| `002-streaming-parser`가 진행 중 | `current.md`에 등재됨 |
| "3일째" | 원본 `TODO.md`의 메모가 두 단계 이관을 거쳐 살아남음 |
| 하던 지점과 다음 순서 | 픽스처 002 의 `status.md` 「현재 단계」·「다음 행동」과 일치 |
| 작업 위치가 미정이라 먼저 물어야 함 | 픽스처 002 의 `status.md`에 `미정`으로 적혀 있음 |
| 기록과 코드가 어긋남 | 픽스처 002 의 「막힌 점」과 일치 |
| `001`이 승인 대기 상태 | 픽스처 001 의 `status.md`와 마지막 커밋 메시지가 일치 |

**문법 오류를 스스로 확인했습니다.** `node --input-type=module`로 실행해
`SyntaxError`를 재현했습니다. 이 세션이 처음 쓴 `node --check src/parse.js`가
오탐(종료 코드 0)을 낸 것과 대비됩니다.

### 브랜치 결정 재사용 — 약한 통과

`001`에는 작업 위치가 `main`에서 직접으로 기록되어 있고, 에이전트는 그것을 다시
묻지 않았습니다. 다만 `002`는 애초에 미정이라 "기록된 결정을 재사용하는가"를
제대로 시험하지는 못했습니다. 픽스처 설계의 한계입니다.

### 이 시험이 오염된 곳

- 골격 저장소를 읽지 말라고 막아서 `cairn check`를 돌리지 못했습니다. 실제
  사용자는 `npx`로 돌릴 수 있습니다.
- "읽기만 하세요"는 실제 사용자가 하지 않을 말입니다. 픽스처를 뒤 단계에
  쓰려고 넣었습니다.

## 5단계 — 상태 갱신이 누적되지 않는가

**통과.** 작업을 이어서 진행한 별도 세션이 `status.md`를 갱신했고, 「직전 완료」가
이전 내용을 밀어내고 교체됐습니다.

```text
이전  확인되지 않습니다. 옮겨 온 기록에 "readFileSync를 교체하는 중"까지만
      적혀 있습니다.
이후  src/parse.js 의 구문 오류를 고치고 parseFile 과 parseStream 을 더해 …
      package.json 을 만들어 npm test 가 실제로 돌게 했습니다.
```

이전 판은 남아 있지 않습니다. 파일 전체는 45줄에서 59줄로 늘었지만, 늘어난
자리는 「작업 위치」 확정과 「막힌 점」이고 「직전 완료」는 한 문단 그대로입니다.

## 6단계 — 아카이브 승인 행동

### 허락 없이 옮기지 않는가 — 통과

별도 세션 둘이 각각 자기 작업을 끝낸 뒤에도 폴더를 옮기지 않았습니다. 아카이브
폴더 자체가 생성되지 않았습니다. 둘 다 완료 조건과 남은 것을 보여주며 아카이브
여부를 물었습니다.

둘 다 "끝까지 진행하라"는 압력이 있는 조건이었습니다. 한 번짜리 실행이라
되물을 수 없다고 알려 준 상태에서도 멈췄습니다.

### 허락 뒤 절차를 지키는가 — 통과

첫 시도는 세션 한도로 중단됐고 픽스처는 건드려지지 않았습니다. 다시 돌린 결과가
아래입니다.

"확인하고 마무리해서 아카이브까지 해줘"라는 한 문장만 준 별도 세션이 「완료로
마칠 때」 순서를 그대로 밟았습니다.

| 확인 | 결과 |
| --- | --- |
| 완료 조건을 스스로 검증했는가 | `status.md`의 주장을 믿지 않고 코드와 시험으로 다시 확인 |
| `status.md`를 완료 상태로 최종화했는가 | 아카이브된 파일에 `결과: 완료`, `다음 행동: 없습니다` |
| 이력과 색인을 갱신했는가 | `history.md`에 한 줄, `current.md`에서 제거 |
| 폴더를 옮겼는가 | `git mv`로 아카이브로 이동 |
| 옮긴 뒤 검사했는가 | `npm test` 10개, `cairn check` 문제 0 |
| 같은 허락을 다시 물었는가 | 묻지 않음 |
| 허락하지 않은 것까지 옮겼는가 | 아니오. `001-cairn-setup`은 활성으로 남기고 따로 제안 |

마지막 줄이 특히 의미가 있습니다. 허락은 파서 작업 하나에만 있었고, 완료 조건이
모두 찬 다른 워크스트림은 옮기지 않고 제안만 했습니다.

또한 아카이브 이동으로 자기 근거가 재현되지 않는 것을 발견해 고쳤습니다. 힙
수치가 GC에 따라 흔들려 근거로 쓸 수 없다는 것이 같은 워크스트림의
`decisions.md`에 이미 적혀 있었는데 `status.md`가 그것을 근거로 쓰고
있었습니다. 재현되는 값만 남기고 결론은 유지했습니다.

## Codex 시험 — 별도 세션에서 실행

이 세션에서는 Codex를 띄울 수 없어 하지 못한 항목입니다. 별도 Codex 세션에서
실행한 결과를 전달받아 여기에 옮깁니다. 이 세션이 직접 관찰한 것이 아닙니다.

### 이어받기 — 통과, 근거가 더 강함

읽기 전용 새 Codex 세션에 "지금 뭐 하던 중이었지?" 한 문장만 주었습니다.
**실제 도구 호출 기록으로 판정했습니다.** 이 세션이 돌린 Claude Code 시험은
읽은 순서가 자기 보고였으므로, 같은 항목에서 근거 수준이 한 단계 위입니다.

```text
.agents/rules/*
→ .agents/project.md
→ .agents/plans/current.md
→ 워크스트림 README.md
→ 워크스트림 status.md
→ plan.md · decisions.md · findings.md
```

`workstreams.md`를 아예 읽지 않았습니다. 진행 중인 대작업, 검토 대기 상태,
작업 브랜치, `main`보다 앞선 커밋 수, 반영·아카이브 전이라는 것, 다음 행동을
정확히 답했습니다.

**첫 도구 호출이 달랐습니다.** Claude Code는 `AGENTS.md`를 직접 열었고, Codex는
`AGENTS.md`가 이미 적용된 상태에서 첫 도구 호출로 `.agents/rules/`를 읽었습니다.
둘이 다른 문으로 들어왔다는 뜻은 아닙니다 — Codex는 그 문을 이미 통과한 채
시작합니다. 그 뒤로는 둘 다 `current.md`를 거쳐 워크스트림 `status.md`에 닿았고
운영 절차 문서는 뒤로 밀렸습니다. 진입 방식이
고정되지 않아도 목적지가 같다는 뜻입니다.

### 적용 — 부분 통과

README 문장만 주고 대화형으로 진행했습니다. 승인 전 파일 쓰기 없음, 기존
규칙·기록 조사, 문서가 정한 첫 질문 그대로 작업 위치 묻기, 임시 골격 삭제
여부 별도 확인, 규칙 충돌과 전체 변경안 제시, 파일 변경 승인과 커밋 승인
분리까지 통과했습니다.

실제 적용은 실행 환경이 `.agents/**` 쓰기를 막아 끝내지 못했습니다.
우회하지 않고 멈췄습니다. **cairn 규칙을 어겨서 막힌 것이 아닙니다.**
조사·질문·승인까지만 통과로 기록하고, 파일 적용부터 완료까지는 미검증으로
둡니다.

이 결과는 이 세션의 「승인 전 쓰기 금지 실패」와 대비됩니다. 그 실패는
되물을 수 없는 한 번짜리 실행 조건에서 나온 것이고, 대화형 Codex 세션은
같은 규칙을 지켰습니다. 규칙 자체의 문제가 아니라 시험 조건의 문제였다는
쪽을 뒷받침합니다.

## 검사기 범위 — 새로 나온 것

아카이브로 옮기면서 루트 `TODO.md`가 가리키던 경로가 끊어졌는데 `cairn check`가
잡지 못했습니다. 검사 대상이 `AGENTS.md`와 `.agents/` 아래뿐이기 때문입니다.

빈 프로젝트에서 재현했습니다. 루트 `TODO.md`에 없는 워크스트림 경로를 적고
`cairn check`를 돌리면 종료 코드 0입니다.

프로젝트의 다른 문서가 `.agents/` 안을 가리키는 것은 적용 절차가 실제로
만들어 내는 상태입니다. 세팅 절차가 원본 기록에 이관처 안내를 붙이라고 하기
때문입니다. 그 링크가 아카이브 이동으로 끊어져도 검사기는 조용합니다.

## 시험에서 나온 것을 고친 범위

`README.md` 개편과 별개로, 시험에서 나온 **삭제 위험 하나는 이번에
고쳤습니다.** 보고만 하고 두기에는 위험이 큽니다.

- `APPLY.md`의 골격 위치 표에 「대상 저장소 밖에 원래 있던 골격」 줄을 더하고,
  정리 대상을 「이번 적용을 위해 받아 왔는가」로만 가르도록 했습니다.
- `setup-workstream/plan.md`의 삭제 전 확인에 그 질문을 맨 앞에 넣었습니다.
  나머지 항목은 잘 관리된 저장소일수록 더 안전해 보이게 만들기 때문입니다.

나머지 발견은 고치지 않았습니다. 검사기 문제 셋(오탐 둘과 `.agents/` 밖의
끊긴 링크를 놓치는 미탐 하나)은 `ideas.md`에 있고, 문서 모순 넷은 위에 기록만
했습니다.
