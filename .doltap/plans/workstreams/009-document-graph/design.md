## 앵커

### 실제로 확인한 것

GitHub의 마크다운 렌더링 API에 이 형식을 그대로 넣어 확인했습니다(2026-09-11).

```text
넣은 것   <a name="doltap-s-3q8m5k-start"></a>
나온 것   <p><a name="user-content-doltap-s-3q8m5k-start"></a></p>
```

| 확인한 것 | 결과 |
| --- | --- |
| `<a name>` | 살아남되 이름 앞에 `user-content-`가 붙음 |
| `<a id>` | 같음 |
| `<span id>` | 같음 |
| HTML 주석 | **통째로 사라짐** |
| `[글](파일#조각)`의 조각 | 접두사가 붙지 않고 원문 그대로 |

두 가지가 결정됩니다.

- **주석을 범위 표식으로 쓸 수 없습니다.** 렌더링 결과에 남지 않으므로 사람이
  누를 목적지가 되지 못합니다. 설계 기록이 빈 앵커를 고른 판단이 확인됐습니다.
- **GitHub에서는 앵커 이름과 링크 조각이 어긋납니다.** 앵커는
  `user-content-doltap-...`이 되는데 링크는 `#doltap-...`으로 남습니다.

### 어긋남을 GitHub가 메워 준다

앵커는 `user-content-`가 붙는데 링크 조각은 그대로이니, 조각이 목적지를 찾으려면
GitHub가 사이를 이어 줘야 합니다. **이어 줍니다.** 근거가 둘입니다.

GitHub가 저장소 화면에 싣는 `behaviors-*.js`에 그 코드가 있습니다.

```js
let e = getHash(location.hash),
    t = e.startsWith("user-content-") ? e : `user-content-${e}`,
    r = find(document, t) ?? ...
```

조각을 읽어 `user-content-`가 없으면 붙인 뒤 그 요소를 찾습니다. 이 스크립트를
실제로 내려받아 확인했습니다.

그리고 다른 세션이 실제 브라우저에서 `kotartemiy/pygooglenews`의 목차 링크를
눌러 대상 절로 이동하는 것을 확인했다고 보고했습니다(스크롤 2136px, 대상이 화면
위쪽 58px). **이 관찰은 이 세션에서 재현하지 못했습니다** — 여기 쓴 브라우저는
앵커와 조각이 일치하는 대조용 파일에서도 스크롤하지 않아, 조각 이동 자체를
판정할 수 없는 환경입니다.

그래서 링크는 `#doltap-...`으로 씁니다. `#user-content-...`로 쓰지 않습니다 —
그렇게 쓰면 GitHub 밖에서는 목적지를 찾지 못합니다.

## ID

```text
doltap-<종류>-<식별자>
종류      d | s | b
식별자    Crockford Base32 소문자 8자
문자 집합 0123456789abcdefghjkmnpqrstvwxyz
```

`i` `l` `o` `u`를 뺍니다. `1`·`l`, `0`·`o`와 헷갈리지 않고, 뜻하지 않은 낱말이
만들어지는 것도 줄입니다.

8자는 40비트입니다. 노드가 1만 개일 때 어딘가 겹칠 확률이 대략 0.005%입니다.
발급할 때마다 레지스트리와 대조하므로 겹치면 조용히 지나가지 않고 다시
뽑습니다. 길이는 충돌 확률보다 **사람이 오류 메시지에서 읽고 옮겨 적을 수 있는가**로
정했습니다.

값은 `crypto.randomBytes(5)`에서 만듭니다. 직접 만든 의사 난수를 쓰지 않습니다.

「검토 상태 없음」은 내용이 바뀌어도 재검토 대상으로 올리지 않는다는 뜻입니다.
찾아가는 길이거나 이력이라 한쪽이 바뀌었다고 다시 볼 이유가 없습니다.

`imports`는 2단계에서 추가하고 설계 기록에도 반영한 관계입니다. 출발 파일이
도착 파일을 **읽어 들여 자기 내용으로 삼는다**는 뜻이고, 두 파일의 글이 같아야
한다는 뜻이 아닙니다. `CLAUDE.md`가 `AGENTS.md`를 가리키는 자리에 씁니다. 내용
비교를 하지 않으므로 한 줄짜리 파일이 긴 파일을 가리켜도 성립합니다.

### `mirror-of`와 `update-with`를 가르는 기준

둘 다 대칭이지만 **판정 방식이 다릅니다.**

```text
mirror-of    양쪽 contentHash 가 같아야 한다 → 다르면 문제(PROBLEM)
update-with  한쪽이 바뀌면 검토 기록이 만료된다 → 재검토 필요(확인)
```

`mirror-of`는 사람의 판단이 끼어들 자리가 없습니다. 같아야 하는데 다르면 틀린
것이고, 검토 기록으로 넘어갈 수 없습니다. `update-with`는 한쪽이 바뀌었을 때
다른 쪽을 **봐야 한다**는 뜻이지 같아야 한다는 뜻이 아니라서, 사람이 보고
「반영함」이나 「영향 없음」을 남기면 해소됩니다.

## 정규화

가장 어려운 항목입니다. 잘못 정하면 서식만 바꿔도 재검토가 쏟아지거나 중요한
변경을 놓칩니다.

### `contentHash`

범위 안의 내용을 아래 순서로 정규화한 뒤 SHA-256을 계산합니다.

1. 줄바꿈을 `LF`로 맞춘다.
2. **강제 줄바꿈을 먼저 표시한다.** 줄 끝에 공백이 둘 이상이거나 역슬래시로
   끝나면 마크다운의 강제 줄바꿈이다. 줄 경계로 표시해 두고 그다음에 줄 끝
   공백을 없앤다. 순서를 뒤집으면 뜻이 있는 줄바꿈이 사라진다.
3. **그대로 두는 구역을 먼저 가른다.** 코드 울타리 안과 네 칸 이상 들여쓴 코드
   블록이다. 아래 6~8번을 적용하지 않는다.
4. **doltap 앵커 줄을 없앤다.** 자기 범위의 시작·끝과 안에 든 자식 범위의
   앵커가 모두 해당한다.
5. **관계 선언 줄을 없앤다.** 이 줄은 `graphHash`가 맡는다.
6. **줄을 잇되 구조를 여는 줄은 잇지 않는다.** 아래 중 하나로 시작하는 줄은
   앞 줄에 붙이지 않고 자기 줄로 남긴다.

   ```text
   #        제목
   - * +    목록 항목
   1.       번호 목록 항목
   |        표의 행
   >        인용
   --- ***  구분선
   ```

   2번에서 강제 줄바꿈으로 표시한 줄 다음도 잇지 않는다. 그 밖의 줄만 앞 줄에
   공백 하나로 잇고, 줄 안의 연속 공백도 하나로 줄인다.
7. 빈 줄이 여러 개 이어지면 하나로 줄이고, 범위의 맨 앞뒤 빈 줄은 없앤다.
8. 일반 마크다운 링크는 표시 이름과 **해결된 대상의 정체**를 남긴다.
   - 관리 대상 문서나 범위로 해결되면 경로 대신 대상 ID와 조각을 남긴다.
   - 관리 대상이 아닌 저장소 안 파일이면 저장소 루트 기준 경로와 조각을 남긴다.
   - 외부 URL이면 전체 URL을 남긴다.

6번이 핵심입니다. 이 저장소는 80칸에서 줄을 바꿉니다. 문장을 한 자 고쳐 아래
줄들이 밀리면 뜻은 그대로인데 여러 줄이 바뀝니다. 줄을 이어서 해시하면 **다시
줄바꿈한 것만으로는 재검토가 일어나지 않습니다.**

**구조를 여는 줄을 가려내지 않으면 목록이 뭉개집니다.** 항목 둘짜리 목록과 그
둘을 한 줄에 쓴 것이 같은 문자열이 되어, 구조가 달라졌는데 해시가 그대로
남습니다. 제목이 본문에 붙는 것도 같은 문제입니다.

8번은 관리 대상이 폴더를 옮겨도 같은 ID라면 재검토가 일어나지 않게 하면서,
동명이 다른 파일로 바뀐 것은 잡기 위한 규칙입니다. 마지막 파일명만 남기면
`docs/a/`와 `docs/b/`에 각각 있는 `README.md`를 구분하지 못합니다. 안정적인 ID가
없는 파일은 이동과 대상 변경을 기계적으로 가를 수 없으므로 전체 저장소 기준
경로를 남기고, 경로가 바뀌면 재검토합니다.

### 무엇이 잡히고 무엇이 안 잡히는가

3단계에서 시험으로 고정할 쌍입니다.

| 바꾼 것 | 해시가 바뀌어야 하나 |
| --- | --- |
| 문단을 다시 줄바꿈함 | 아니오 |
| 줄 끝 공백을 지움(강제 줄바꿈이 아닌 것) | 아니오 |
| 빈 줄을 하나 더 넣음 | 아니오 |
| CRLF를 LF로 바꿈 | 아니오 |
| ID가 있는 링크 대상이 폴더만 옮겨짐 | 아니오 |
| ID가 없는 링크 대상의 경로가 바뀜 | **예** |
| 관계 선언을 더하거나 지움 | 아니오 — `graphHash`가 바뀜 |
| 자식 범위에 앵커를 새로 넣음 | 아니오 |
| 낱말 하나를 고침 | **예** |
| 문장을 지움 | **예** |
| 목록 항목 순서를 바꿈 | **예** |
| **목록 항목 둘을 한 줄로 합침** | **예** |
| **제목을 본문 문단에 붙임** | **예** |
| **강제 줄바꿈을 없앰** | **예** |
| 코드 울타리 안의 공백을 고침 | **예** |
| **네 칸 들여쓴 코드의 공백을 고침** | **예** |
| **링크가 다른 파일을 가리키게 됨** | **예** |
| **동명이 다른 파일을 가리키게 됨** | **예** |
| 링크 표시 이름을 고침 | **예** |

굵게 표시한 항목은 첫 초안이 놓쳤던 것입니다. 줄을 무조건 이으면 목록과
제목이 본문에 뭉개지고, 줄 끝 공백을 먼저 지우면 강제 줄바꿈이 사라지며,
목적지를 통째로 버리면 링크가 다른 문서로 바뀐 것을 놓칩니다.

### `graphHash`

그 노드가 선언한 나가는 관계만 봅니다.

```text
정렬한 "<관계 유형>:<도착 ID>" 목록을 개행으로 이어 SHA-256
관계가 없으면 빈 문자열의 해시
```

표시 이름과 경로는 넣지 않습니다. 관계의 뜻은 유형과 대상이지 라벨이 아닙니다.

두 해시를 나누는 이유는 **재검토가 관계망을 타고 번지는 것을 막기 위해서**입니다.
상대가 관계 하나를 더했을 때 그 노드의 `graphHash`만 바뀌고 `contentHash`는
그대로이므로, 그 노드를 가리키던 관계들의 검토 기록은 만료되지 않습니다.

### `mirror-of`가 제외하는 것

위 1~8번을 양쪽에 똑같이 적용한 결과를 비교합니다. 그래서 **서로 다른 ID를 가진
두 범위가 같은 글이면 해시가 같습니다.** 앵커(3번)와 관계 선언(4번)이 이미
빠지므로 따로 뺄 것이 없습니다.

## 살아 있는 항목

아카이브 전에 걸러야 할 전제와 열린 질문입니다. 검사기가 자연어의 뜻을 읽지
않으므로 **선언 표식**을 둡니다.

```markdown
<a name="doltap-b-9k4m2npq-start" id="doltap-b-9k4m2npq-start"></a>

- `열린 질문` 이 구조를 쓰는 외부 프로젝트가 있는지 확인되지 않았습니다.
  - `상태` 이월 — 활성 문서가 이 범위를 가리켜야 합니다.

<a name="doltap-b-9k4m2npq-end" id="doltap-b-9k4m2npq-end"></a>
```

표식은 둘입니다.

- `` `열린 질문` `` — 아직 답이 없는 물음
- `` `전제` `` — 확인하지 않고 기대고 있는 것

상태는 넷입니다.

| `상태` | 뜻 | 검사기가 요구하는 것 |
| --- | --- | --- |
| `미해결` | 아직 처리하지 않음 | **이 상태가 남아 있으면 아카이브를 막는다** |
| `해결` | 답이 나왔음 | 없음 |
| `이월` | 아직 살아 있어 활성 영역이 가리켜야 함 | 활성 노드에서 이 노드로 들어오는 관계가 하나 이상 있을 것 |
| `폐기` | 더 이상 유효하지 않음 | 같은 범위에 비어 있지 않은 이유가 있을 것 |

`assumes`는 기본 관계로 남깁니다. `이월`한 항목을 활성 판단이 가리킬 때 쓰는
관계가 바로 이것이고, 관계 없이 상태만 두면 활성 쪽에서 찾아갈 길이 생기지
않습니다.

### 아카이브 전 검사

```text
워크스트림 폴더 안의 모든 노드를 훑는다
  상태가 `미해결` 인 것이 있으면      → 문제. 아카이브를 막는다
  상태가 `이월` 인데 들어오는 관계가 없으면 → 문제
  상태가 `폐기` 인데 이유가 비어 있으면    → 문제
  그 밖                                → 통과
```

아카이브 전 검사를 구현하는 7단계에서 고정할 fixture는 네 가지입니다 — 미해결이
남은 것, 이월인데 연결이 없는 것, 폐기인데 이유가 없는 것, 그리고 **셋 다 제대로
처리해서 걸리지 않아야 하는 것**입니다. 마지막이 없으면 오탐을 잡지 못합니다.

## 관리 범위

```text
기본
├─ AGENTS.md
├─ CLAUDE.md        특수 연결
└─ <운영 폴더>/**/*.md

등록해서 넣는 것
└─ 관계의 근거나 대상으로 실제로 쓰는 외부 마크다운
```

### 외부 문서 등록

운영 폴더 안의 문서가 그 외부 문서를 **ID 조각이 있는 관계로 가리키면** 등록된
것으로 봅니다. 별도의 등록 목록 파일을 두지 않습니다. 목록을 따로 두면 목록과
실제 관계가 어긋나는 자리가 하나 더 생깁니다.

등록된 외부 문서에는 문서 ID를 주고 그래프에 넣되, 그 안의 모든 제목에 범위를
강제하지 않습니다.

### `CLAUDE.md`

`@AGENTS.md` 한 줄을 지켜야 하므로 **앵커를 넣지 않습니다.** 대신 검사기가
이 파일을 구조로 확인하고, 그래프에서는 고정 ID를 가진 연결 노드로 표현합니다.

```text
doltap-d-claude-md ──imports──▶ AGENTS.md 의 문서 노드
```

**`mirror-of`를 쓰지 않습니다.** `mirror-of`는 양쪽 `contentHash`가 같아야
성립하는데 `CLAUDE.md`는 한 줄이고 `AGENTS.md`는 그렇지 않아 언제나 불일치로
잡힙니다. 두 파일은 같은 글이어야 하는 관계가 아니라 한쪽이 다른 쪽을 읽어
들이는 관계이므로 `imports`가 맞습니다.

이 ID만 난수가 아니라 고정값입니다. 파일 안에 발급 기록을 남길 자리가 없기
때문입니다.

### 탐색에서 빼는 것

```text
.git  node_modules  .svn  .hg  dist  build  coverage
점으로 시작하는 폴더 중 운영 폴더가 아닌 것
<운영 폴더>/recovery
심볼릭 링크
```

빼는 목록은 검사기 안에 두고, 프로젝트가 늘릴 수 있게 합니다. 줄이지는 못하게
합니다 — `.git` 안을 문서로 읽을 이유가 없습니다.

## 명령

```text
doltap check [경로] [--json]
doltap map [경로] [--json]
doltap context <ID> [--depth N] [--budget N] [--json]
doltap audit <경로> [--relation 유형] [--changed] [--budget N]
doltap id <파일> --kind d|s|b --at <줄 또는 제목>
doltap link <출발 ID> --to <도착 ID> --as <관계 유형>
doltap move-fix [경로] [--apply]
doltap recover <실행 ID> [--apply|--discard]
doltap review <관계 ID> --as 반영함|영향없음|재검증함 --why "<이유>" --actor 사람|에이전트 [--apply]
doltap migrate [경로] [--apply]
doltap archive-check <워크스트림 경로>
doltap delete <ID> --mode replace|tombstone|purge --why 이유 [--to ID] [--apply]
doltap review <노드 ID> --node --as 최신임|"고쳐야 함" --why 이유 --actor 사람|에이전트 [--apply]
doltap suggest <출발 ID> --to ID --relation 유형 --as 반영|기각|보류 --evidence 근거 --why 이유 --actor 주체 [--apply]
doltap init [경로]
```

`id`와 `link`는 파일을 고치므로 미리보기를 먼저 내고 `--apply` 없이는 쓰지
않습니다. `check` `map` `context` `audit`은 읽기만 합니다.

종료 코드는 지금 규칙을 그대로 씁니다. 문제가 있으면 1, 확인만 있으면 0입니다.

## 발급 레지스트리

운영 폴더에 마크다운 한 장으로 둡니다. 적용된 프로젝트에 사람이 읽을 수 있는
마크다운만 남는다는 조건을 깨지 않기 위해서입니다.

```markdown
| ID | 종류 | 상태 | 경로 | 대체 |
| --- | --- | --- | --- | --- |
| doltap-s-3q8m5k2p | s | 활성 | AGENTS.md | |
| doltap-s-2v7m9q4r | s | 아카이브 | archive/approval.md | |
| doltap-b-8x1c5tgh | b | 삭제 | (없음) | doltap-s-3q8m5k2p |
```

레지스트리에는 삭제 이유 열을 추가합니다. 표식·완전 삭제 모두 마지막 경로와
이유를 유지하며 이후 ID 발급에서도 지우지 않습니다.

상태는 `활성` `아카이브` `삭제` 셋입니다. **삭제한 줄을 지우지 않습니다.** 지우면
같은 ID가 다시 발급됩니다.

ID 발급과 상태 전환은 분리합니다. 기존 ID를 다시 확인하거나 경로를 갱신하는
것만으로 `아카이브`를 `활성`으로 바꾸지 않습니다. 새 아카이브 문서에 ID를 줄
때는 첫 기록부터 `아카이브`로 원자적으로 적고, 기존 범위를 복원할 때는 상태 변경
작업을 명시적으로 실행합니다. 레지스트리에 같은 ID가 둘 이상 있으면 어느 행이
원본인지 추측하지 않고 모든 변경을 멈춥니다.

동시 실행은 같은 폴더에 잠금 파일을 만들어 막고, 쓰기는 임시 파일에 다 쓴 뒤
바꿔치기합니다. 명령이 끝나면 잠금 파일이 남지 않습니다.

## 검토 기록

운영 폴더 아래 **연도별 파일 한 장**씩 둡니다.

```text
<운영 폴더>/reviews/2026.md
```

관계별 파일은 관계가 늘수록 파일이 늘고, 한 장이면 몇 해 뒤 너무 커집니다.
연도별이면 사람이 찾아 읽을 파일 수를 예측하기 쉽습니다. 현재 구현은 상태
계산을 위해 과거 연도도 모두 읽으므로, 연도 분할 자체가 조회 성능 대책은 아닙니다.

한 줄이 한 건입니다. **표가 둘입니다** — 노드 자신을 본 것과 관계를 본 것은
다른 일이고, 만료 조건도 다릅니다.

### 노드 검토

그 노드의 지금 내용과 **자기가 선언한 관계 구성**을 봤다는 기록입니다.

```markdown
## 노드 검토

| 시각 | 노드 ID | contentHash | graphHash | 판단 | 이유 | 주체 |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-09-11 | doltap-s-3q8m5k2p | 3f2a… | 7b04… | 최신임 | 승인 문구를 새로 넣고 관계 둘을 붙임 | 사람 |
```

두 해시 중 **하나라도 바뀌면 만료됩니다.** 관계를 하나 더한 것도 그 노드를
다시 봐야 할 이유이기 때문입니다. 다만 이 만료는 그 노드에서 멈춥니다 — 그
노드를 가리키던 다른 관계의 검토 기록은 `contentHash`가 그대로면 살아 있습니다.

판단은 `최신임`과 `고쳐야 함` 둘입니다. `고쳐야 함`으로 남긴 노드는 감사에서
따로 모입니다.

### 관계 검토

두 노드의 지금 내용이 그 관계에 어떤 영향을 주는지 봤다는 기록입니다.

```markdown
## 관계 검토

| 시각 | 관계 ID | 출발 해시 | 도착 해시 | 판단 | 이유 | 주체 |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-09-11 | doltap-s-aaa:update-with:doltap-s-bbb | 3f2a… | 9c71… | 반영함 | 승인 문구를 양쪽에 맞춤 | 사람 |
```

만료 방향은 관계 유형이 정합니다. 위 「관계 유형」 표의 마지막 칸입니다.

판단은 `반영함` `영향 없음` `재검증함` 셋입니다.

해시는 앞 8자만 적습니다. 표를 짧게 유지하려는 선택입니다. 8자리로 자르면
충돌 가능성이 있으므로 대규모 사용에서도 충분하다고 검증한 값은 아닙니다.
대조할 때는 전체 해시를 다시 계산해서 앞 8자를 견줍니다.

**덮어쓰지 않고 쌓습니다.** 지금 양쪽 해시와 맞는 가장 최근 줄이 유효한
영수증이고, 나머지는 판단 이력입니다. 관계가 사라져도 줄을 지우지 않습니다 —
왜 그렇게 판단했는지가 남아야 합니다.

### `영향 없음`

- 이유가 비어 있으면 받지 않습니다. 공백만 있는 것도 비어 있는 것으로 봅니다.
- 열 글자 미만이면 받지 않습니다. 「없음」 「ok」로 채우는 것을 막습니다.
- 주체는 `사람`과 `에이전트` 둘입니다. **이 표시는 신원 증명이 아닙니다.**
  에이전트가 `사람`이라고 적는 것을 기술적으로 막지 못하므로, 감사할 때 이
  칸을 근거로 쓰지 않습니다.
- 한 번에 여러 관계를 검토 완료로 만드는 기본 명령을 두지 않습니다. 범위를
  명시하고 대상 목록을 먼저 보여준 뒤에만 여러 건을 받습니다.

## 미리보기

문서를 고치는 명령은 모두 같은 형태로 먼저 보여주고 승인을 받습니다.

```text
고칠 파일 3개, 줄 7개

AGENTS.md:42
- [작업 전 승인](.doltap/rules/old.md#doltap-s-3q8m5k2p-start)
+ [작업 전 승인](.doltap/rules/verification.md#doltap-s-3q8m5k2p-start)
```

경로만 바꾸고 표시 이름은 건드리지 않습니다.

### 여러 파일을 고칠 때

**파일 여러 개를 원자적으로 바꿔치기할 방법은 없습니다.** 파일 하나는 임시 파일에
다 쓰고 교체하면 안전하지만, 열 개를 고치다 일곱 번째에서 멈추면 여섯 개만 새
버전이 됩니다. 백업과 일지로 되돌립니다.

```text
<운영 폴더>/recovery/<실행 ID>/
├─ manifest.json
└─ files/<원래 경로를 인코딩한 이름>.bak
```

백업은 원래 확장자를 쓰지 않고 `.bak`으로 저장하며, 복구 폴더 전체를 그래프
탐색에서 제외합니다. `<운영 폴더>/recovery/.gitignore`는 `*`를 담아 백업과
일지가 커밋되지 않게 합니다. 따라서 백업 안의 ID가 원본과 중복되거나 사용자
문서와 함께 공개되지 않습니다.

```text
1  모든 원본 백업과 새 내용을 만든다
2  모든 파일의 경로·원본 해시·새 해시를 `prepared` 상태로 manifest에 기록하고 닫는다
3  파일마다 임시 파일을 디스크에 쓴 뒤 교체한다
4  모두 교체되면 manifest를 `success`로 바꾼다
```

복구는 manifest에 적힌 **모든 파일**을 봅니다. 현재 해시가 원본 해시이면 손대지
않고, 새 해시이면 백업으로 되돌립니다. 둘 다 아니면 사람이 그사이 고친 것이므로
멈추고 충돌을 알립니다. 교체와 `success` 기록 사이 어디서 죽어도 이 판정은
같습니다. 파일별 `완료` 표시에 기대지 않으므로 교체 직후 죽는 구간도 빠지지
않습니다.

잡을 수 있는 오류는 같은 절차로 즉시 되돌립니다. 프로세스가 강제로 끝나면 다음
`check`가 닫히지 않은 manifest를 알리고, `recover`를 제외한 모든 쓰기 명령은
복구 전까지 거부합니다. `recover`는 바꿀 파일을 먼저 보여주고 `--apply`에서
복구합니다. 성공한 실행의 백업도 자동으로 지우지 않으며, 사용자가 결과를 확인한
뒤 `--discard`로 지웁니다. 닫히지 않은 실행에는 `--discard`를 허용하지 않습니다.

`--discard`는 복구 자료를 지우는 작업이므로 실행 ID와 지울 경로를 보여준 뒤
명시적으로 실행합니다. 다른 실행의 복구 자료를 함께 지우지 않습니다.

구형 구조를 만나면 필수 문서가 없다는 일반 오류 대신 무엇이 바뀌었고 어디를
보면 되는지 한 문단으로 알립니다. 구형 구조를 계속 지원하는 것은 아닙니다.

## 적용 범위

기존 프로젝트에 처음 얹을 때 자동으로 주는 것은 **문서 ID까지**입니다.

제목마다 범위를 자동으로 넣지 않습니다. 어디를 하나의 뜻으로 묶을지는 사람이
정할 일이고, 자동으로 넣으면 지우는 일이 더 큽니다.

레거시 아카이브도 같습니다. 문서 ID만 주고 세부 범위는 소급하지 않습니다.

## 커밋하지 않는 프로젝트

운영 폴더를 `.gitignore`에 둔 프로젝트에서는 레지스트리와 검토 기록이 그 작업
공간에만 있습니다. 검사·지도·맥락은 그대로 동작합니다.

`check`가 이 상태를 알아보고 한 번 알립니다 — 기록이 이 컴퓨터에만 있고, 다른
checkout이나 CI에서는 같은 검사를 할 수 없다는 것. 자동으로 백업하지 않습니다.

## 맥락 조회

```text
doltap context doltap-s-3q8m5k2p --depth 2 --budget 4000
```

예산은 **본문 문자 수**로 셉니다. ID·경로·관계와 JSON 형식은 별도 메타데이터라
이 한도에 포함하지 않습니다. 루트도 넘치면 잘라 표시합니다. 모델별 tokenizer를
의존성으로 넣지 않습니다.

예산을 넘으면 자르는 순서가 있습니다.

```text
1  대상 노드의 본문              본문 예산 안에서 낸다
2  들어오고 나가는 관계 목록      끝까지 낸다
3  깊이 1 이웃의 본문            예산이 닿는 만큼
4  깊이 2 이상                   제목과 ID만
```

무엇이 잘렸는지 끝에 한 줄로 적습니다. 조용히 자르지 않습니다.

### `--json` 스키마

```json
{
  "schema": "doltap.context.v1",
  "root": "doltap-s-3q8m5k2p",
  "depth": 2,
  "budget": { "unit": "chars", "limit": 4000, "used": 3812 },
  "nodes": [
    {
      "id": "doltap-s-3q8m5k2p",
      "kind": "s",
      "title": "작업 전 승인",
      "path": "AGENTS.md",
      "line": 42,
      "state": "active",
      "depth": 0,
      "contentHash": "3f2a...",
      "graphHash": "7b04...",
      "body": "정규화하지 않은 원문",
      "bodyTruncated": false
    }
  ],
  "edges": [
    {
      "id": "doltap-s-3q8m5k2p:supersedes:doltap-s-2v7m9q4r",
      "from": "doltap-s-3q8m5k2p",
      "type": "supersedes",
      "to": "doltap-s-2v7m9q4r",
      "direction": "out",
      "review": { "required": false, "state": "none" }
    }
  ],
  "omitted": [
    { "id": "doltap-s-8x1c5tgh", "reason": "budget", "depth": 2 }
  ]
}
```

`state`는 `active` `archived` `legacy` `deleted` 넷입니다. `review.state`는
`none` `fresh` `stale` 셋이고, `stale`이면 그 관계가 재검토 대상입니다.

`omitted`가 비어 있지 않으면 예산이나 깊이에 걸려 빠진 것이 있다는 뜻입니다.
`reason`은 `budget`과 `depth` 둘입니다.

`body`는 **정규화하기 전 원문**입니다. 사람과 호스트 에이전트가 읽을 것이므로
해시 계산용으로 뭉갠 글을 주지 않습니다.

## 감사

결과는 네 갈래로 나눠서 냅니다. 섞으면 근거 수준이 다른 것이 같은 무게로
읽힙니다.

```text
오류        검사기가 결정적으로 확인한 것
재검토 필요  해시가 바뀌어 검토가 만료된 것
제안        호스트 AI가 본문을 읽고 낸 후보
모호함      한 방향으로 정하지 못한 것
```

### 제안과 기각 기록

검토 기록과 같은 연도별 파일에 세 번째 표로 둡니다.

```markdown
## 감사 제안

| 시각 | 제안 ID | 출발 | 관계 | 도착 | 근거 | 판정 | 판정 이유 | 주체 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-11 | doltap-s-aaa@3f2a:verified-by:doltap-d-bbb | doltap-s-aaa | verified-by | doltap-d-bbb | 이 주장이 시험 기록을 근거로 삼음 | 기각 | 그 시험은 다른 것을 봄 | 사람 |
```

제안 ID는 관계 ID에 **제안할 당시 출발 노드의 `contentHash` 앞 4자**를 붙여
만듭니다. 같은 관계를 같은 내용 상태에서 다시 제안하지 않기 위해서입니다.
출발 노드가 실제로 바뀌면 ID가 달라지므로 다시 올릴 수 있습니다.

판정은 `반영` `기각` `보류` 셋입니다. `기각`과 `보류`에는 이유가 필요하고,
빈 이유는 검토 기록과 같은 기준으로 받지 않습니다.

`모호함`으로 분류된 것은 제안 표에 넣지 않습니다. 출발·관계·도착 중 하나를
정하지 못한 상태라 제안 ID를 만들 수 없기 때문입니다. 사람이 방향을 정해 제안이
되거나 버려집니다.

## 전환

자기 적용 저장소와 template이 함께 엄격 검사를 통과한 뒤 새 그래프 검사를
기본값으로 승격합니다. 최종 CLI에서는 임시 `--schema next` 옵션과 이관 NOTICE를
제거합니다. 구형 구조는 오류와 APPLY.md 안내로 알립니다.

## 훅

예시만 제공하고 설치하지 않습니다.

```text
Git       .git/hooks/pre-commit 에 넣을 두 줄
Claude    Stop 훅에서 같은 검사기를 부르는 어댑터
Codex     Stop 훅에서 같은 검사기를 부르는 어댑터
```

셋 다 `doltap check .`를 부르는 것이 전부입니다. 훅마다 다른 검사 논리를 두지
않습니다.

제거 방법을 같은 자리에 적습니다. 넣는 법만 적고 빼는 법을 안 적으면 남습니다.

감사 후보는 검토 가능한 본문만 포함합니다. 발급·검토 파일, 삭제 표식, CLAUDE 특수 노드는 제외합니다.
관계·상태 필터는 후보와 재검토 목록, 기존 제안 판단에 함께 적용합니다.
관계는 선택 범위 안의 끝점 중 하나가 상태·레거시 조건을 만족할 때 포함합니다.
구조 오류는 범위 기준으로 계속 보여줍니다. 미등록 외부 후보에는 상태·관계가 없으므로
두 필터를 지정했을 때 포함하지 않습니다.
