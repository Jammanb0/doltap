# 표식과 관계

[사용 안내](README.md) · 이전: [시작하기](getting-started.md) · 다음: [작업 기록](workstreams.md)

doltap은 문서 안의 **범위 표식**과 범위 사이의 **관계 선언**만 읽습니다. 둘 다 HTML
주석이라 GitHub나 편집기 미리보기처럼 렌더링한 화면에는 보이지 않고, 원문을 여는 사람과
AI에게만 보입니다. 이 문서가 표식·관계·지문·검토 기록의 기준입니다. 검사 결과의 코드는
[검사 항목 참고](checks.md), 명령은 [명령 참고](commands.md)에 있습니다.

## 범위 표식

범위는 시작 표식과 끝 표식 사이의 본문입니다. 각 범위에는 바뀌지 않는 ID가 있습니다.

```markdown
<!-- doltap:start doltap-s-3q8m5k2p -->
## 설치 조건

Node.js 22 이상이 필요합니다.
<!-- doltap:end doltap-s-3q8m5k2p -->
```

- 표식이 있는 문서를 **관리 문서**라고 합니다. 관리 문서에는 문서 전체를 감싸는 `d` 범위가
  하나 있어야 합니다. 그 밖에는 빈 줄, 파일 맨 앞의 YAML front matter, HTML 주석만 둘 수
  있습니다.
- 안쪽 범위는 필요할 때만 만듭니다. 모든 제목이나 문단에 붙이지 않습니다. 따로 참조하거나
  검토할 의미 단위가 기준이며, 설명과 코드 예시가 함께 있어야 뜻이 통하면 한 범위로
  묶습니다.
- 범위 안에 범위를 둘 수 있습니다. 안쪽 범위를 먼저 닫아야 하며, 서로 엇갈리면 오류입니다.
  `d`는 맨 바깥에만, `s`와 `b`는 `d` 안에만 두며 `s`와 `b`는 어느 순서로든 겹쳐 둘 수 있습니다.

### 표식 문법

- 시작 표식은 한 줄(`<!-- doltap:start <ID> -->`)이나 여러 줄로 씁니다. 여러 줄이면 다음
  줄부터 관계 줄을 적고 `-->`만 있는 줄이나 마지막 관계 줄 끝의 `-->`로 닫습니다. 그
  사이에는 관계 줄과 빈 줄만 둡니다.
- 끝 표식은 한 줄(`<!-- doltap:end <ID> -->`)입니다. 가장 안쪽에 열린 범위를 닫습니다.
- 표식은 줄 첫머리(앞 공백은 괜찮음)에서 시작합니다. `<!--`와 `doltap:` 사이 공백은 있어도
  없어도 됩니다. 지시어는 `start`와 `end`뿐이고, 한 줄 표식의 `-->` 뒤에는 아무것도 두지
  않습니다.
- 대문자(`DOLTAP:`), 모르는 지시어, 없거나 형식이 틀린 ID, 표식 뒤의 다른 내용, 줄 가운데의
  표식처럼 모양이 조금이라도 틀린 표식은 조용히 넘기지 않고 오류로 알립니다. 손상된 시작
  표식의 범위는 없는 것으로 보고, 그 ID가 걸린 관계는 판정하지 않습니다.

### 표식으로 읽지 않는 곳

예시를 아래 자리에 적으면 표식으로 읽지 않습니다. 이 문서의 예시도 그래서 표식이 아닙니다.

- 울타리 코드 블록(백틱이나 물결 3개 이상) 안. 인용문(`>`) 안이나 목록 항목 기호 바로 뒤(`- ```js`)에서
  연 코드 블록도 같습니다.
- 들여쓴 코드 블록 안. 다만 목록 항목 안쪽으로 들여쓴 줄은 코드가 아닙니다.
- doltap 표식이 아닌 HTML 주석 안
- 인라인 코드 안

### ID

ID는 `doltap-<종류>-<8자>` 형식입니다. 종류는 문서 전체면 `d`, 절이면 `s`, 문단이나 작은
범위면 `b`입니다. 8자는 숫자와 소문자로 된 무작위 값이며, 헷갈리기 쉬운 i·l·o·u는 쓰지
않습니다. 대문자나 다른 글자가 섞이면 ID가 아닙니다.

- 새 ID는 `doltap id` 명령이 만들어 줍니다. 만들 때 프로젝트의 모든 Markdown 파일(설정으로 뺀
  파일 포함)과 `.doltap/reviews.json`에 이미 있는 ID와 겹치지 않는지 확인합니다. 발급 대장은
  없어서, 예전에 지운 ID가 다시 나오는 것까지 막지는 않습니다.
- 표식을 직접 쓰고 싶으면 `doltap id --kind s`처럼 종류만 주어 쓰지 않은 ID를 받습니다.
- 편집하거나 파일을 옮길 때 ID는 그대로 둡니다.

## 세 가지 관계

관계는 시작 표식 안에 적습니다. 대상은 ID로만 적고 경로는 적지 않습니다.

```markdown
<!-- doltap:start doltap-s-3q8m5k2p
same-as: doltap-s-7c2m9n4r
depends-on: doltap-b-5a8v2x6t
-->
```

| 관계 | 이쪽 | 저쪽 | 뜻 |
| --- | --- | --- | --- |
| 동일 | `same-as` | `same-as` | 같은 의미와 문서 골격을 유지해야 함 |
| 의존 | `depends-on` | `depended-on-by` | 이쪽이 저쪽을 기준·전제·근거로 삼음 |
| 정합성 | `consistent-with` | `consistent-with` | 다른 내용이지만 함께 적용했을 때 어긋나면 안 됨 |

관계 줄은 `<관계 이름>: <ID>[, <ID> …]` 형식입니다. 대상은 쉼표나 공백으로 나누고 끝에 남은
쉼표는 무시합니다. 같은 관계 이름을 여러 줄에 나눠 적어도 합쳐서 읽습니다.

관계를 고를 때는 아래 순서로 물어봅니다.

1. 같은 의미와 골격이어야 하는가? → `same-as`
2. 한쪽이 다른 쪽의 기준·전제·근거인가? → `depends-on`
3. 다른 내용이지만 구체적으로 맞물려야 하는가? → `consistent-with`
4. 단순 참고, 목차, 관련 자료인가? → 관계가 아니라 일반 Markdown 링크

### `same-as` — 번역처럼 같아야 하는 범위

한국어 설치 조건과 영어 설치 조건처럼 언어나 표현은 달라도 뜻과 구성이 같아야 하는 범위입니다.
doltap은 양쪽 선언이 맞은 `same-as` 관계에서 두 범위의 **골격**이 같은지 검사합니다. 안쪽
범위의 본문도 포함하고 표식 줄은 뺍니다.

| 요소 | 비교하는 것 |
| --- | --- |
| 제목 | 범위 안에서 가장 높은 제목을 기준으로 한 상대 수준 |
| 문단 | 개수와 순서. 줄을 바꾼 위치와 공백 수는 보지 않음 |
| 목록 | 번호 목록인지 글머리 목록인지, 항목 수, 항목 안의 요소(하위 목록 포함). 기호가 바뀌면 새 목록 |
| 표 | 열 수와 본문 행 수 |
| 코드 블록 | 위치와 개수. 내용과 언어는 보지 않음 |
| 인용 | 안쪽 요소 |
| 구분선·HTML 블록 | 위치 |

HTML 주석, 링크 참조 정의, 빈 줄은 골격에 넣지 않습니다. 문장 수나 마침표 개수도 보지
않습니다. 골격이 다르면 처음 달라진 자리를 양쪽 줄 번호와 함께 알립니다. 뜻이 실제로
같은지는 사람이나 AI가 검토합니다.

### `depends-on` — 기준이 되는 쪽이 있는 관계

설치 안내(B)가 지원 환경 규칙(A)을 기준으로 쓰였다면 B에 `depends-on: A`, A에
`depended-on-by: B`를 적습니다. 기능 설명이 검증 보고서를 근거로 삼는 경우도 같습니다.

- A가 바뀌면 B가 새 기준에 맞는지 확인합니다.
- B가 바뀌어도 바뀐 B가 A에 맞는지 확인합니다. A를 B에 맞춰 고치라는 뜻이 아닙니다.
- 관계가 있다고 검증에 성공했다는 뜻은 아닙니다. 연결하지 않은 코드의 변경까지 알아채지도
  않습니다.

### `consistent-with` — 맞물려야 하는 다른 내용

사용자 안내에는 "신청서를 이메일로 보낸다", 운영 절차에는 "이메일로 접수한다"가 있다면 두
내용은 다르지만 맞물려야 합니다. 사용자 안내만 웹 양식으로 바뀌면 운영 절차와 어긋납니다.
무엇이 맞아야 하는지 구체적으로 말할 수 있을 때만 씁니다. 주제가 같다는 이유만으로 잇지
않습니다.

## 양쪽에 적고 하나로 다룹니다

관계는 두 범위 모두에 적습니다. 어느 문서만 열어도 관계를 알 수 있게 하려는 것입니다.
`doltap relate`를 쓰면 양쪽 선언을 함께 넣어 줍니다. 두 선언은 관계 하나이며, 검토 기록과
알림도 하나입니다.

- 한쪽 선언이 없거나 종류·방향이 맞지 않으면 `doltap check`가 알립니다. 관계를 해제하는
  중일 수도 있으므로 빠진 쪽을 자동으로 채우지 않습니다. 두 범위를 보고 추가할지 지울지
  정합니다.
- 한 쌍의 범위 사이에는 관계를 하나만 둡니다. 관계를 바꾸려면 `doltap unrelate`로 해제한 뒤
  다시 `relate`합니다.
- A–B, B–C 관계가 있어도 A–C 관계는 생기지 않습니다. `doltap show`는 이런 간접 연결을
  따로 보여 주지만 검토 의무로 바꾸지 않습니다.
- 출력과 검토 기록에서는 관계를 **관계 키**로 가리킵니다. `same-as`와 `consistent-with`는 두
  ID를 사전순으로 놓은 `<앞 ID> <관계> <뒤 ID>`, 의존 관계는 `<의존하는 쪽 ID> depends-on
  <기준 ID>`입니다.

## 관계를 어디에 붙이나

바깥 범위는 안쪽 범위의 본문을 포함합니다. 안쪽 본문이 바뀌면 바깥 범위도 바뀐 것으로
봅니다. 그래서 관계는 **뜻이 충분히 전달되는 가장 작은 범위**에 붙입니다. 문서 전체에
관계를 붙이면 그 문서의 어느 곳을 고쳐도 검토 대기가 됩니다. 포함 관계만으로는 의미 관계가
생기지 않습니다.

## 무엇이 바뀌면 다시 검토하나

doltap은 범위 본문의 **지문**을 계산해 마지막 검토 때와 비교합니다. 지문은 본문을 다듬은 뒤
SHA-256으로 줄인 값이며, 내용이 바뀌었는지 비교하는 데만 씁니다.

- 지문이 바뀌는 것: 글자, 문단 경계, 제목·목록·표·인용의 구성, 코드 블록 안의 내용(공백
  포함), 링크가 가리키는 대상, doltap 표식이 아닌 HTML 주석.
- 지문에 들어가지 않는 것: 문단·목록 항목·인용 안에서 줄을 바꾼 위치, 공백 개수, 표식과
  관계 선언, 검토 기록. 관계를 더하거나 검토를 기록해도 다른 관계의 검토가 풀리지 않습니다.
- 제목·표의 행·구분선은 한 줄로 끝나는 요소라 다음 줄을 이어 붙이지 않습니다. `# 지원`
  다음 줄에 `Node 22`가 있는 것과 `# 지원 Node 22` 한 줄은 다른 글로 봅니다.
- 파일을 옮기고 링크 경로만 고치면 같은 문서를 가리키므로 지문이 원래대로 돌아옵니다.
- 한쪽 범위를 실제로 고치면 그 범위의 다른 관계도 검토 대기가 됩니다. 예를 들어 지원 환경
  규칙이 바뀌어 설치 안내를 고치면, 설치 안내의 번역과의 관계도 다시 확인할 차례가 됩니다.

## 검토 기록

`doltap review`로 남긴 기록은 `.doltap/reviews.json`에 있습니다. 처음 검토를 기록할 때 생기며
직접 고칠 필요는 없습니다.

```json
{
  "version": 1,
  "relations": {
    "doltap-b-5a8v2x6t depends-on doltap-s-7c2m9n4r": {
      "by": "agent",
      "fingerprints": {
        "doltap-b-5a8v2x6t": "4f1c2a9e03b7d615",
        "doltap-s-7c2m9n4r": "a90b3c77e2d41f08"
      },
      "method": 1,
      "note": "설치 안내의 Node 22 조건이 지원 환경 규칙과 같음",
      "reviewedAt": "2026-10-01T05:00:00.000Z"
    }
  }
}
```

- 키는 관계 키입니다. 관계마다 마지막 기록 하나만 두고 지난 기록은 쌓지 않습니다.
- `fingerprints`는 검토할 때 두 범위의 지문입니다. 지금 지문과 다르면 다시 확인할 차례입니다.
- `method`는 그 지문을 만든 계산 방식의 번호입니다. doltap이 지문 계산 방식을 고치면 같은
  글에서도 지문이 달라지므로, 번호가 지금과 다른 기록은 지문을 비교하지 않고 "비교 방식이
  바뀌어 재검토 필요"로 알립니다. 이때도 저절로 검토 완료로 처리하지 않습니다.
- `by`는 `human` 또는 `agent`입니다. 이름 같은 개인정보는 적지 않습니다.
- `note`는 무엇을 확인했는지, `reviewedAt`은 기록한 시각입니다.
- 키를 정렬해 쓰므로 같은 내용이면 같은 파일이 됩니다.

검토 기록은 사람이나 AI가 두 범위를 확인했다는 기록입니다. 내용이 참이라는 증명이나 사용자
승인이 아닙니다.

## 편집하고 옮기고 지울 때

- 평소처럼 편집기로 고칩니다. 표식의 ID만 바꾸지 않으면 됩니다.
- 파일을 옮겨도 관계는 ID로 이어지므로 그대로입니다. 다른 문서의 일반 링크만 새 경로로
  고치면 되고, `doltap check`가 끊어진 링크를 알려 줍니다. 같은 문서를 가리키게 고치면
  지문도 원래대로 돌아옵니다.
- 범위나 문서를 지울 때는 표식도 함께 지웁니다. 관계가 없던 범위라면 그걸로 끝입니다.
  관계가 있던 범위라면 `doltap check`가 남은 선언의 위치를 알려 주므로 그 선언을 지우거나
  `doltap unrelate <ID> <ID> --apply`로 해제합니다. 따로 적어 둘 삭제 기록은 없습니다.
- 복사해서 새 문서를 만들면 ID가 겹칩니다. 복사본에는 `doltap id --kind <종류>`로 받은
  새 ID를 씁니다.

## 보관한 문서와의 관계

마친 작업의 기록은 `.doltap/archive/`에 보관합니다. 보관 위치와 관계의 유효성은 별개입니다.

- 보관한 근거가 지금도 성립해야 현재 내용이 유효하면, 현재 문서의 범위에 `depends-on`으로
  그 근거 범위를 잇습니다. 이 관계는 활성 문서끼리의 관계와 똑같이 검사하고 검토합니다.
- 당시 경위를 참고만 할 때는 일반 링크를 씁니다.
- 현재 결정이 바뀌어도 과거 기록을 현재 내용에 맞춰 고치지 않습니다. 현재 문서와 필요한
  관계를 갱신하고, 과거 기록은 당시 사실로 둡니다.
- 현재 내용과 과거 결정이라는 이유만으로 `same-as`를 잇지 않습니다.
