# doltap 문서 그래프 설계 기록

> 상태: 2026-09-11에 009 워크스트림을 열었다. 이 문서가 그 대작업의 설계
> 원본이고, 「009 워크스트림의 완료 조건」이 그 대작업의 종료 기준으로
> 확정됐다. 그 절을 고치는 것은 009의 완료 조건을 바꾸는 일이므로
> `.doltap/plans/workstreams/009-document-graph/decisions.md`에 이유를 남긴다.

> 보존하고, 초기 질문과 구현에서 확정한 결과를 구분해 둔다. 이 문서를
> 처음 쓸 당시에는 워크스트림을 만들거나 기존 골격·검사기를 변경하지 않았다.
> 009의 문서 이관과 조회·검토·복구 명령을 구현했다. 현재 검증 상태와 남은 행동은
> 워크스트림의 status.md가 원본이다. 이 기록의 초기 논의는 아래에 보존한다.
>
> **이름 주의:** 009의 첫 제품 결정으로 **새 공개 이름을 `doltap`으로 정했다**
> (2026-09-11). npm 패키지명, CLI 명령, 운영 폴더 `.doltap/`, 앵커 접두사가 모두
> 같은 문자열이고, 임시 클론 폴더는 `.doltap-bootstrap/`으로 갈라 충돌을 없앤다.

>

> **왜 이름을 바꾸는지 설명하는 자리**, 개편 전 동작과 같은 이름을 쓰는 남의 저장소다.
> 그 자리는 그때의 사실이므로 그대로 둔다.

## 이 문서의 목적

설계를 시작할 때 doltap의 문서는 사람이 읽을 수 있지만, 문서 사이의 실제 의미 관계는 대부분
에이전트가 글을 읽고 기억해서 복원한다. 문서가 적을 때는 가능하지만, 활성 문서와
아카이브가 오래 쌓이면 다음 문제가 커진다.

- 새 세션이 함께 봐야 할 문서를 놓칠 수 있다.
- 파일 이름이나 제목이 바뀌면 예전 링크가 가리키던 대상을 복구하기 어렵다.
- 어느 규칙이 어느 결정이나 검증 기록에 근거하는지 다시 찾아야 한다.
- 한 문서가 바뀌었을 때 함께 검토해야 할 문서를 잊기 쉽다.
- 아카이브를 포함한 기록이 많아지면 사람이 경로와 제목만으로 관계를 추적하기
  어려워진다.

해결 방향은 AI가 더 잘 기억하게 강제하는 것이 아니다. **문서와 문서 내부 범위에
안정적인 식별자를 주고, 그 사이 관계를 마크다운에 명시하며, doltap이 이를
기계적으로 검사하고 탐색할 수 있게 만드는 것**이다.

그래프는 새 원본이 아니다. 사람이 관리하는 마크다운이 원본이고, 그래프·역방향
색인·JSON·화면은 언제든 다시 만들 수 있는 파생물이다.

### 실제로 확인된 누락 사례

이 설계가 막으려는 문제는 가상이 아니다. 아카이브된 007 워크스트림에는
“외부 사용이 확인되지 않았음”과 “외부 사용자가 없음”을 구분해야 한다는 검토
기록이 있었다. 뒤의 검토에서는 `history.md`의 요약과 활성 `ideas.md`만 읽고 그
워크스트림의 `status.md`까지 열지 않아, 이미 고쳤던 “외부 사용자가 없다”는
단정을 다시 사용했다.

이 사례에서는 AI가 읽은 내용을 잊은 것이 아니라 **필요한 아카이브 범위를 애초에
읽지 않았다.** 개편 전 `cairn check`는 아카이브를 재귀 검사에서 제외하므로 기존
검사만으로는 드러나지 않았다. 아카이브를 포함하는 `map`과 `context`, 그리고
아카이브할 때 살아 있는 전제·열린 질문을 활성 영역으로 승격하는 규칙이 필요한
실제 근거로 사용한다.

## 개편 전 출발점

개편 전 `cairn check`는 의미 그래프를 만들지 않았다. 실제 코드를 기준으로 다음만
했다.

- `AGENTS.md`, `CLAUDE.md`, `.agents/`의 필수 구조를 확인한다.
- `CLAUDE.md`가 `@AGENTS.md` 한 줄인지 확인한다.
- 활성 `.agents/**/*.md`에서 백틱으로 감싼 문자열 중 `/`를 포함하고 `.md`로
  끝나는 경로를 찾아 파일 존재 여부를 확인한다.
- 코드 울타리와 HTML 주석은 이 경로 검사에서 제외한다.
- 아카이브는 재귀 문서 검사에서 제외한다.
- 일반적인 `[표시 이름](경로)` 마크다운 링크, `#제목` 조각, 범위 ID, 관계 유형,
  역방향 연결은 해석하지 않는다.

당시 검사기는 자연어의 뜻을 추론하지 않는다. 새 설계도 자연어 추론을
검사의 핵심으로 삼지 않는다.

## 합의한 핵심 결정

1. 공개 프로젝트 이름 `Cairn`은 바꾼다. 새 이름을 먼저 정하고 그 이름에 맞춰
   CLI, 운영 폴더, 앵커 접두사와 문서를 한 번에 바꾼다. **이름은 `doltap`으로
   정해졌다.**
2. 운영 폴더는 `.agents/`에서 새 이름의 전용 폴더 `.doltap/`로 바꿨다.
3. 새 운영 폴더 아래의 모든 마크다운 문서는 그래프에서 도달 가능해야 한다.
4. 파일 전체, 제목 단위 항목, 더 작은 블록을 모두 노드로 표현할 수 있어야 한다.
5. 각 노드는 프로젝트의 관리 범위 전체에서 유일한 불변 ID를 가진다.
6. 같은 ID를 둘 이상의 파일이나 범위에 두지 않는다.
7. ID는 사람이 임의로 만들지 않고 doltap 명령이 생성한다.
8. 범위는 빈 HTML 앵커 두 개로 시작과 끝을 명시한다.
9. 링크는 표준 마크다운 링크를 사용해 사람이 누를 수 있게 한다.
10. 관계 유형은 링크와 함께 사람이 볼 수 있는 텍스트로 기록한다.
11. 관계는 출발점과 도착점을 가지며, 단방향·대칭·실제 상호 관계를 구분한다.
12. 역방향 색인은 중복 작성하지 않고 doltap이 계산한다.
13. 파일 관계와 세부 항목 관계는 별도 체계가 아니다. 노드의 크기만 다르다.
14. 세부 항목 관계에서 파일 수준 요약 관계를 파생할 수 있지만 원본에 중복
    저장하지 않는다.
15. 아카이브도 검색·복구·그래프의 대상이며, ID와 관계를 유지한다.
16. 아카이브할 때 해결되지 않은 전제와 열린 질문을 조용히 함께 묻지 않는다.
17. 삭제 전에 들어오는 관계를 검사하고, 참조 중인 대상은 기본적으로 삭제를
    거부한다.
18. 변경 감지는 Git이 아니라 파일 내용 해시를 기준으로 한다. Git은 선택적인
    보조 수단일 뿐이다.
19. “검토했음”은 단순 스냅샷 갱신이 아니라, 관계와 양쪽 내용 해시에 묶인 명시적
    검토 기록으로 남긴다.
20. 노드 자신의 최신성 검토와 다른 노드와 맺은 관계의 영향 검토를 구분한다.
21. 검사와 탐색은 Git이 없거나 새 운영 폴더가 `.gitignore`에 있어도 로컬 파일을
    직접 읽어 동작해야 한다.
22. 핵심 기능은 사람이 직접 실행할 수 있는 로컬 CLI로 제공한다. Git·에이전트
    훅은 같은 검사기를 선택적으로 호출할 수 있지만 강제하거나 자동 설치하지
    않는다.
23. doltap은 AI API 키를 받거나 모델 API를 직접 호출하지 않는다. 의미 판단은
    이미 사용 중인 Codex·Claude CLI·데스크톱 같은 호스트 에이전트가 맡는다.
24. 형태를 바꾸는 기반 작업은 한 대작업에서 함께 완성한다. 그래프 화면처럼
    기반 형식을 바꾸지 않는 소비 기능만 뒤로 미룰 수 있다.

## 용어와 데이터 모델

### 노드

노드는 링크할 수 있는 식별된 범위다.

| 접두사 | 이름 | 가리키는 것 |
| --- | --- | --- |
| `d-` | document | 파일 전체 |
| `s-` | section | 제목을 중심으로 한 항목 |
| `b-` | block | 문장 묶음, 목록, 주장처럼 더 작은 명시적 범위 |

접두사는 사람이 ID만 보고 대략적인 크기를 알아보기 위한 것이다. 파일 경로나
제목은 위치와 표시 이름이고, ID는 정체성이다.

### 엣지

엣지는 두 노드 사이의 관계다.

```text
출발 노드 ──관계 유형──▶ 도착 노드
```

예를 들어 다음은 “새 규칙이 이전 규칙을 대체한다”는 뜻이다.

```text
s-new-approval ──supersedes──▶ s-old-approval
```

`supersedes`는 대상 파일의 종류가 아니다. 출발점이 도착점을 어떤 의미로
바라보는지를 나타낸다.

### 포함 관계

파일과 내부 항목의 중첩은 별도로 반복 작성하지 않고 범위 배치에서 계산한다.

```text
d-agents
└─ contains → s-approval
   └─ contains → b-push-approval
```

## 노드의 표준 표현

### 빈 앵커 두 개를 쓴다

범위는 다음 형태를 기본으로 한다.

```markdown
<a name="doltap-s-3q8m5kx0-start" id="doltap-s-3q8m5kx0-start"></a>

## 작업 전 승인

- 커밋 전 승인을 받습니다.
- push 전에도 별도 승인을 받습니다.

<a name="doltap-s-3q8m5kx0-end" id="doltap-s-3q8m5kx0-end"></a>
```

이 앵커는 내용을 `<a>...</a>`로 감싸지 않는다. 시작과 끝에 놓인 빈 표식이다.
`<div>`로 내용을 감싸는 방식은 마크다운 렌더링과 중첩 규칙에 영향을 줄 수
있으므로 기본 형식으로 사용하지 않는다.

기본 ID는 `s-3q8m5k`이고, 실제 앵커 이름에는 역할을 붙인다.

- 시작: `doltap-s-3q8m5kx0-start`
- 끝: `doltap-s-3q8m5kx0-end`

사람과 도구가 이동할 때는 항상 `-start` 앵커를 링크한다. `-end`는 범위 검사와
내용 해시 계산에 사용한다.

### 파일 전체도 같은 방식으로 표현한다

파일 ID를 위한 별도 frontmatter 체계를 만들지 않고 같은 범위 문법을 쓴다.

```markdown
<a name="doltap-d-7h2p4nx0-start" id="doltap-d-7h2p4nx0-start"></a>

# 검증 규칙

이 파일의 전체 내용입니다.

<a name="doltap-d-7h2p4nx0-end" id="doltap-d-7h2p4nx0-end"></a>
```

파일에 YAML frontmatter가 이미 있다면 frontmatter는 파일의 첫 블록으로 유지하고,
문서 시작 앵커는 그 바로 뒤에 둔다. ID의 원본은 frontmatter가 아니라 앵커다.

### 범위 중첩 규칙

범위는 서로 분리되거나 완전히 포함되어야 한다.

허용되는 중첩:

```text
A 시작
  B 시작
  B 끝
A 끝
```

금지되는 교차:

```text
A 시작
  B 시작
A 끝
  B 끝
```

교차 범위는 어느 노드가 내용을 소유하는지 모호하게 하므로 `doltap check` 오류로
처리한다. 파서는 시작 앵커를 스택에 넣고, 끝 앵커가 스택 맨 위 ID와 같은지
확인할 수 있다.

부모 범위의 내용 해시는 기본적으로 자식 범위의 내용도 포함한다. 같은 문장이
여러 개념과 연결되어야 할 때는 교차 범위를 만들지 않고, 하나의 범위에 여러
관계를 붙인다.

### ID 중복은 허용하지 않는다

하나의 ID는 관리 범위 전체에서 정확히 한 노드만 가리킨다. 같은 내용을 두 곳에
두더라도 ID를 공유하지 않는다.

```text
d-active-123 ──mirror-of── d-template-456
```

ID를 공유하면 링크 목적지, 파일 이동 복구, 그래프 노드, 아카이브와 삭제 대상이
모두 모호해진다. 활성 문서, 아카이브, 삭제 표식과 발급 기록을 포함해 중복을
검사하고, 삭제한 ID도 다시 발급하지 않는다.

## 링크와 관계의 표준 표현

### 앵커와 링크의 역할은 다르다

- `<a name="...">`: 노드의 정체성, 주소, 범위를 선언한다.
- `[표시 이름](파일#앵커)`: 다른 노드로 사람이 이동할 수 있는 연결이다.
- 관계 유형: 그 연결을 어떤 의미로 해석할지 정한다.

다른 항목을 단순히 참고하는 문장은 일반 마크다운 링크로 쓸 수 있다.

```markdown
[작업 전 승인](AGENTS.md#doltap-s-3q8m5kx0-start)을 확인합니다.
```

관계 유형을 분명히 해야 하는 연결은 다음처럼 쓴다.

```markdown
- `supersedes` [이전 승인 방식](archive/approval.md#doltap-s-2v7m9qx0-start)
```

표시 이름은 사람이 읽는 라벨이고, 경로는 현재 위치이며, 조각은 불변 ID로 만든
안정적인 목적지다. 파일이 이동해 경로가 깨져도 doltap은 프로젝트에서 같은 ID를
찾아 새 경로를 제안할 수 있다.

관계를 기계적으로 관리해야 하는 줄에서는 허용된 관계 유형을 백틱으로 표시하고
바로 뒤에 대상 링크를 둔다. HTML 주석에 관계를 숨기거나 별도의 관계 전용 파일에만
쓰는 방향은 택하지 않는다.

**일반 링크는 엣지로 보지 않는다.** 이 문서는 처음에 일반 링크를 기본
`references`로 해석하는 쪽으로 적었지만, 009의 2단계에서 그렇게 하지 않기로
정했다. 현재의 정확한 문법은 [현재 사양](document-graph-spec.md)의 「링크와 관계」에 있다.

### 관계의 출발점

링크가 놓인 위치를 포함하는 가장 안쪽 노드가 관계의 출발점이다.

```text
문서 범위 d-A 안
  항목 범위 s-B 안
    링크가 있음
```

이 링크의 출발점은 `d-A`가 아니라 `s-B`다. 파일 전체 관계를 적으려면 어떤
section이나 block 범위에도 들어가지 않은 문서 범위 안의 `문서 관계` 목록에
둔다. `문서 관계` 제목 자체에 section ID를 주지 않으면 그 목록의 가장 안쪽
식별 범위는 문서 노드다.

### 파일 관계와 세부 관계는 같은 문법을 쓴다

노드 종류에 따라 다음 관계가 모두 가능하다.

```text
d → d    파일 전체와 파일 전체
d → s    파일 전체와 다른 파일의 특정 항목
s → d    특정 항목과 다른 파일 전체
s → s    특정 항목끼리
b → s    작은 주장과 근거 항목
```

파일 관계는 문서를 언제 읽고 무엇이 바뀌면 함께 봐야 하는지를 나타내는 운영
관계에 주로 사용한다. 세부 관계는 특정 주장, 규칙, 결정, 검증 근거를 정확히
연결하는 데 사용한다.

### 관계를 만드는 기준

같은 단어가 나오거나 주제가 비슷하다는 이유만으로 관계를 만들지 않는다. 다음
중 하나를 만족해 나중의 탐색이나 검사가 실제로 달라질 때 관계를 만든다.

- **찾기:** 새 세션이 출발 문서에서 대상을 찾아가야 한다.
- **함께 검토하기:** 한쪽 변경이 다른 쪽의 재검토 필요 여부에 영향을 준다.
- **근거 추적하기:** 주장·규칙·산출물의 결정이나 검증 근거를 보존해야 한다.
- **대체 이력 찾기:** 예전 대상을 보았을 때 현재 대상을 찾을 수 있어야 한다.
- **도달성 만들기:** 색인에서 활성 문서나 아카이브 기록으로 들어가는 길이
  필요하다.
- **기계 검사하기:** 미러 일치, 파생물 최신성, 삭제 안전성처럼 관계가 있어야
  결정적으로 검사할 수 있다.

관계의 크기는 실제 의미가 성립하는 가장 작은 안정적인 범위를 고른다.

- 문서 전체가 규칙이나 색인 역할을 하면 `d → d` 또는 `d → s`를 쓴다.
- 특정 절의 주장만 근거를 가지면 문서 전체가 아니라 `s → s`를 쓴다.
- 한두 문장만 검증 대상이면 필요할 때 `b`를 만든다.
- 단순히 읽기 편한 이동만 필요하면 일반 `references` 링크로 충분하다.
- 관계 유형을 설명하기 어렵다면 먼저 `related-to`를 붙이는 것이 아니라, 이
  관계가 실제로 필요한지 다시 본다.

너무 큰 범위에 관계를 붙이면 작은 변경에도 불필요한 재검토가 발생한다. 반대로
모든 문장을 block으로 만들면 작성 부담과 시각적 소음이 커진다. 기본 단위는
document와 section이고, block은 주장 단위 추적이 실제로 필요할 때만 사용한다.

## 관계 유형과 방향

초기 관계 어휘는 작고 의미가 분명해야 한다. 비슷한 관계를 계속 추가하면 같은
뜻을 서로 다른 단어로 기록하게 된다. 다음은 지금까지 필요하다고 본 기본 후보다.

| 저장하는 관계 | 역방향 표시 | 방향 | 뜻 |
| --- | --- | --- | --- |
| `references` | `referenced-by` | 단방향 | 대상을 일반적으로 참고함 |
| `indexes` | `indexed-by` | 단방향 | 대상들을 찾는 목차임 |
| `governs` | `governed-by` | 단방향 | 출발 규칙이 대상에 적용됨 |
| `imports` | `imported-by` | 단방향 | 출발 파일이 도착 파일을 읽어 자기 내용으로 삼음 |
| `depends-on` | `required-by` | 단방향 | 출발 대상을 이해·유지하는 데 도착 대상이 필요함 |
| `produces` | `produced-by` | 단방향 | 절차나 입력이 대상 산출물을 만듦 |
| `verified-by` | `verifies` | 단방향 | 주장이나 문서가 대상 근거로 검증됨 |
| `derived-from` | `source-of` | 단방향 | 출발 내용이 대상에서 파생됨 |
| `decided-by` | `decides` | 단방향 | 규칙이나 구현이 대상 결정에 근거함 |
| `assumes` | `assumption-for` | 단방향 | 출발 판단이 아직 확인되지 않은 대상 전제에 의존함 |
| `supersedes` | `superseded-by` | 단방향 | 출발 대상이 이전 대상을 대체함 |
| `related-to` | `related-to` | 대칭 | 더 구체적인 방향을 정하기 어려운 연관 |
| `mirror-of` | `mirror-of` | 대칭 | 양쪽 내용을 같은 상태로 유지해야 함 |
| `update-with` | `update-with` | 대칭 | 한쪽 변경 시 다른 쪽도 함께 검토해야 함 |

관계 이름과 정확한 허용 대상은 구현 전에 최종 확정해야 한다. 특히
`mirror-of`와 `update-with`가 실제로 같은 검증 규칙을 가져야 하는지는 시험이
필요하다. `assumes`는 아카이브된 전제를 활성 판단에서 계속 보이게 할 후보이며,
전제 자체를 별도 노드로 만들지 아니면 워크스트림 종료 절차의 승격 규칙만으로
해결할지는 구현 전에 정한다.

### 탐색의 양방향성과 의미의 대칭성을 구분한다

`supersedes`는 의미상 단방향이다.

```text
새 규칙 ──supersedes──▶ 이전 규칙
이전 규칙 ──superseded-by──▶ 새 규칙  # doltap이 계산
```

마크다운에는 첫 관계만 기록한다. doltap이 역방향 색인을 만들어 어느 쪽에서도
찾을 수 있게 한다. 즉 **탐색은 양방향이지만 의미는 단방향**이다.

`related-to`, `mirror-of`, `update-with`는 의미 자체가 대칭이다. 이것도 한쪽에
한 번만 기록하고 양쪽에서 같은 관계로 보여준다.

방향별 관계가 실제로 각각 존재한다면 두 개를 기록한다.

```text
A ──depends-on──▶ B
B ──depends-on──▶ A
```

이것은 단순한 양방향 표시가 아니라 순환 의존이다. doltap은 두 관계를 유지하고
순환으로 분석해야 한다.

## 명시적 파일 관계와 파생 파일 관계

파일 수준 그래프에는 두 종류의 선이 생길 수 있다.

### 명시적 관계

사람이 문서 범위에서 직접 선언한 관계다.

```text
AGENTS.md ──governs──▶ verification.md
```

운영 의미가 있으므로 원본 관계이고 검사 대상이다.

### 집계 관계

여러 세부 노드의 관계를 파일 단위로 접어 보여주는 파생 관계다.

```text
AGENTS.md의 항목 3개 ──references──▶ verification.md의 항목 2개

파일 화면에서는:
AGENTS.md ──references × 3──▶ verification.md
```

집계 관계는 마크다운에 다시 저장하지 않는다. 세부 엣지에서 매번 계산한다.
그래프 화면에서는 명시 관계를 실선, 집계 관계를 점선으로 구분할 수 있다. 같은
의미를 파일과 항목에 이중 기록해 서로 어긋나는 일을 막기 위한 규칙이다.

## 관리 범위와 연결되어야 하는 문서

doltap은 저장소의 모든 마크다운과 소스 파일에 ID와 관계를 강제하지 않는다. 기본
관리 범위는 doltap이 운영에 직접 사용하는 문서로 한정한다.

```text
기본 관리 범위
├─ AGENTS.md
├─ CLAUDE.md
└─ .doltap/**/*.md

명시적으로 등록할 수 있는 외부 문서
├─ docs/trials/README.md
└─ doltap 관계의 근거·대상으로 선택한 기타 마크다운
```

- `.doltap/**/*.md`의 운영 문서는 모두 관리 대상이다. 쓰기 명령의 `.bak`·JSON
  복구 자료만 두는 예약 경로 `.doltap/recovery/`는 탐색에서 제외하고 사용자
  문서를 두지 않는다.
- `AGENTS.md`는 doltap 문서의 운영 진입점이므로 관리 대상이다.
- `CLAUDE.md`는 `@AGENTS.md` 한 줄을 유지해야 하는 특수 연결 파일이다. 앵커를
  삽입해 이 제약을 깨지 않고, 고정 ID를 가진 내부 노드에서 `AGENTS.md` 문서
  노드로 향하는 `imports` 관계로 표현한다. 두 파일의 글이 같아야 하는
  `mirror-of`로 보지 않는다.
- `docs/trials/README.md`처럼 doltap 규칙의 근거나 검증 기록으로 실제 사용하는
  외부 문서는 명시적으로 등록할 수 있다.
- 일반 README, 설계 문서, 소스 파일은 저장소에 있다는 이유만으로 자동 관리하지
  않는다.
- 외부 문서의 일반 마크다운 링크를 따라가며 관리 범위를 무한히 확장하지 않는다.
- 관리하지 않는 파일로 향하는 일반 링크는 사람이 이동하는 링크로 남길 수 있다.
  파일 존재 여부만 검사할지 여부는 별도 정책으로 정한다.

외부 문서를 그래프 관리 대상으로 넣으려면 doltap 문서 ID와 관리 범위 안에서
출발한 명시적 관계가 있어야 한다. 반대로 ID 없는 일반 링크 하나만으로 대상
문서 전체에 ID·범위 규칙을 강제하지 않는다.

관리 범위 안의 모든 문서가 서로 직접 링크해야 한다는 뜻도 아니다. 정해진
진입점에서 관계를 따라 도달할 수 있어야 한다는 뜻이다.

예상되는 기본 흐름은 다음과 같다.

```text
AGENTS.md
└─ .doltap/ 운영 문서
   ├─ rules/*
   └─ plans/*
      ├─ project.md → 프로젝트 목적과 범위
      ├─ current.md → 활성 워크스트림
      └─ history.md → 아카이브 워크스트림
```

- 활성 `.doltap/**/*.md`는 현재 운영 진입점에서 도달 가능해야 한다.
- 활성 워크스트림은 `current.md`에서 도달 가능해야 한다.
- 아카이브 워크스트림은 `history.md`나 보존 색인에서 도달 가능해야 한다.
- 아카이브 내부 문서도 해당 워크스트림의 루트에서 도달 가능해야 한다.
- 연결되지 않은 문서는 고아 문서로 보고한다.
- 아카이브에는 과거 판단이 있으므로 현재 규칙의 의미까지 다시 강제하지는
  않지만, ID 중복·깨진 범위·복구 불가능한 대상 같은 그래프 무결성은 검사한다.

`check`와 `map`의 목적은 구분한다. 활성 운영 검사는 현재 상태에 더 엄격할 수
있지만, 장기 검색과 그래프를 만드는 `map`은 아카이브를 반드시 포함한다.

## ID 생성과 수명

### 생성 원칙

ID는 doltap의 별도 명령 또는 같은 내부 모듈을 사용하는 편집 명령이 만든다.

- Node.js 내장 `crypto.randomUUID()` 또는 `randomBytes()`를 사용한다.
- 직접 만든 의사 난수 생성기를 사용하지 않는다.
- 후보를 만든 뒤 관리 범위 전체와 발급 기록에서 중복을 검사한다.
- 중복이면 새 후보를 만들고 다시 검사한다.
- 대상 범위에 이미 ID가 있으면 새 ID를 만들지 않고 기존 ID를 반환한다.
- 동시에 두 명령이 실행될 수 있으므로 임시 잠금과 원자적 교체가 필요하다.
- 잠금 파일은 실행 중에만 존재하고, 적용된 프로젝트에 상주 프로세스를 남기지
  않는다.

정확한 ID 길이와 인코딩은 구현 전에 정한다. 사람이 복사하거나 오류 메시지에서
읽을 수 있을 만큼 짧되, 충돌 가능성을 충분히 낮춰야 한다.

### 발급 기록

삭제한 ID를 다시 쓰지 않으려면 현재 파일만 검색해서는 부족하다. 발급 이력이나
삭제 표식을 보존해야 한다. doltap의 “적용된 프로젝트에는 사람이 읽을 수 있는
마크다운만 남는다”는 성립 조건을 유지하려면 영구 레지스트리도 마크다운으로 두는
방향이 적합하다.

정확한 파일 이름과 표 문법은 미정이지만, 최소한 다음 정보가 필요하다.

- 발급한 ID
- 종류(`d`, `s`, `b`)
- 현재 상태: 활성, 아카이브, 삭제 표식
- 현재 또는 마지막으로 알려진 경로
- 대체 ID가 있다면 그 ID

이 레지스트리는 `.doltap/` 그래프에서 고립되지 않게 운영 색인과 연결한다.

## 이동, 아카이브와 삭제

### 파일이나 항목 이동

ID는 유지하고 경로만 바꾼다. 기존 링크의 경로가 깨져도 대상 ID가 다른 경로에서
유일하게 발견되면 doltap이 다음을 할 수 있어야 한다.

1. 깨진 경로를 보고한다.
2. 동일 ID의 새 위치를 보여준다.
3. 자동 수정 전 변경할 링크 목록을 보여준다.
4. 승인된 수정 명령이 링크 경로만 바꾼다.

내용을 옮기면서 새 ID를 부여하면 이전 관계를 이어갈 수 없으므로, 같은 논리적
대상을 이동한 것이라면 ID를 보존한다.

### 아카이브

아카이브는 삭제가 아니다.

- 문서·section·block ID를 그대로 유지한다.
- 워크스트림 폴더를 아카이브로 옮겨도 내부 관계를 유지한다.
- `current.md`의 활성 관계를 제거하고 `history.md`의 보존 관계를 만든다.
- 경로가 바뀐 기존 링크는 ID를 기준으로 새 아카이브 경로를 찾고 갱신한다.
- 그래프 화면에서는 아카이브 노드를 상태나 색으로 구분한다.
- `map`과 역방향 검색은 아카이브를 포함한다.

아카이브 실행에는 기존 doltap 규칙대로 사용자 승인이 필요하다. 그래프 기능이 이
승인 규칙을 우회해서는 안 된다.

### 살아 있는 전제와 열린 질문은 아카이브 전에 승격한다

현재 운영에서는 공통 결정·전제를 `.doltap/plans/decisions.md`로 승격한다.
규칙의 적용 문구는 AGENTS.md·rules, 프로젝트 설명은 project.md, 미착수 후보는
ideas.md가 맡는다. 작업 종료까지 기다리지 않고 해당 내용이 공통으로 적용되는
시점에 반영한다. 과거 문서는 출처이며, 아카이브의 전제를 직접 참조하는 방식은
그 과거 결과 자체가 필요한 경우에만 선택한다. 모든 현재 판단의 필수 경로가 아니다.

워크스트림을 완료하거나 취소해 아카이브할 때 `status.md`, `decisions.md` 등에
해결되지 않은 전제·위험·열린 질문이 남아 있을 수 있다. 파일을 보존하는 것만으로는
충분하지 않다. 활성 문서가 그 깊은 범위를 가리키지 않으면 이후 에이전트는
`history.md`의 한 줄만 보고 상세 경고를 놓칠 수 있다.

아카이브 전에 각 항목을 다음 중 하나로 처리한다.

1. 실제로 해결하고 결과를 종료 기록에 남긴다.
2. 여전히 유효하면 활성 `ideas.md`, 프로젝트 문서나 후속 워크스트림으로 옮기고
   원래 범위와 명시적으로 연결한다.
3. 현재 판단이 그 전제에 의존하면 `assumes` 같은 타입 관계로 활성 판단에서
   아카이브의 전제 노드를 가리킨다.
4. 더 이상 유효하지 않다면 폐기 이유를 남긴다.

어느 방식이든 해결되지 않은 항목이 아카이브에만 남아 활성 영역에서 찾을 길이
없는 상태를 허용하지 않는다. `map`은 아카이브를 포함하고, `context`는 활성
노드에서 들어가고 나오는 관계를 따라 필요한 아카이브 범위를 가져와야 한다.
종료 검사기가 열린 질문의 자연어 뜻을 추측하지는 않는다. 따라서 어떤 표식이나
관계로 “살아 있는 항목”을 선언할지, 아카이브 전 검사가 이를 어떻게 요구할지는
구현 전에 기계적으로 판정 가능한 문법으로 정한다.

### 결정은 계속 유효한지 이번만인지 선언한다

전제와 열린 질문은 답이 없는 것을 가리킨다. 이미 정한 결정에도 아카이브 때 갈라야
할 구분이 하나 더 있다. **그 대작업이 끝난 뒤에도 따라야 하는 사양인지, 대작업을
운영하는 동안에만 필요했던 판단인지**다. 앞쪽은 담당 활성 원본으로 올려야 하고,
뒤쪽은 폴더와 함께 묻어도 된다.

표식이 없으면 이 구분을 아카이브 직전에 결정 전체를 다시 읽어서 해야 한다. 009의
`decisions.md`만 해도 결정이 스무 개가 넘고 둘이 순서 없이 섞여 있었다. 그래서
워크스트림 `decisions.md`의 결정마다 한 줄을 선언한다.

- `` `계속 유효` `` — 대작업이 끝난 뒤에도 따라야 하는 것. 담당 활성 원본을 같은
  줄에 적는다. 이미 옮겼으면 `활성 원본:`, 아직이면 `옮길 곳:`으로 구분한다.
- `` `이번만` `` — 그 대작업을 운영하며 필요했던 판단. 옮길 곳이 없다.

아카이브 전 검사는 결정(`##` 절)마다 표식이 하나 있는지와 `계속 유효`에 원본이
적혀 있는지만 본다. **적어 둔 원본이 실제로 그 내용을 담고 있는지는 읽지 못한다.**
옮겼다고 적고 옮기지 않는 것을 막지 못하므로 이 표식은 사람이 판단한 결과의
기록이며 이관의 증명이 아니다. 실제로 옮겼는지는 아카이브 전에 사람이 대조한다.

표식은 아카이브 때 몰아서 붙이지 않고 결정을 적을 때 함께 붙인다. 나중에 붙이면
당시 판단을 다시 복원해야 하고, 그 비용이 이 표식으로 줄이려는 바로 그 비용이다.

### 개편 전 아카이브는 삭제하지 않고 동결한다

이번 개편이 크다는 이유로 기존 아카이브를 일괄 삭제하지 않는다. 기존 8개
워크스트림과 그 문서들은 현재 규칙이 만들어진 이유, 실제 검증 근거, 마이그레이션
성공 여부를 확인할 자료다. 지금의 작은 아카이브도 안전하게 옮기지 못한다면 향후
수백·수천 개 기록이 쌓인 사용자의 이관을 신뢰하기 어렵다.

개편 전 기록과 개편 후 기록은 다음처럼 경계를 둔다.

```text
.doltap/archive/
├─ legacy/
│  └─ workstreams/   개편 전 기록
└─ workstreams/      개편 이후 기록
```

레거시 아카이브에는 최신 그래프 작성 규칙을 전부 소급하지 않는다.

- `.doltap/archive/`의 기존 기록을 `.doltap/archive/legacy/` 아래로 옮긴다.
- 각 기존 마크다운 파일에는 최소한 문서 단위 `d-...` ID를 부여한다.
- 기존의 모든 제목과 문장에 section·block ID를 소급해서 붙이지 않는다.
- `history.md`에서 각 레거시 워크스트림의 `README.md`로 이어지게 한다.
- 워크스트림 내부 문서가 기존 링크만으로 모두 도달되지 않으면 레거시 색인이
  빠진 문서를 직접 연결한다.
- 당시 구조와 판단을 설명하는 산문과 명령 예시는 역사적 사실로 보존한다.
- 현재도 눌러서 작동해야 하는 링크와 기계가 읽는 경로만 새 위치로 고친다.
- 최신 규칙 준수나 관계 최신성은 강제하지 않는다.
- 문서 ID 중복, 범위 문법, 파일 존재, 진입점 도달 가능성은 검사한다.
- 개편 후 새로 만들어지는 아카이브부터 전체 document·section·block 및 관계
  규칙을 적용한다.

Git 이력에 남아 있다는 이유만으로 작업 트리의 기록을 지우지 않는다. 그러면
일반 사용자와 에이전트는 과거 결정을 찾기 위해 별도로 Git 이력을 조사해야 하고,
장기 기록을 쉽게 찾아 연결한다는 doltap의 목적과 어긋난다.

정말 가치가 없는 중복이나 실수로 만들어진 파일이 발견되면 일괄 삭제와 분리해
파일별로 판단한다. 삭제 원칙과 사용자 승인 규칙은 레거시에도 그대로 적용한다.

### 삭제

삭제 전에 대상 노드로 들어오는 관계를 모두 보여주는 사전 검사가 필요하다.
참조 중인 노드는 기본적으로 삭제를 거부한다. 처리 방법은 세 가지다.

1. **대체:** 새 노드를 만들고 `supersedes` 관계와 링크 이동을 기록한다.
2. **삭제 표식:** 내용은 없애되 ID, 마지막 경로, 삭제 이유, 대체 ID를 남긴다.
3. **완전 삭제:** 들어오는 관계가 없고 사용자가 명시적으로 승인한 경우에만
   수행한다. ID 발급 기록은 남겨 재사용을 막는다.

파일 삭제는 포함된 자식 노드의 삭제이기도 하므로, 문서 ID뿐 아니라 모든 자식
ID의 들어오는 관계를 검사해야 한다. 폴더 단위 purge는 등록 문서들을 하나의 범위로
묶고 외부 참조 제거를 명시하도록 한다. 미등록 파일은 보존하고 기본은 미리보기다.
코드와 HTML 주석의 예시는 아카이브 선언으로 세지 않는다.

사용자가 파일이나 문단을 직접 지운 경우는 delete-fix로 현재 상태에서 정리한다.
ID 또는 경로를 지정하고 이유를 남기며, 살아 있는 ID와 손상된 범위를 먼저 확인한다.
이동 탐색은 일반 Markdown 관리 경계를 따르고 숨김·빌드·복구 경로는 제외한다.
들어오는 관계 제거는 --drop-links로 따로 명시해야 하며 독립된 관계 줄만 처리한다.
일반 문장·링크는 직접 판단한다. 기본은 미리보기이고 --apply에서 대장과 관계를
함께 갱신한다. 복구는 그 갱신만 되돌리며 이미 지운 본문은 되살리지 못한다.
Git 복원을 강제하지 않되, 정상 삭제의 사전 검사를 대신하는 경로로 삼지는 않는다.

## 변경 감지와 검토 기록

### Git을 기준으로 삼지 않는다

핵심 변경 감지는 각 노드 범위의 정규화된 내용에서 계산한 해시를 사용한다.

```text
노드 ID + 정규화된 범위 내용 → 내용 해시
```

이 방식은 다음 경우에도 동작한다.

- Git 저장소가 아님
- 아직 커밋하지 않음
- 새 운영 폴더가 `.gitignore`에 있음
- 브랜치나 커밋 이력이 없음

Git diff는 변경 설명이나 성능 최적화를 위한 선택 기능으로만 사용할 수 있다.
Git이 없으면 기능이 깨지는 설계는 채택하지 않는다.

### 스냅샷만으로는 부족하다

검사할 때마다 현재 해시로 기준값을 자동 갱신하면 실제로 검토했는지 알 수 없다.
Doorstop처럼 명시적인 검토 명령에서만 기준값을 갱신하면 이 구분은 가능하다.
doltap은 여기에 최신 판단의 이유와 주체를 남긴다. 2026-09-12 사용자 결정으로
과거 검토 누적 대신 대상별 최신 검토를 덮어쓰는 정책을 선택했다.

따라서 상태가 필요한 관계에는 명시적인 검토 기록이 필요하다.

### 노드 검토와 관계 검토를 나눈다

[Doorstop의 `review`와 `clear` 흐름](https://doorstop.readthedocs.io/en/stable/cli/validation.html)은
이 구분이 실제로 쓰이는 선행 사례다. Doorstop은 항목 자신의 현재 지문을
`reviewed`에 저장하고, 연결에는 상대 항목을 확인했을 당시의 지문을 따로 저장한다.
[실제 `item.py`](https://github.com/doorstop-dev/doorstop/blob/develop/doorstop/core/item.py)에서
자기 항목의 지문에는 자신의 링크 목록을 포함하지만, 연결에 저장하는 상대
지문에는 상대의 링크 목록을 포함하지 않는 것을 확인했다. 상대가 다른 링크 하나를
추가했다는 이유만으로 연결을 따라 재검토가 연쇄 전파되는 일을 줄이는 구조로
해석할 수 있다. 이 설계 이유는 확인한 소스 주석에 직접 적혀 있지 않으므로
Doorstop의 공식 설명이 아니라 코드에 근거한 추론으로 구분한다.

doltap도 다음 두 상태를 구분한다.

```text
노드 검토
  이 노드 자신의 현재 내용과 나가는 관계 구성을 검토했는가

관계 검토
  두 노드의 현재 내용이 이 관계에 미치는 영향을 검토했는가
```

Doorstop은 요구사항의 자식에서 부모로 향하는 계층 관계가 중심이므로 연결에 상대
한쪽 지문을 저장한다. doltap에는 `update-with` 같은 대칭 관계와 양쪽 변경이 모두
중요한 `verified-by`가 있으므로, 관계 검토 기록에는 기본적으로 출발·도착 양쪽의
내용 해시를 저장한다. 어떤 관계가 어느 쪽 변경으로 만료되는지는 관계 유형별로
정한다.

Doorstop 소스는 LGPL-3.0-only이므로 코드를 가져오지 않는다. 공개된 동작 원리만
참고해 Node.js 기본 기능으로 독립 구현한다.

```text
관계 ID
출발 노드 ID와 검토 당시 내용 해시
도착 노드 ID와 검토 당시 내용 해시
판단: 반영함 / 영향 없음 / 재검증함 등
짧은 이유
검토 시각
검토 주체: 사람 / 호스트 에이전트
```

관계 유형이 관찰하도록 정한 쪽의 `contentHash`가 바뀌면 그 검토 기록은 자동으로
만료되고 다시 확인할 대상이 된다. 예를 들어 `derived-from`은 원본 쪽 변경이,
대칭 관계는 양쪽 변경이 재검토를 일으킬 수 있다. 정확한 만료 방향은 관계 유형별
규칙으로 확정하며, `update-with`, `derived-from`, `verified-by` 같은 관계의
최신성을 판단할 때 사용한다.

관계 자체의 ID는 프로젝트 ID, 출발 ID, 관계 유형, 도착 ID로 결정적으로 만들 수
있다. 다만 관계 ID 형식과 검토 기록의 마크다운 저장 형식은 구현 전에 확정해야
한다. 검토 기록을 관계가 들어 있는 같은 범위에 넣으면 기록 추가가 내용 해시를
다시 바꾸는 자기 참조 문제가 생기므로, 이름 확정 뒤의 새 운영 폴더 안에 별도
관리 문서로 두는 편이 안전하다.

노드·관계 검토는 .doltap/reviews/reviewed.md에 대상별 최신 한 건만 남기고
덮어쓴다. 현재 해시와 마지막 검토의 해시만 비교하며, 일치하는 과거 기록을 찾아
재사용하지 않는다. A 검토 → B 변경·검토 → A 복원은 재검토 대상이다. B를
검토하지 않았다면 마지막 검토 A와 일치하므로 복원한 A는 유효하다.

이는 Doorstop처럼 마지막으로 검토한 상태를 기준으로 삼고, 같은 대상의 반복
검토로 장부가 커지는 일을 없애려는 사용자 결정이다. Git 없이도 검사와 검토는
동작하지만 과거 판단 보존은 보장하지 않는다. Git도 커밋한 버전만 보존한다.
새 대상과 삭제된 대상의 마지막 기록, 감사 제안 및 복구 백업의 용량 문제는 별개다.

구형 연도별 파일은 첫 검토 실행의 미리보기와 적용 과정에서 이관한다. 대상별로
검토 시각이 가장 늦은 한 건만 가져오고 과거 노드·관계 검토 행은 제거한다.
동일 시각이면 경로순으로 읽은 뒤 나중에 나온 행을 선택한다. 별도 검토 이력은
만들지 않는다. 감사 제안은 연도별 파일에 보존하고, 복구 백업 정책은 유지한다.

`영향 없음`은 단순히 경고를 없애는 명령이 아니다. 비어 있지 않은 구체적인 이유를
필수로 받고, 나중에 같은 판단만 모아 감사할 수 있어야 한다. 에이전트가 기록한
`사람 검토` 표시는 기술적으로 신원을 증명하는 보안 경계가 아니므로, 검토 주체와
사용자의 작업 승인도 구분한다. 관계를 검토했다는 영수증은 커밋·push·아카이브
같은 별도 작업의 사용자 승인이 아니다.

모든 항목을 한 번에 검토 완료로 만드는 기본 명령은 두지 않는다. 일괄 처리가
필요해지더라도 대상과 변경 요약을 먼저 보여주고, 명시적인 범위와 판단 이유를
요구해야 한다. 기록은 “현재 상태를 살펴봤다”는 영수증이지 내용이 참이라는
증명이 아니다.

### 내용 해시와 관계 구성 해시를 구분한다

SHA-256 계산 자체는 단순하지만 무엇을 해시할지 정하는 일은 이 기능에서 가장
어려운 부분이다. 한 종류의 해시로 본문 변경과 관계 구성 변경을 모두 표현하면,
상대가 새 관계를 하나 추가했을 때 관계망 전체로 재검토가 번질 수 있다.

개념적으로 다음 두 값을 구분한다.

```text
contentHash
  정규화한 사람이 쓴 의미 내용
  관계가 상대 내용의 변화를 관찰할 때 사용

graphHash
  현재 노드가 선언한 관계 ID·유형·대상 구성
  노드 자신의 관계 구성을 검토할 때 사용
```

관계 검토 영수증은 관계 유형이 요구하는 양쪽 `contentHash`를 사용하고, 관계
선언 자체가 바뀌면 관계 ID 또는 `graphHash` 변화로 따로 드러낸다. start/end
앵커, 검토 영수증과 순수 doltap 메타데이터는 `contentHash`에서 제외하는 방향으로
간다. 다만 사람이 읽는 관계 줄의 표시 이름과 설명, 일반 마크다운 링크를 어디까지
의미 내용으로 볼지는 fixture와 회귀 시험으로 최종 고정한다.

내용 해시는 경로와 분리한다. 같은 노드를 다른 파일로 옮긴 것만으로 내용 변경이
되면 안 된다. 최소한 줄바꿈 차이와 start/end 앵커 같은 doltap 경계 표식을 어떻게
정규화할지 정해야 한다. `mirror-of`가 서로 다른 ID 표식을 제외하고 무엇을
비교할지도 구현 전 시험으로 고정한다. 이 규칙이 불분명하면 실제 글은 같은데 ID가
다르다는 이유로 미러가 항상 불일치할 수 있다.

### 실행 방식: 수동 실행이 기본이고 자동 호출은 선택이다

doltap이 제공하는 핵심은 개인이 현재 작업 디렉터리에서 직접 실행할 수 있는 하나의
로컬 검사 스크립트, 즉 CLI 검사기다. CI 서비스가 없어도 이 기능이 완전하게
동작하는 것이 우선이다.

```text
doltap check
├─ 사람이 직접 실행
├─ 선택적 Git 훅에서 실행
├─ 선택적 Claude·Codex 훅에서 실행
└─ 선택적 CI에서 실행
```

훅과 CI가 별도의 검사 논리를 가지지 않는다. 모두 같은 `doltap check`와 같은
기계용 출력을 호출해야 한다. 그래야 수동 실행과 자동 실행의 판정이 갈라지지
않는다.

기본 적용 절차는 훅을 설치하거나 외부 설정을 수정하지 않는다. 사용자가 선택한
경우에만 Git 훅이나 에이전트 훅에서 검사기를 호출한다. 선택적 훅을 설치하면 그
clone이나 도구 설정에 doltap 관련 호출이 남을 수 있으므로 위치, 동작, 제거 방법을
먼저 보여줘야 한다. 이는 기본 적용 결과에 상주 프로세스나 필수 런타임을 남기지
않는다는 원칙의 명시적인 선택 사항이다.

정책을 한 문장으로 정리하면 **훅과 CI를 강제하지 않는다. 단, 사용할 수 있는
환경은 만든다**이다. 여기서 환경은 훅·CI마다 새로운 검사기를 만드는 것이 아니라,
로컬 명령, 종료 코드, JSON 출력과 짧은 연결 예시를 제공한다는 뜻이다. 제품의
초점은 CI 파이프라인보다 개인의 수동 실행과 로컬 자동 호출에 둔다.

Git 훅은 CI와 비슷한 로컬 품질 관문이지만 CI와 같지 않다.

- 현재 clone과 현재 컴퓨터에서만 실행된다.
- Git을 사용하지 않으면 실행할 수 없다.
- 다른 clone에 Git 훅이 자동 전달되지 않는다.
- 설치하지 않았거나 우회한 사용자의 작업은 검사하지 못한다.
- 별도 깨끗한 환경이나 중앙 실행 기록을 제공하지 않는다.
- 대신 현재 작업 디렉터리를 읽으므로 gitignore된 `.doltap/`도 검사할 수 있다.

에이전트 훅도 해당 Claude·Codex 실행에서만 작동한다. 모든 파일 읽기를 가로막는
강제 장치로 쓰지 않고, 작업 완료 시점이나 사용자가 고른 시점에 같은 검사기를
호출하는 용도로 쓴다. 도구별 훅 형식과 입출력 어댑터가 필요할 수 있지만 검사
규칙을 복제하지 않는다.

검사기는 최소한 사람용 출력, 안정적인 종료 코드, 기계용 JSON 출력을 제공해야
한다. 정확한 옵션 이름은 구현 전에 정하지만 다음 사용이 가능해야 한다.

```text
doltap check .
doltap check . --json
```

### Gitignore와 CI의 한계

`.doltap/`이 gitignore되어도 같은 작업 디렉터리의 로컬 검사는 정상 동작해야
한다. 그러나 CI checkout에는 무시된 파일이 전달되지 않으므로 CI는 존재하지 않는
`.doltap/`을 검사할 수 없다. 이것은 검사기 문제가 아니라 입력 파일이 없는
문제다.

- `.doltap/`과 검토 기록을 커밋하면 CI에서도 같은 무결성·최신성 검사를 실행할 수
  있다.
- 커밋하지 않으면 수동 실행, 로컬 Git 훅, 로컬 에이전트 훅과 로컬 그래프만
  사용할 수 있다.
- doltap 자체 저장소의 CI는 doltap 코드·template·플랫폼 동작 검증을 위해
  현재처럼 유지할 수 있다.
- doltap을 적용한 프로젝트에는 CI를 기본 요구사항이나 필수 강제 수단으로 두지
  않는다. CI 연동은 지원 가능한 부가 사용법일 뿐 제품의 중심이 아니다. 원본이
  CI에 전달되고 프로젝트가 원할 때만 같은 검사기를 호출한다.

## 검사기가 책임질 것

형식을 문서에 먼저 심고 검사기를 나중으로 미루지 않는다. 잘못된 ID와 관계가
쌓이면 나중에 소급 정리해야 하므로, 새 형식과 최소 검사기는 같은 기반 변경에서
함께 제공한다.

### 상태가 필요 없는 검사

- 시작·끝 앵커 문법
- 끝나지 않은 범위와 잘못 닫힌 범위
- 교차 범위 금지
- ID 전체 유일성
- ID 접두사와 노드 종류 일치
- 허용되지 않은 관계 유형
- 링크 대상 파일과 ID 존재 여부
- 링크 경로가 깨졌지만 같은 ID가 이동했는지 여부
- 대칭 관계의 불필요한 중복 선언
- 모든 `.doltap/**/*.md`의 진입점 도달 가능성
- 활성 워크스트림과 `current.md` 관계
- 아카이브 워크스트림과 `history.md` 관계
- 아카이브되는 워크스트림의 살아 있는 전제·열린 질문이 해결·승격·폐기 중 하나로
  처리됐는지
- 참조 중인 노드 삭제 시도
- `mirror-of`처럼 결정적으로 비교 가능한 관계

### 검토 기록이 필요한 검사

- `update-with` 양쪽 중 하나가 검토 이후 바뀌었는지
- `derived-from` 원본 변경 후 파생 문서를 다시 확인했는지
- `verified-by` 주장이나 근거가 검토 이후 바뀌었는지
- “영향 없음” 판단이 현재 양쪽 내용 해시에 대한 것인지
- 검토 기록에 판단 이유와 검토 주체가 있으며, 관계 유형이 요구하는 양쪽 해시와
  일치하는지

오류와 사람의 판단 대상을 구분한다. 존재하지 않는 ID나 교차 범위는 오류지만,
내용이 바뀌어 재검토가 필요한 관계는 곧바로 내용 불일치라고 단정하지 않는다.

### AI가 잊는 문제를 운영에서 막는 시점

관계를 기록해도 아무도 검사하지 않으면 잊는 문제는 남는다. 해결은 모든 파일
읽기를 훅으로 막는 것이 아니라, 기존 doltap 방식대로 중요한 완료 시점에 한 번의
결정적인 검사를 실행하게 하는 것이다.

```text
작업 중
  → 마크다운과 관계 갱신
  → 완료 보고 전 doltap check
  → 깨진 관계·고아 문서·재검토 필요 항목 확인
  → 필요한 판단을 검토 기록으로 남김
  → 다시 check
  → 통과한 범위만 완료로 보고
```

이 검사는 Git diff가 아니라 현재 파일시스템을 읽는다. 에이전트 지시 문서에는
“완료 보고 전 검사”를 두되, PreToolUse 훅이나 상주 감시기로 매 행동을 차단하지
않는다. 검사하지 않은 에이전트의 행동 자체를 기술적으로 금지할 수는 없지만,
검사를 실행한 순간 누락을 결정적으로 드러내는 것이 doltap이 책임질 범위다. 같은
완료 검사를 Git 훅이나 에이전트 훅에서 자동 호출하는 것은 사용자가 선택할 수
있지만, 훅이 doltap의 유일한 실행 경로가 되지는 않는다.

## 예상 명령의 역할

정확한 명령 이름은 대작업에서 확정한다. 필요한 기능 단위는 다음과 같다.

- **ID 생성·범위 삽입:** 종류와 대상 위치를 받아 고유 ID와 시작·끝 앵커를 넣음
- **관계 추가:** 출발 범위와 대상 ID, 관계 유형을 받아 표준 마크다운 링크를 만듦
- **검사:** 문법, 중복, 대상, 도달성, 삭제, 검토 만료를 검사함
- **지도 생성:** 활성 문서와 아카이브를 포함해 노드와 엣지를 JSON으로 출력함
- **맥락 조회:** 특정 노드에서 시작해 관계 깊이와 출력 예산 안의 범위만 제공함
- **범위 감사:** 특정 폴더·문서 집합을 훑을 수 있도록 기계적 문제와 AI 검토
  후보를 준비함
- **역방향 조회:** 특정 노드를 가리키는 모든 관계를 보여줌
- **이동 복구:** ID는 찾았지만 경로가 깨진 링크의 수정안을 만듦
- **검토 기록:** 현재 양쪽 해시에 대해 사람이 내린 판단을 기록함

예를 들어 `doltap map --json`은 화면 구현과 에이전트 질의가 함께 사용할 안정적인
중간 형식이 될 수 있다. 명령 이름을 먼저 고정하기보다 출력 스키마와 실패 조건을
시험으로 정하는 것이 우선이다.

## 필요한 범위만 읽는 `context`

그래프의 첫 목적은 누락 방지와 이동 복구다. 두 번째 효과로 AI가 관련 없는 문서
전체를 읽지 않고 필요한 범위만 선택하게 해 읽기 비용을 줄일 수 있다. 이 효과를
얻으려면 지도 JSON만 만들지 않고 범위 중심 조회를 기반에 포함해야 한다.

가칭 명령은 다음과 같다.

```text
doltap context <ID>
doltap context <ID> --depth 2 --budget 4000
```

출력에는 다음이 들어간다.

- 노드의 제목과 현재 경로
- start/end 사이의 실제 내용
- 직접 나가고 들어오는 관계
- 필요한 부모·자식 범위
- 재검토가 필요한 관계
- 옵션으로 선택한 아카이브 관계

AI에게 전달하는 출력에서는 탐색에 불필요한 앵커 반복과 내부 관리 정보를 줄인다.
관계 깊이, 활성·아카이브 상태, 관계 유형, 문자나 토큰에 대응하는 출력 예산을
제한할 수 있어야 한다. 정확한 토큰 수 계산을 위해 모델별 tokenizer를 필수
의존성으로 넣기보다 안정적인 문자·바이트 근사치를 사용할 수 있다.

`context`는 본문을 이해하는 일을 대신하지 않는다. 관련 범위를 고르는 비용과
같은 파일을 반복 탐색하는 비용을 줄이는 기능이다. 문서가 적을 때보다 아카이브와
관계가 많이 쌓였을 때 효과가 커진다. 관계를 지나치게 넓고 많이 만들면 오히려
출력이 커지므로 document·section을 기본으로 하고 필요한 주장만 block으로
좁힌다는 원칙과 함께 사용한다.

## 넓은 범위를 다시 살피는 `audit`

`context`가 특정 노드에서 좁게 출발한다면, 감사는 특정 폴더나 문서 집합에서
넓게 출발한다.

```text
context: 특정 노드 → 관련 범위만 선택 → 작업 맥락과 비용 절감
audit:   특정 범위 → 전체 관계를 재검토 → 누락과 의미 변화 발견
```

가칭 사용 예:

```text
doltap audit .doltap/rules
doltap audit .doltap/plans
doltap audit docs/trials --relation verified-by
doltap audit .doltap/archive --include-legacy
doltap audit .doltap --changed --budget 8000
```

감사는 관리 범위 전체를 항상 읽는 명령이 아니다. 사용자가 경로, 관계 유형,
활성·아카이브 상태를 선택할 수 있어야 한다. 이전 감사 이후 해시가 바뀐 노드를
우선하고, 바뀌지 않은 범위는 건너뛰며, 레거시 아카이브는 명시했을 때만 포함한다.
사용자가 외부 경로를 감사 범위로 직접 지정할 수는 있지만, 일회성 감사만으로 그
폴더의 모든 문서가 그래프 관리 대상에 자동 등록되지는 않는다. 감사 결과에서
승인해 ID와 관계를 부여한 문서만 명시적 외부 관리 대상이 된다.

### 기계 검사와 의미 감사를 나눈다

doltap만으로 확정할 수 있는 것:

- 중복 ID, 깨진 범위와 없는 대상
- 고아 문서와 삭제된 노드를 가리키는 관계
- 허용되지 않거나 폐기된 관계 유형
- `mirror-of`의 결정적인 불일치
- 검토 기록 이후 달라진 내용 해시

본문의 뜻을 읽어야 판단할 수 있는 것:

- 주장에 `verified-by`가 새로 필요한지
- 일반 `references`보다 `derived-from`이나 `decided-by`가 정확한지
- 새 문서가 과거 결정을 대체했는데 `supersedes`가 빠졌는지
- 두 문서가 의미상 충돌하는지
- 관계 범위를 document에서 section이나 block으로 좁혀야 하는지
- 더 이상 의미 없는 관계가 남아 있는지

결과는 근거 수준을 섞지 않는다.

| 결과 | 뜻 |
| --- | --- |
| 오류 | doltap이 결정적으로 확인한 무결성 문제 |
| 재검토 필요 | 내용 해시 변경으로 기존 검토가 만료된 상태 |
| 제안 | 호스트 AI가 본문을 읽고 근거와 함께 제시한 변경 후보 |
| 모호함 | 한 방향으로 확정하지 못해 사람의 판단이 필요한 항목 |

AI 제안은 자동으로 원본 그래프에 쓰지 않는다. 출발·대상 범위와 근거를 보여주고
승인된 관계만 표준 문법으로 반영한 뒤 `doltap check`를 다시 실행한다. 이미
검토하고 기각한 제안을 반복하지 않도록 감사 시점의 해시와 판단 기록을 남길 수
있어야 한다.

### doltap은 AI API를 호출하지 않는다

doltap CLI의 책임은 로컬 파일을 읽어 그래프, 내용 해시, 결정적인 오류, 감사 후보,
필요한 문맥 묶음을 텍스트나 JSON으로 출력하는 데까지다. API 키 입력, OpenAI·
Anthropic SDK, 외부 모델 호출을 넣지 않는다.

```text
doltap CLI
  → 로컬에서 check·map·context·감사 후보 생성
  → 텍스트 또는 JSON 출력

현재 사용 중인 Codex·Claude CLI·데스크톱
  → 출력이 가리키는 범위를 읽음
  → 의미상 누락·잘못된 관계를 판단
  → 근거가 붙은 수정안을 제안
  → 승인된 내용만 반영
```

AI가 없는 터미널에서도 `check`, `map`, `context`와 감사의 기계적 부분은 온전히
동작한다. 의미 판단이 필요한 후보는 “AI 또는 사람의 검토 필요”로 남는다. Codex나
Claude 안에서 실행할 때는 이미 그 세션에서 사용하는 호스트 모델이 마지막 의미
검토를 맡는다. doltap 자체는 별도 API 계정·키나 직접 청구되는 모델 호출을
요구하지 않는다. 다만 의미 감사를 수행하는 호스트 에이전트의 기존 사용량과
네트워크 요구사항까지 없애는 것은 아니다.

## 그래프 화면으로 확장하는 방법

이 형식만 갖춰지면 AI 추론 없이도 화면 그래프를 만들 수 있다.

- 앵커 ID → 노드
- start/end → 노드 내용과 미리보기
- 범위 중첩 → `contains` 엣지
- 타입이 붙은 링크 → 명시적 엣지
- 역방향 색인 → 들어오는 관계
- 파일 경로와 start 앵커 → 클릭할 위치
- 활성·아카이브·삭제 표식 → 노드 상태
- 검토 기록 → 최신·재검토 필요 상태

첫 화면은 파일 노드만 보여주고, 파일을 펼치면 section과 block을 보여주는 방식이
적합하다.

```text
파일 보기
AGENTS.md ─────▶ verification.md
    └──────────▶ current.md

AGENTS.md 펼치기
├─ 프로젝트 설정
├─ 작업 전 승인
│  ├─ 커밋 승인
│  └─ push 승인
└─ Git과 커밋
```

표현 규칙의 예:

- 화살표: 단방향 의미
- 화살표 없는 선: 대칭 관계
- 실선: 명시한 원본 관계
- 점선: 세부 관계에서 집계한 파일 관계
- 회색 노드: 아카이브
- 삭제 표식 아이콘: 내용이 제거된 ID
- 빨간 선: 대상 없음이나 문법 오류
- 노란 선: 내용 변경 후 재검토 필요

정적 HTML로 시각화할 수 있다. 그래프에서 노드를 눌러 VS Code나 다른 편집기의
정확한 파일 위치로 여는 기능은 편집기별 연결 방식이 다르므로 별도 어댑터가
필요할 수 있다. 화면과 편집기 연동은 기반 ID·관계 형식을 바꾸지 않고 나중에
추가할 수 있으므로 첫 대작업의 필수 범위가 아니다.

## 프로젝트 이름과 운영 폴더 전환

### `Cairn` 이름은 기반 구현 전에 바꾼다

같은 AI 에이전트·프로젝트 기억 분야에서 `Cairn`이라는 이름이 이미 반복 사용되고
있다. 특히 [`cairn-framework/cairn`](https://github.com/cairn-framework/cairn)은
`.cairn/`, 타입 그래프, `context`, 변경 감지, 훅과 웹 탐색기를 사용하고,
[`iBlinkQ/project-cairn`](https://github.com/iBlinkQ/project-cairn)은 `AGENTS.md`와
Markdown 프로젝트 기억을 Claude Code·Codex용 스킬로 관리한다. 이 밖에도 같은
이름의 AI 에이전트·기억·테스트 도구가 여럿 있어 검색과 설명만이 아니라 CLI와
운영 폴더의 실제 충돌 가능성이 있다.

당시 `package.json`의 npm 패키지 이름은 `cairn-agents`였고 npm 레지스트리에는
등록되지 않은 상태였다. 패키지 이름이 따로 있어도 설치되는 명령 `cairn`, GitHub
저장소 이름과 예정 운영 폴더 `.cairn/`의 충돌은 해결되지 않았다.

따라서 다음 순서를 지킨다.

1. 009 워크스트림의 첫 제품 결정으로 새 공개 이름을 정한다. **끝났다 —
   `doltap`이다.**
2. 새 이름에 맞는 npm 패키지명, CLI 명령, 운영 폴더와 앵커 접두사를 함께 정한다.
   **끝났다 — 넷 다 `doltap`이고 운영 폴더는 `.doltap/`이다.**
3. `.agents/`와 기존 명령을 새 체계로 옮겼다. 009의 5단계에서 실행했다.

불변 ID는 4단계 발급기와 6단계 문서 이관에서 넣었다. 현재 형식의 정확한 값은
[현재 사양](document-graph-spec.md)이 정하고, 실제 명령 사용법은 GRAPH.md에 있다.

### 운영 폴더를 바꾸는 범위

이름 변경은 폴더 하나를 옮기는 작업이 아니다. 최소한 다음이 함께 바뀐다.

- 이 저장소가 실제로 사용하는 `.doltap/`
- 배포 원본 `template/.doltap/`
- 적용용 `setup-workstream/` 문서
- `AGENTS.md`와 template의 안내표·규칙
- `README.md`, `README.en.md`, `APPLY.md`
- `lib/check.mjs`, CLI 출력과 사용법
- 시험 fixture와 예상 경로
- 패키지 배포 파일 확인
- 워크스트림 활성·아카이브 경로

개편 전 `.cairn/`은 기존 프로젝트에 적용할 때 저장소를 얕게 클론하는 임시 폴더
이름이었다. 새 운영 폴더가 이 경로와 같거나 충돌하면 임시 클론 기본
이름도 함께 바꿔야 한다. **이름이 정해지면서 이 충돌은 실제로 생긴다** — 운영
폴더가 `.doltap/`이므로 임시 클론 폴더는 `.doltap-bootstrap/`으로 갈라 둔다.

링크와 기록은 시간이 지날수록 늘어나므로 이름 변경과 기반 형식 도입을 여러 번의
호환성 마이그레이션으로 나누는 것보다 한 대작업에서 완성하는 편이 낫다. 다만
기존 사용자의 존재가 확인되지 않았다는 것을 사용자가 없다는 사실로 단정하지
않는다. 구형 구조를 영구 지원하는 호환 계층은 기본 범위에 넣지 않되, 구형 구조를
발견하면 무엇이 바뀌었고 어디에서 이관 방법을 볼 수 있는지 안내한다.

적용·마이그레이션 절차는 외부 사용자 수와 무관하게 사용자 문서를 바꾸는 작업이다.
변경할 파일과 diff를 먼저 보여주고 사용자가 승인한 뒤 적용하며, 중간 실패에도
원본을 잃지 않게 설계한다. 전용 롤백 명령이나 장기 다운그레이드 지원까지 반드시
만들 필요는 없지만, 임시 위치에서 완성한 뒤 교체하거나 백업을 남기는 등 Git이
없는 프로젝트에서도 부분 적용을 복구할 최소 수단은 필요하다. 구현에서는
`migrate`와 `recover`를 두고, 기본 미리보기와 명시적 `--apply`를 채택했다.

구형 구조 감지는 침묵해서는 안 된다. 예를 들어 구형 `.agents/`는 있고 새 운영
폴더가 없다면 필수 문서가 없다는 일반 오류만 내지 말고, 구조가 바뀌었다는 사실과
이관 안내 위치를 짧게 알려준다. 이는 구형 구조를 계속 지원하는 호환 계층이 아니라
확인되지 않은 기존 사용자가 막혔을 때의 최소한의 복구 경로다.

### 전환 중 검사 정책

이 저장소는 자기 자신에게 doltap을 적용하고 `template/`도 같은 검사기로 검증한다.
새 검사기가 먼저 엄격해지면 아직 이관하지 않은 현재 문서와 template이 모두
실패하고, 문서를 먼저 옮기면 구형 검사기가 새 구조를 이해하지 못한다. 개발 중
작업 트리가 잠시 실패하는 것은 허용할 수 있지만, 검사를 제거하거나 꺼 둔 상태를
중간 커밋이나 완료 상태로 남기지 않는다.

전환 중에는 기존 검사와 새 검사를 다음처럼 함께 보이게 한다.

```text
기본 검사
  기존 규칙 위반       → 문제(PROBLEM), 종료 코드 실패
  새 그래프 이관 상태  → 확인(NOTICE), 종료 코드 영향 없음

차기 스키마 엄격 검사
  새 그래프 규칙 위반  → 문제(PROBLEM), 종료 코드 실패

이관 완료 뒤 기본 검사
  새 그래프 규칙 위반  → 문제(PROBLEM), 종료 코드 실패
```

전환 중에는 `--schema next`를 사용했고, 10단계에서 제거했다. 현재 check는
새 그래프 위반을 기본 실패 조건으로 삼는다. 전환 중 기본 검사에서는 이관량을
문서·유형별로 요약했다. 기존 `문제`와 `확인` 구분을 그대로 사용한다.

새 파서와 검사는 fixture에서 처음부터 엄격하게 시험한다. 실제 저장소와 template은
기본 NOTICE로 남은 이관량을 계속 보여주고, 엄격 검사가 통과한 뒤 둘을 같은 전환
지점에서 새 기본값으로 승격한다. 승격 조건과 임시 옵션 제거 여부도 기반 대작업의
완료 조건으로 고정한다.

### 구현 난이도와 가장 큰 위험

해시 함수 호출과 난수 ID 후보 생성 자체는 어렵지 않다. 가장 어려운 단일 항목은
줄바꿈·공백·앵커·관계 선언·중첩 범위를 어떤 의미 내용으로 볼지 정하는
**정규화 규칙**이다. 잘못 정하면 작은 서식 변경마다 재검토가 쏟아지거나 중요한
변경을 놓친다.

현재 저장소와 template의 문서 변환만 보면 데이터 이관 난이도는 중간 정도다.
레거시 아카이브에는 문서 ID만 소급하고 세부 범위를 동결하기 때문이다. 다만
미리보기, 승인, 부분 실패 방지, 자기 적용 저장소와 template의 같은 시점 전환은
문서 개수와 별개의 제품 안전성 작업이다. 확인되지 않은 사용자를 위한 장기 호환
계층은 만들지 않지만 이 안전성은 줄이지 않는다.

코드가 처음 동작하는 시점과 규칙이 장기간 쓸 만큼 안정되는 시점을 구분한다.
오탐은 소스만 읽어서 모두 찾기 어렵고 실제 문서를 편집하는 동안 드러난다. 최소
규칙과 fixture를 일찍 완성해 이 저장소에서 직접 사용하고, 어떤 알림을 왜
오탐으로 판단했는지 시험으로 옮긴다. 커밋 수, 현재 코드 줄 수나 근거 없는 배수로
전체 기간과 최종 코드 크기를 단정하지 않는다.

| 아카이브된 이름을 `current.md`가 가리킬 때 메시지가 부정확함 | 새 활성·아카이브 ID 해석에 포함 | 경로 추측을 고치는 것보다 ID로 위치와 상태를 구분하는 것이 근본 해결임 |
| `~~~`와 들여쓴 코드 블록을 구분하지 못함 | 새 마크다운 파서 시험에 포함 | 기존 경로 토큰 파서를 먼저 고치면 새 앵커·링크 파서에서 다시 작업하게 됨 |
| 검사 범위가 `.doltap/` 안으로 한정됨 | 새 관리 범위·도달성 설계에 포함 | 외부 검증 문서와 근거 링크까지 연결할 새 범위 규칙이 필요함 |
| 임시 골격 이름 `.doltap`만 검사함 | 공개 이름과 운영 폴더 이름을 확정할 때 제거·대체 | `.doltap/`도 임시 이름이므로 새 이름을 정한 뒤 검사 대상을 한 번에 바꿔야 함 |
| 경로가 뒤따르지 않는 임시 폴더 언급을 놓침 | ID·표준 링크 검사로 대체 | 자연어 속 폴더 이름을 추측하는 기존 기준을 확장하지 않음 |

이 항목은 기존 검사기에 작은 수정으로 먼저 넣지 않는다. 대작업을 열면 각각을
새 검사기의 요구사항과 회귀 시험으로 옮기고, 구현이 끝난 뒤 `ideas.md`와 알려진
제한에서 해결 상태를 정리한다.

### 기반 뒤로 미룰 항목

- **템플릿 영어판:** 지금 번역하면 `.doltap/`, ID·관계 문법, 새 CLI와 적용 절차를
  개편 뒤 다시 번역해야 한다. 새 한국어 골격과 용어가 안정된 뒤 진행한다.
- **npm 레지스트리 등록:** 지금 공개하면 곧 폴더·검사·template·CLI가 크게 바뀐
  후속 버전을 다시 배포해야 한다. 문서 그래프 기반이 정착된 버전을 npm 공개의
  출발점으로 삼는다. 패키지 이름 사용 가능 여부는 등록 시점에 다시 확인한다.
- **원격 브랜치·PR·병합 검증:** 새 경로와 template으로 다시 실행해야 하므로
  기반 이관 후 검증한다.
- **승인 출처와 승인 종료점 재현 시험:** 규칙 자체는 그대로 보존하되, 경로와
  fixture가 바뀐 새 구조에서 두 시험을 함께 다시 실행한다.

### 독립적으로 남겨도 되는 항목

PowerShell에서 작은따옴표가 포함된 폴더 이름의 `cd` 안내가 깨지는 문제는 문서
그래프와 직접 연결되지 않는다. 같은 CLI 파일을 크게 고친다는 이유만으로 범위를
넓히지 않고 별도 작은 수정으로 남겨도 재작업이 크지 않다.

### 기존 기록과 새 설계가 다르게 말하는 부분

개편 전 시험 기록은 “아카이브를 검사에서 제외한다”는 결정을 담았다. 새 설계는
이를 전부 뒤집는 것이 아니라 검사의 층을 나눈다.

- 현재 운영 규칙 준수: 활성 문서에 엄격하게 적용
- 그래프 무결성: 활성 문서와 아카이브 모두에 적용
- 검색과 지도 생성: 아카이브 포함
- 과거 문서의 최신 규칙 준수와 최신성: 레거시에는 소급하지 않음

`docs/trials/README.md`의 현재 제한과 시험 설명은 구현이 바뀌면 새 실제 결과에
맞춰 갱신한다. 과거 검증 결과를 현재 동작처럼 남겨 두지 않되, 당시 사실은
레거시 아카이브와 Git 이력에서 보존한다.

다음은 기반 형식을 소비하는 기능이므로 이후 대작업으로 미룰 수 있다.

- 대규모 저장소용 고급 성능 최적화

## 하지 않을 것

- AI가 문서를 읽고 관계를 추측한 결과를 자동으로 원본 관계로 확정하지 않는다.
- AI API 키를 받거나 AI SDK·외부 모델 호출을 doltap CLI에 넣지 않는다.
- 임베딩이나 벡터 데이터베이스를 핵심 동작에 요구하지 않는다.
- Graphify의 Python 런타임이나 상주 훅을 그대로 가져오지 않는다.
- 에이전트의 모든 Read/Grep 실행을 가로막아 doltap 사용을 강제하지 않는다.
- 훅을 자동 설치하거나 doltap 사용의 필수 조건으로 만들지 않는다.
- 적용 프로젝트에 CI 구성을 요구하거나 CI 통과만을 유일한 검사 경로로 만들지
  않는다.
- 그래프 JSON이나 HTML을 사람이 편집하는 두 번째 원본으로 만들지 않는다.
- 같은 ID를 복제본, 미러, 이전 버전에 공유하지 않는다.
- 파일 관계와 항목 관계에 서로 다른 ID·링크 체계를 만들지 않는다.
- 검토 여부를 Git 커밋 유무로 대신하지 않는다.

Graphify에서 가져오는 것은 “관계를 기계가 읽을 수 있게 만들고 파생 그래프를
생성한다”는 관점과 명시 관계·추론 관계를 구분하는 태도다. doltap은 관계의 원본을
사람이 읽는 마크다운에 명시하고, AI 없이 결정적으로 검사하는 방향을 유지한다.

## 구현 전에 확정하거나 시험할 것

아래는 처음 설계할 때 남겼던 27개 질문이다. 현재 형식은 [현재 사양](document-graph-spec.md)에 정리했다. 당시의 처리 표와 조사 과정은 009의 기록에 남는다.

1. `Cairn`을 대신할 공개 이름과 그에 맞는 npm 패키지명, CLI, 운영 폴더와 앵커
   접두사

6. 대상별 최신 검토와 누적 감사 제안의 저장 위치 및 삭제된 대상 기록의 보존 정책
7. 관계 ID를 결정적으로 만드는 정확한 입력과 문자열 형식

   둘지

12. 일반 링크를 모두 `references`로 볼지, doltap ID 조각이 있는 링크만 그래프
    엣지로 볼지
13. 명시적 외부 문서 등록의 정확한 문법과 `CLAUDE.md` 특수 연결을 그래프에서
    표현할 내부 방식
14. 저장소 전체를 탐색할 때 `.git`, `node_modules`, 생성물 등 제외 규칙
15. 기존 제목 조각 링크를 유지·경고·자동 이관하는 정책
16. 빈 `<a name="...">` 앵커의 지원 렌더러인 GitHub 저장소 README와 VS Code
    기본 마크다운 미리보기 동작을 실제 fixture로 확인할 것. 다른 렌더러는

17. 파일 이동 복구와 자동 수정이 경로를 바꾸기 전 보여줄 diff 형식

## 009 워크스트림의 완료 조건

009 워크스트림은 다음 조건을 모두 만족해야 완료로 판단한다. 이 목록을 바꾸는
것은 대작업의 완료 조건을 바꾸는 일이므로 변경 이유를 `decisions.md`에 남긴다.

- 새 공개 이름이 정해지고 npm 패키지명, CLI, 운영 폴더와 앵커 접두사에 옛 이름
  `cairn`이 의도치 않게 남아 있지 않다. 역사와 출처를 설명하는 문장은 예외다.
- 운영 폴더와 임시 클론 폴더의 이름이 충돌하지 않는다.
- 기존 저장소와 새 template 결과가 같은 새 구조를 사용한다.
- 기본 관리 범위가 `AGENTS.md`, 특수 연결인 `CLAUDE.md`, 새 운영 폴더의
  `**/*.md`로 제한되고, 다른 문서는 명시적으로 등록했을 때만 그래프 관리 대상이
  된다.
- 파일·section·block을 표준 문법으로 식별할 수 있다.
- 중복 ID, 잘못 닫힌 범위, 교차 범위, 없는 대상과 고아 문서를 잡는다.
- 같은 ID를 이동 후 발견해 깨진 경로의 복구 후보를 제시한다.
- 단방향·대칭·실제 상호 관계가 중복 없이 표현되고 역방향 조회가 된다.
- 아카이브가 지도와 검색에 남고, 활성 상태에서는 분리된다.
- 아카이브 전에 살아 있는 전제와 열린 질문이 해결·승격·폐기 중 하나로 처리되며,
  활성 판단이 의존하는 아카이브 전제를 `context`에서 찾을 수 있다.
- 참조 중인 파일이나 범위를 조용히 삭제할 수 없다.
- 노드 자신의 검토와 관계 영향 검토가 구분되고, 상태가 필요한 관계는 현재 양쪽
  `contentHash`와 대상별 마지막 검토 해시를 비교할 수 있다.
- `영향 없음`에는 이유와 검토 주체가 남고, 관계 검토가 사용자 작업 승인으로
  해석되지 않는다.
- `context`가 특정 ID에서 필요한 범위만 깊이와 출력 예산 안에서 제공한다.
- `audit`가 선택한 폴더·문서 범위의 기계적 문제와 호스트 AI 검토 후보를
  구분해서 제공한다.
- AI가 없는 로컬 터미널에서도 기계적 검사·지도·맥락·감사 후보 생성이 동작한다.
- doltap CLI는 AI API 키나 직접적인 외부 모델 호출을 요구하지 않는다.
- Git이 없는 임시 프로젝트에서 검사와 지도 생성이 동작한다.
- 새 운영 폴더가 gitignore된 로컬 프로젝트에서도 같은 로컬 기능이 동작한다.
- 개인이 수동으로 실행하는 로컬 검사가 완전한 기본 경로이고, 같은 검사기를
  선택적 Git·에이전트 훅에서 호출할 수 있다.
- CI는 적용 프로젝트의 필수 조건이 아니며, 원본이 전달되는 프로젝트가 원하면
  같은 검사기를 호출할 수 있다.
- 적용된 프로젝트에는 상주 프로세스나 필수 외부 런타임 의존성이 남지 않는다.
- 그래프 JSON은 마크다운에서 다시 생성할 수 있고 원본으로 취급되지 않는다.
- 전환 중 기본 검사는 새 그래프 이관량을 요약 NOTICE로 항상 보여주고, 엄격
  검사에서는 같은 항목이 실패한다. 이관 완료 뒤 새 검사가 기본 실패 조건으로
  승격된다.
- 구형 구조를 만나면 일반적인 필수 파일 오류만 내지 않고, 구조 변경과 이관 안내
  위치를 알려준다.
- 문서를 고치는 이관·복구 명령은 변경 미리보기와 승인 뒤 실행되며 중간 실패에도
  원본을 잃지 않는다. 구형 구조를 영구 지원하는 호환 계층은 요구하지 않는다.
- 기존 경로와 문법을 사용하는 README, APPLY, template, setup-workstream,
  시험에 오래된 안내가 남지 않는다.

## 다음 세션에서 이 문서를 사용하는 방법

워크스트림은 열렸지만 **이 문서를 읽었다고 구현 승인을 받은 것은 아니다.**
작업 위치와 브랜치, 무엇을 승인받았는지는
`.doltap/plans/workstreams/009-document-graph/status.md`에 있고, 단계와 검증

정확히 설명하지 않으면 상태 표기와 관련 절을 함께 갱신한다.
