# 문서 그래프 기반 — 계획

> 무엇을 왜 하는지는 `README.md`, 지금 어디까지 왔는지는 `status.md`에
> 있습니다. 여기는 순서와 검증 방법만 담습니다.

순서를 정하는 기준은 **무엇을 두 번 하게 되는가**입니다. 이름은 운영 폴더와
앵커 접두사를 통해 모든 문서와 ID에 박히므로 먼저 정합니다. 형식은 검사기가
무엇을 잡을지 결정하므로 코드보다 먼저 확정합니다. 이관은 검사기가 잡아 줄
수 있게 된 뒤에 합니다.

**이 계획은 1~2단계 뒤에 다시 자릅니다.** 지금은 확정되지 않은 형식 위에 세운
순서라, 형식이 정해지면 3단계 아래는 모양이 달라질 수 있습니다.

## 1. 새 공개 이름을 정한다

**사용자가 정할 항목입니다. 이름에 의존하는 작업이 여기서 막힙니다** — 운영
폴더 이름 변경, 앵커 접두사, 불변 ID 발급, 그 ID를 실제 문서에 넣는 일입니다.
2단계의 형식 확정과 3단계의 파서·검사기는 이름과 무관하게 진행할 수 있습니다.

같은 분야에 같은 이름과 `.cairn` 폴더를 쓰는 도구가 여럿이라 검색과 설명만이
아니라 CLI·폴더의 실제 충돌 가능성이 있습니다. 배경은 설계 기록의 「프로젝트
이름과 운영 폴더 전환」에 있습니다.

한 번에 정할 다섯 값입니다.

```text
공개 이름 · npm 패키지명 · CLI 명령 · 운영 폴더 · 앵커 접두사
```

검증

- 후보마다 npm 레지스트리, GitHub 저장소, 일반 검색에서 충돌을 다시 확인한다.
  `ideas.md`의 2026-09-07 확인 결과를 그대로 쓰지 않는다.
- 운영 폴더 이름이 적용할 때 쓰는 임시 클론 폴더 이름과 겹치지 않는지 본다.
- 다섯 값이 모두 정해졌을 때만 다음으로 간다. 하나라도 미정이면 2단계에서
  이름에 의존하지 않는 항목만 진행한다.

## 2. 형식을 확정한다

설계 기록의 「구현 전에 확정하거나 시험할 것」 27개를 각각
확정·시험 대상·범위 밖으로 가릅니다. 결과는 `design.md`(형식)와
`decisions.md`(결정과 이유)에 남깁니다.

**이름을 기다리지 않고 먼저 할 수 있는 항목**이 있습니다. 1단계가 늦어져도
여기부터 진행합니다.

- 20번 정규화 규칙 — `contentHash`에서 줄바꿈·공백·경계 앵커·관계 선언·표시
  이름을 어떻게 다룰지. **이 대작업에서 가장 어려운 항목입니다.**
- 8·10~12번 관계 어휘 — 초기 관계 유형, 역관계, 대칭 여부, 어느 쪽 변경이 검토를
  만료시키는지, `mirror-of`와 `update-with`의 차이
- 16번 렌더러 동작 — 빈 `<a name="...">` 앵커가 GitHub·VS Code·주요 마크다운
  렌더러에서 어떻게 보이는지
- 9번 살아 있는 항목 — `assumes`를 기본 관계로 둘지, 아카이브 종료 시 활성
  문서로 승격하는 구조만 둘지 정합니다. 전제와 열린 질문의 선언 표식,
  해결·승격·폐기 상태와 아카이브를 막는 조건도 함께 확정합니다. 7단계 검사가
  자연어의 뜻을 추측하지 않고 판정하려면 여기서 기계적인 문법이 나와야 합니다.

검증

- 27개 항목에 빠짐없이 처리 결과가 붙는다. 「나중에 정함」으로 남는 항목이
  없다.
- 16번은 글로 판단하지 않고 실제 fixture를 만들어 각 렌더러에서 눈으로
  확인한다. 여기서 형식이 흔들리면 3단계 이후가 통째로 바뀌므로 먼저 본다.
- 20번은 같은 뜻인데 서식만 다른 쌍과, 서식은 같은데 뜻이 바뀐 쌍을 각각
  만들어 어느 쪽이 해시 변경으로 잡히는지 시험으로 고정한다.
- 9번은 처리하지 않은 항목과 해결·승격·폐기한 항목을 각각 표현할 수 있고,
  아카이브를 막아야 하는 상태가 문법만으로 구분되는지 fixture로 확인한다.

## 3. 파서와 검사기를 fixture에서 만든다

실제 문서를 건드리기 전에 fixture에서 엄격하게 만듭니다. 순서를 뒤집으면 아직
이관하지 않은 문서 때문에 검사가 늘 실패하고, 그 상태에 익숙해집니다.

만들 것은 상태가 필요 없는 검사부터입니다 — 앵커 문법, 닫히지 않은 범위, 교차
범위, ID 유일성, 접두사와 종류 일치, 허용되지 않은 관계 유형, 링크 대상 존재,
도달성입니다. 관계 선언은 한 번만 저장하되 나가는 관계와 들어오는 관계를 모두
조회할 수 있도록 역방향 색인을 같은 단계에서 계산합니다.

검증

- 잡아야 할 경우와 잡으면 안 되는 경우를 쌍으로 시험한다. `~~~` 울타리와 네
  칸 들여쓴 코드 블록을 여기서 함께 고정한다.
- 관계를 한쪽에 한 번 선언했을 때 출발점에서는 나가는 관계, 도착점에서는
  들어오는 관계로 조회된다. 단방향 관계의 역관계 이름과 대칭 관계의 표시가
  2단계에서 정한 어휘대로 나오는지 함께 고정한다.
- 사람용 출력, 종료 코드, 기계용 JSON 출력 셋이 같은 판정을 낸다.
- `npm test`가 통과한다.

## 4. ID 생성과 발급 기록을 만든다

Node 내장 난수로 후보를 만들고, 관리 범위 전체와 발급 기록에서 중복을
검사합니다. 발급 기록은 사람이 읽는 마크다운으로 둡니다.

검증

- 같은 범위에 두 번 실행해도 새 ID를 만들지 않고 기존 ID를 돌려준다.
- 삭제 표식이 남은 ID를 다시 발급하지 않는다.
- 두 명령이 동시에 실행돼도 같은 ID가 두 곳에 생기지 않는다.
- 실행이 끝난 뒤 잠금 파일이 남지 않는다.

## 5. 이름과 운영 폴더를 옮긴다

1단계에서 정한 이름으로 한 번에 바꿉니다. 함께 움직일 곳은 설계 기록의 「운영
폴더를 바꾸는 범위」에 있습니다.

검증

- 저장소 전체를 검색해 옛 이름이 현재 사용법으로 남은 곳이 없다. 역사와 출처를
  설명하는 문장만 남는다.
- 새 이름의 `init`으로 빈 폴더에 골격을 만들고, 그 결과가 곧바로 검사를
  통과한다. 골격 문서만 읽고 판단하지 않는다.
- 임시 클론 폴더 이름이 새 운영 폴더와 겹치지 않는다.

## 6. 문서에 ID와 관계를 부여하고 레거시를 동결한다

이 저장소의 활성 문서와 `template/`에 ID와 관계를 넣습니다. 기존 아카이브는
지우지 않고 레거시로 옮겨 동결합니다 — 문서 단위 ID만 주고 세부 범위는 소급하지
않습니다.

검증

- 관리 범위 안의 문서가 모두 진입점에서 도달된다. 고아 문서가 0이다.
- 레거시 아카이브에 문서 ID 중복·깨진 범위·없는 대상이 없다. 최신 관계 규칙은
  강제하지 않는다.
- `history.md`에서 각 레거시 워크스트림의 `README.md`로 이어진다.
- 이관 명령이 변경 미리보기를 보여주고 승인 뒤에 실행하며, 중간에 멈춰도 원본이
  남는다. 일부러 중간에 끊어 확인한다.

## 7. 이동·삭제·아카이브의 의미를 구현한다

완료 조건에는 들어 있는데 단계에 자리가 없던 셋입니다. 문서에 ID가 실제로 박힌
뒤라야 뜻이 생기므로 6단계 다음에 둡니다.

선행 조건은 3단계의 파서와 역방향 색인, 4단계의 발급 기록, 6단계의 ID 부여이고,
아카이브 전 검사는 2단계에서 나온 「살아 있는 항목」 문법이 있어야 합니다.

**이동 복구.** 경로가 깨진 링크를 만나면 같은 ID가 있는 새 위치를 찾아 수정안을
만듭니다. 경로를 바꾸기 전에 무엇을 어떻게 고칠지 보여주고 승인을 받습니다.

**참조 중 삭제 방지.** 삭제 전에 대상으로 들어오는 관계를 모두 보여주고, 참조가
남아 있으면 기본적으로 거부합니다. 대체·삭제 표식·완전 삭제 세 갈래를 둡니다.
파일 삭제는 그 안의 모든 자식 ID까지 함께 봅니다.

**아카이브 전 전제 처리.** 워크스트림을 아카이브하기 전에 해결되지 않은 전제와
열린 질문이 해결·승격·폐기 중 하나로 처리됐는지 검사합니다. 활성 영역에서 찾을
길이 없는 채로 아카이브에만 남는 것을 막는 것이 목적입니다.

검증

- 이동한 ID의 복구 후보가 실제로 나오고, 승인하기 전에는 파일이 바뀌지 않는다.
- 같은 ID가 두 곳에서 발견되면 자동으로 고르지 않고 멈춘다.
- 참조가 남은 노드를 지우려 하면 거부하고 들어오는 관계를 보여준다.
- 파일을 지울 때 그 안의 자식 ID로 들어오는 관계도 함께 걸린다.
- 삭제 표식이 남은 ID가 다시 발급되지 않는다.
- 처리하지 않은 전제가 남은 워크스트림은 아카이브 전 검사에서 걸리고, 처리한
  전제는 걸리지 않는다. 두 경우를 쌍으로 고정한다.

## 8. 상태 기능을 붙인다

`contentHash`와 `graphHash`를 나누고, 누적 검토 기록과 만료 판정을 만듭니다.

검증

- 서식만 바꾼 변경이 재검토를 일으키지 않는다.
- 뜻이 바뀐 변경은 관계 유형이 정한 쪽에서 재검토를 일으킨다.
- 상대가 관계 하나를 더했다는 이유로 재검토가 관계망을 타고 번지지 않는다.
- 「영향 없음」이 이유 없이 기록되지 않는다.
- 모든 항목을 한 번에 검토 완료로 만드는 명령이 없다.

## 9. 지도·맥락·감사를 만든다

지도 출력은 아카이브를 포함하고, 맥락 조회는 깊이와 출력 예산 안에서 필요한
범위만 돌려주며, 감사는 사용자가 고른 폴더·문서 범위의 기계적 문제와 호스트 AI
검토 후보를 나눠서 냅니다. 명령 이름은 2단계에서 함께 확정합니다.

검증

- **007 누락 사례를 회귀 시험으로 고정한다.** 활성 판단이 의존하는 아카이브의
  전제를 맥락 조회가 실제로 찾아낸다. 이 시험이 이 대작업의 목적 자체를
  검사한다.
- 오류·재검토 필요·제안·모호함이 출력에서 섞이지 않는다.
- AI 없는 터미널에서 검사·지도·맥락·감사 후보 생성이 모두 동작한다.
- Git 저장소가 아닌 임시 폴더와 운영 폴더가 gitignore된 폴더에서 같은 결과가
  나온다.

## 10. 전환을 승격하고 기록을 정리한다

이관이 끝나면 새 검사를 기본 실패 조건으로 올리고 임시 옵션을 걷어냅니다.

- 전환 중 기본 검사가 내던 이관 현황 요약을 걷는다.
- 선택적 Git·에이전트 훅 연결 예시와 제거 방법을 문서에 남긴다.
- `docs/trials/README.md`의 「알려진 제한」과 「검증하지 않는 것」을 실제 결과에
  맞춰 갱신한다. 과거 검증 결과를 현재 동작처럼 남기지 않는다.
- `ideas.md`에서 이 대작업이 흡수한 항목을 지운다.
- `docs/document-graph-design.md`의 상태 표기와 달라진 절을 갱신한다.

검증

```text
npm test
새 이름의 check template
새 이름의 check .
빈 폴더에 init → check
```

넷 다 통과하고 문제가 0이어야 합니다. 확인으로 남는 항목이 있으면 무엇이 왜
남았는지 `status.md`에 적습니다.

## 이 계획에 없는 것

반영, push, 아카이브, 릴리즈는 이 계획의 단계가 아닙니다. 각각 사용자 승인을
따로 받고 하며, 절차는 `.agents/plans/workstreams.md`의 「마칠 때」에 있습니다.
