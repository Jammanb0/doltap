# 문서 그래프 기반 — 결정

> 이 대작업을 운영하며 정한 것과 그 이유를 둡니다. 아직 정하지 않은 것은 여기
> 적지 않습니다 — 설계 기록의 「구현 전에 확정하거나 시험할 것」과
> `status.md`의 열린 질문에 있습니다.

## 설계 기록을 워크스트림 문서에 복제하지 않는다

`docs/document-graph-design.md`가 설계의 원본입니다. 합의한 결정 24개와 미확정
항목 27개, 009의 완료 조건이 모두 그 안에 있습니다.

이것을 `README.md`나 `design.md`로 옮겨 적으면 같은 내용의 원본이 둘이 됩니다.
한쪽만 고치는 순간 갈라지고, 어느 쪽이 맞는지 판단하는 비용이 계속 듭니다.
`AGENTS.md`가 「같은 규칙의 상세 내용을 여러 문서에 독립된 원본으로 복제하지
않습니다」라고 정한 것과 같은 이유입니다.

그래서 워크스트림 문서는 묶음 이름과 절 제목으로 가리키기만 합니다. 설계가
바뀌면 설계 기록을 고치고, 이 폴더에는 그 대작업을 운영하며 새로 정한 것만
남깁니다.

## 설계 기록의 완료 조건을 009의 종료 기준으로 확정한다

설계 기록의 「009 워크스트림의 완료 조건」을 이 대작업의 종료 기준으로
채택합니다. `README.md`는 그 목록을 복제하지 않고 해당 절을 가리키며, 아래에
009가 별도로 만족할 조건만 덧붙입니다.

해당 절을 고치는 것은 참고 문구를 다듬는 일이 아니라 완료 조건을 바꾸는
일입니다. 구현 중 사실이 달라져 목록을 바꿔야 한다면 설계 기록과 `README.md`의
참조를 함께 확인하고, 무엇을 왜 바꿨는지 이 문서에 남깁니다.

## 이름 결정을 대작업 밖이 아니라 1단계로 둔다

설계 기록 초안에는 다음 두 문장이 함께 있었습니다.

```text
「기반 대작업을 열기 전에 새 공개 이름을 결정한다」
「그 대작업의 첫 제품 결정은 Cairn 을 대신할 공개 이름이며」
```

009를 열면서 뒤쪽을 따르기로 정했고, 설계 기록의 현재 문구도 그 결정에 맞췄습니다.
대작업 밖에서 정하면 후보와 기각 이유, 충돌 확인 결과가 어디에 남을 자리가
없습니다. 이름은 운영 폴더와 앵커 접두사를 통해 모든 문서에 박히는 결정이라
근거가 남아야 합니다.

대신 막히는 범위를 분명히 합니다. 이름이 정해지기 전에는 불변 ID를 발급하지
않고, 폴더와 명령 이름을 바꾸지 않습니다. 정규화 규칙과 관계 어휘, 렌더러 동작
확인은 이름에 의존하지 않으므로 먼저 진행합니다.

## 새 공개 이름은 `doltap`으로 한다

2026-09-11에 사용자가 정했습니다. 돌탑은 돌을 하나씩 쌓아 길을 알리는 것이라
`cairn`과 뜻이 같습니다. 이름만 바꾸고 은유는 그대로 가져갑니다.

다섯 값을 한 번에 맞춥니다.

| 무엇 | 값 |
| --- | --- |
| 공개 이름 | `doltap` |
| npm 패키지명 | `doltap` |
| CLI 명령 | `doltap` |
| 운영 폴더 | `.doltap/` |
| 앵커 접두사 | `doltap` |

앵커는 `doltap-s-3q8m5k-start` 모양이 됩니다. 설계 기록의 예시와 한 자 차이라
범위 문법을 다시 손댈 필요가 없습니다.

채택 조건을 만족한 결과입니다. 2026-09-11 확인이고, 같은 주소로 다시 볼 수
있습니다.

| 확인한 것 | 결과 | 다시 보는 곳 |
| --- | --- | --- |
| npm에 같은 패키지 | 없음 (404) | `https://registry.npmjs.org/doltap` |
| 이름이 정확히 같은 저장소 | 없음 | `https://api.github.com/search/repositories?q=doltap+in:name` |
| 이름이 정확히 같은 계정·조직 | 없음 (404) | `https://api.github.com/users/doltap` |
| 같은 분야 충돌 | 확인한 범위에서 없음 | 일반 검색 |

이름 일치 검색에 걸린 것은 `doltap-legal` 하나이고 이 분야와 무관합니다. 마지막
줄은 검색으로 확인한 것이라 **없다는 증명이 아니라 확인되지 않았다는 뜻**입니다.

**임시 클론 폴더는 `.doltap-bootstrap/`으로 따로 둡니다.** 지금은 적용할 때
저장소를 얕게 클론하는 임시 폴더가 운영 폴더와 같은 이름을 쓰게 되어 있어,
운영 폴더가 `.doltap/`이 되면 겹칩니다. 이름을 갈라서 충돌을 없앱니다.

npm 패키지명에 접미사를 붙이지 않아도 됩니다. `cairn`은 이미 있는 패키지라
`cairn-agents`를 써야 했지만, `doltap`은 비어 있어 명령·폴더·패키지명이 모두
같은 문자열이 됩니다.

**이름만 정했고 아직 바꾸지 않았습니다.** 실제 폴더와 명령 이름은 `plan.md`의
5단계에서 옮깁니다. 그때까지 문서는 `.agents/`와 현재 명령을 그대로 가리킵니다.

## 이름 충돌은 이름 일치 검색으로 본다

키워드 검색은 별 수로 정렬해서 작은 저장소를 덮습니다. `varde`를 키워드로 찾았을
때는 상위 결과가 전부 무관한 것이라 통과로 보였는데, 이름 일치 검색으로 다시
보니 같은 분야의 AI 에이전트 기억 시스템이 있었습니다.

별이 적다고 충돌이 아닌 것이 아닙니다. 이름이 겹치면 CLI 명령과 운영 폴더가
겹치고, 그게 이 이름을 바꾸는 이유입니다.

## 이름 후보에서 기각한 것과 그 이유

2026-09-11에 확인했습니다. npm은 `npm view <이름>`, GitHub는 이름 일치 검색으로
봤습니다.

| 후보 | 기각 이유 |
| --- | --- |
| `cairn` | npm에 이미 있고, 같은 분야 도구가 같은 이름과 운영 폴더를 씁니다 |
| `varde` | 이름이 같은 저장소가 20곳이 넘고, 그중 하나가 AI 에이전트 기억 시스템입니다 |
| `menhir` | OCaml LR 파서 생성기로 널리 쓰입니다. 마크다운을 파싱하는 도구가 쓰면 헷갈립니다 |
| `selvage` | 이름이 같은 자율 코드 구현 파이프라인이 있습니다. 피하려던 충돌과 같습니다 |
| `lodemark` | 같은 이름의 조직이 Claude Code용 지시 파일 도구를 만들고 있습니다 |
| `waymarker` | 이름이 같은 저장소 하나가 AI 튜터링 에이전트입니다 |
| `sarsen` | 위성 SAR 처리 라이브러리와 이름이 같고, 이름 일치 저장소가 30곳입니다 |
| `stele` `waypoint` `lodestar` `throughline` `ogham` `catena` `colophon` `quipu` `trailhead` `blaze` `dolmen` 등 | npm에 이미 있습니다 |

**단어 하나짜리 이름은 npm이 거의 다 차 있습니다.** 뜻이 맞는 후보 30여 개 중
npm이 비어 있던 것은 열셋뿐이었고, 그중 대부분이 GitHub에서 걸렸습니다. 「어디에도
같은 이름이 없는 단어」를 기준으로 삼으면 고를 수 있는 것이 남지 않습니다.
그래서 기준을 **AI 에이전트·개발 도구 영역에 같은 이름이 없을 것**으로 둡니다.

## 이름이 정해진 뒤에도 5단계까지는 현재 경로를 가리킨다

이름을 정했다고 문서가 `.doltap/`을 가리키기 시작하면, 아직 존재하지 않는
폴더를 가리키는 글이 됩니다. 실제 이관은 `plan.md` 5단계이고, 그전까지 이
저장소의 운영 폴더는 `.agents/`입니다.

그래서 문서에서 `.doltap/`과 `doltap` 명령은 **앞으로 그렇게 된다는 설명**으로만
씁니다. 지금 무엇을 읽고 실행해야 하는지 알려 주는 자리에는 현재 경로와 현재
명령을 그대로 둡니다.

불변 ID도 같습니다. 접두사는 `doltap`으로 정해졌지만 발급은 4단계와 6단계에서
시작합니다. 파서와 발급 기록이 없는 상태에서 먼저 박아 두면 중복 검사와 재사용
방지를 거치지 않은 ID가 남습니다.

덧붙여 현재 검사기는 활성 문서에 남은 임시 골격 참조를 확인 항목으로 올립니다.
기본 이름 뒤에 경로가 이어진 것만 세므로, 이름을 말로 부르는 문장은 걸리지
않지만 폴더 구조를 예시로 적으면 걸립니다.

## 계획 커밋을 기준 브랜치가 아니라 작업 브랜치에 둔다

`workstreams.md`의 기본 절차는 계획을 기준 브랜치에 커밋한 뒤 거기서 작업
브랜치를 가르라고 합니다. 다른 세션이 기준 브랜치만 읽어도 무엇이 진행 중인지
볼 수 있게 하려는 것입니다.

여기서는 그렇게 하지 않습니다. 사용자가 로컬 브랜치를 만들어 그 안에서
진행하라고 했습니다. 007과 008도 같은 이유로 계획 커밋을 작업 브랜치에 뒀고,
그 기록이 각 `status.md`에 남아 있습니다.

무엇을 잃는지 적어 둡니다. `main`의 `current.md`는 진행 중인 대작업이 없다고
말합니다. 이 브랜치를 모르는 세션은 이 대작업을 찾지 못합니다. 이어받으려면
브랜치 이름을 알아야 합니다.
