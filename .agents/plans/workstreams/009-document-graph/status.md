# 문서 그래프 기반 — 상태

> 배경과 완료 조건은 `README.md`, 단계와 검증 방법은 `plan.md`, 정한 것과 그
> 이유는 `decisions.md`에 있습니다. 여기는 지금 어디까지 왔고 다음이 무엇인지만
> 다룹니다.

## 작업 위치

| 항목 | 값 | 어떻게 정했나 |
| --- | --- | --- |
| 작업 위치 | `workstream/009-document-graph` | 사용자 지시 — "로컬 브랜치 하나 만들어서 진행하고" |
| 기준 브랜치 | `main` | 실제 작업 시작점 — 갈림점이 `main`의 `50cf939` |
| 반영 대상 브랜치 | `main` | 사용자가 이 대화에서 직접 확인 |
| 원격 작업 흔적 | 남기지 않음 — 원격 작업 브랜치·PR·병합 커밋 없음 | 사용자 지시 — "푸시는 진행하지 말아줘" |

기준 브랜치는 사용자가 따로 고른 값이라고 적지 않고, 실제로 이 작업 브랜치를
만든 시작점을 기록합니다. 작업 위치는 처음 요청에서, 반영 대상은 뒤에 사용자가
직접 정했습니다.

**원격 작업 흔적은 push 금지 지시에서 나온 값입니다.** 원격에 작업 브랜치를
만들고 PR을 열지는 따로 묻지 않았습니다. 나중에 push를 승인받으면 그때 다시
정합니다.

계획 커밋도 기준 브랜치가 아니라 이 브랜치에 둡니다. 그 이유와 대가는
`decisions.md`에 있습니다.

**받은 승인의 범위**

- 워크스트림 생성 — 받음 ("다음 대작업 세팅을 해야해. 진행해줘")
- 이 브랜치 안의 파일 변경과 로컬 커밋 — 받음 ("로컬 커밋을 승인하며")
- 반영 대상 브랜치를 `main`으로 확정 — 받음 ("반영 대상은 main이 맞다고 지금
  말해줄게")
- **설계와 실제 코드 수정을 포함한 009 진행 — 받음** ("작업 이어서 진행해줘.
  별도로 묻지말되"). 단계마다 진행 허락을 다시 묻지 않습니다
- push — **받지 않음** ("푸시는 진행하지 말아줘")
- `main` 반영 — **받지 않음**
- 대작업 종료와 아카이브 — **받지 않음**
- 작업 브랜치 삭제 — **받지 않음**

처음에는 세팅만 요청받아 구현 착수를 받지 않은 것으로 적어 두었는데, 그 뒤
사용자가 이어서 진행하라고 지시해 범위가 넓어졌습니다. 하지 말라고 한 넷은
그대로입니다.

## 현재 단계

`plan.md` 1~3단계를 마쳤습니다. 이름이 정해졌고, 형식이 `design.md`에 있으며,
파서와 상태 없는 검사가 fixture에서 동작합니다. 4단계 ID 생성에 들어가기
전입니다.

## 직전 완료

- **3단계 검사기의 관리 경계와 문법 검사를 보완했습니다.** 관계로 등록하는 외부
  문서는 저장소 안의 허용된 마크다운으로 제한하고 숨김·복구·제외 폴더 우회를
  막았습니다. `CLAUDE.md`의 존재와 `@AGENTS.md` 한 줄도 새 스키마에서 직접
  확인하며, 앵커의 가짜·중복 속성을 거부합니다. 살아 있는 항목의 아카이브 판정
  fixture는 실제 검사를 만드는 7단계로 문서 위치를 바로잡았습니다.

## 다음 행동

`plan.md` 4단계 — ID 생성과 발급 레지스트리를 만듭니다. 같은 범위에 두 번
실행해도 새 ID를 만들지 않는 것, 삭제 표식이 남은 ID를 다시 쓰지 않는 것,
동시 실행에서 같은 ID가 두 곳에 생기지 않는 것을 시험으로 고정합니다.

단계마다 진행 허락을 다시 묻지 않습니다. 받지 않은 것은 push, `main` 반영,
종료·아카이브, 브랜치 삭제입니다.

## 검증

3단계 코드를 넣은 뒤 돌린 것입니다.

| 확인 | 결과 |
| --- | --- |
| `npm test` | 89개 통과 (기존 42 + 그래프 47) |
| `node bin/cairn.mjs check template` | 문제 0, 확인 5 |
| `node bin/cairn.mjs check .` | 문제 0, 확인 0, 진행 중인 대작업 1개 |
| 빈 폴더에 `init` → `check` | 종료 코드 0 |
| `check . --schema next` | 문제 43개 — 모두 「문서 노드가 없습니다」 |

`check template`의 확인 5개는 골격이 일부러 비워 둔 채우기 자리입니다. 손대지
않았고 이 대작업 전에도 같은 수였습니다.

**`--schema next`의 43개는 정상입니다.** 아직 어느 문서에도 앵커가 없어서
나오는 것이고, 6단계에서 ID를 넣으면 사라집니다.

43개는 각 경로가 현재 관리 대상이고 아직 문서 노드가 없다는 것을 대조했습니다.
따라서 **이번 실행의 43개는 실제 위반**이지만, 개수와 문제 종류만으로 오탐이나
미탐이 없다고 넓혀 말하지 않습니다. 미탐은 설계에서 잡아야 할 입력을 따로 만들고,
오탐은 잡으면 안 되는 짝 입력을 함께 만들어 확인합니다.

## 막힌 점과 열린 질문

- **이름은 정해졌지만 아직 아무것도 바꾸지 않았습니다.** 문서와 코드는 여전히
  `.agents/`와 현재 명령을 씁니다. 폴더·명령 이름 변경은 5단계, 불변 ID 발급은
  4·6단계입니다. 그때까지 `.doltap/`을 가리키는 글을 쓰면 없는 폴더를 가리키게
  됩니다.
- `ideas.md`의 npm 등록 항목이 아직 `cairn-agents`를 써야 한다고 적고 있습니다.
  `doltap`이 비어 있어 접미사가 필요 없어졌습니다. 5단계의 저장소 전체 검색에서
  함께 걸러야 합니다.
- **이 구조를 쓰는 외부 프로젝트가 있는지 확인되지 않았습니다.** 없다고
  단정하지 않습니다. 확인되지 않았다는 것과 없다는 것을 섞어 쓴 것이 007에서
  고친 실수입니다.
- **VS Code에서 앵커가 목적지가 되는지 확인하지 않았습니다.** 이 세션에는
  확인할 수단이 없어 6단계로 미뤘고, `plan.md` 6단계 검증에 넣어
  두었습니다. 실제 문서에 앵커가 들어간 뒤 파일 하나를 열어 보면 끝납니다.
  거기서 안 되면 링크 표기를 다시 정해야 합니다. 그 밖의 렌더러는 지원 범위
  밖입니다.
- 정규화 규칙이 여전히 가장 위험한 항목입니다. `design.md`에 규칙과 판정 표를
  적었지만, 오탐은 소스만 읽어서 다 찾지 못하고 실제 문서를 고치는 동안
  드러납니다. 3단계에서 fixture로 고정하고 6단계에서 실제 문서에 써 봐야
  판단할 수 있습니다.
- `plan.md`의 4단계 아래는 3단계에서 파서를 만들어 보면 모양이 달라질 수
  있습니다.
